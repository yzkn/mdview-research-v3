# 公開用リポジトリへの移行手順

`./migration-v2` に置いた一式を、**public リポジトリへ載せる**ための手順。
社内向けの記録（設計書・手順書・計測）は含めない。

最終更新: 2026-10-09（2 回目以降の反映の手順を足した。§7）

---

## 0. 複製は**スクリプトで作り直す**

**手で写さない。** 本体へ手を入れるたびに複製へ写していると、必ずどこかが
ずれる。実際、2026-10-05 まで公開側のリリースワークフローは古いままだった。

```powershell
python tools/build-public-copy.py          # 作り直して検査する
python tools/build-public-copy.py --check  # 検査だけ
```

やっていること:

1. 複製側の「生成するもの」を消す（**書き下ろした文書と CI は残す**）
2. 本体から**許したものだけ**を写す
3. 写しながら**社名・文書名・社内向けの言い回し**を落とす
4. **禁止語が残っていないか調べる**（1 件でもあれば失敗して終わる）

### BOM は 1 つだけ（2026-10-08 に踏んだ）

公開側の組み立てが、Windows のインストーラを組む段で落ちた。

```
ParserError: build-installer.ps1:18
  18 |  [CmdletBinding()]
     | Unexpected attribute 'CmdletBinding'.
```

**BOM が 2 重になっていた。** 写すときに `utf-8` で読んでいたため、
BOM が U+FEFF という**文字として本文に残り**、そのうえで BOM を
足していた。

PowerShell は**先頭の 1 つ目だけ**を取り除く。2 つ目は見えない文字として
本文の先頭に残り、`#Requires` の行が文として解釈されて、次の
`[CmdletBinding()]` が「文の後の属性」になる。

|直し方|理由|
|---|---|
|読みを `utf-8-sig` にする|BOM を剥がして読む。**付けるのは 1 か所だけ**にする|
|**検査で捕まえる**|`--check` が本文の U+FEFF を見る。禁止語の検査では引っかからない|

壊れていたのは `build-installer.ps1` / `mdview.iss` / `sample.txt` の 3 件。
**検査を足してから壊し直し、落ちることを確かめてある。**

### なぜ「複製だけで試験が通る」では足りなかったか

**`cargo test` は Rust のソースしか触らない。** 複製の中身は Rust が
63 件、それ以外が 33 件あり、**配布物を組むスクリプトは一度も通らない。**

禁止語の検査も語しか見ない。どちらにも引っかからないまま、
公開側で走らせるまで分からなかった。

**「複製だけで試験が通る」を「公開できる状態」の根拠にしてはいけない。**
それが示すのは「Rust が自己完結していること」だけである。

### いま `--check` が見るもの

|見るもの|捕まえる壊れ方|
|---|---|
|禁止語|9 語|
|**本文の BOM**|2 重の BOM（今回のもの）|
|**`.sh` の改行と BOM**|CRLF だと `$'
': command not found`。BOM だと `#!` が効かない|
|**YAML の解析**|写したワークフローが壊れている|
|**`.ps1` の構文**|`pwsh` で解析する（Windows でのみ）|

**飛ばした検査は「飛ばした」と出す。** 黙って通すと、確かめていない
ものを確かめたことにしてしまう。

5 つとも、**わざと壊して落ちることを確かめてある。**
確かめる過程で、`.ps1` の検査が**1 本も見ていない**ことが分かった
（`pwsh -Command` は後ろに並べた引数を `$args` に束縛しない）。
**壊して確かめなければ、検査を足したつもりで何も見ていなかった。**

### それでも残る穴

**写したものを実行してみる以外に、確かめる方法は無い。**
`.iss` の中身・`fetch-fonts.py` の動作・パッケージが実際に組めるかは、
公開側でリリースを 1 回通すまで分からない。

> **本体側では起きない。** 本体のファイルは BOM が 1 つで、
> 手元の組み立ては通っていた。**写したものだけが壊れていた**ので、
> 公開側で走らせるまで分からなかった。

### 「写すものを選ぶ」のであって「除外を並べる」のではない

除外の一覧で管理すると、**新しく足したフォルダが黙って公開側へ入る**。
`COPY_DIRS` / `COPY_FILES` に無いものは公開されない。
フォルダを足したら、公開してよいかを考えてからスクリプトへ足す。

## 4. 載せる手順

1. GitHub で **public の空リポジトリ**を作る（README も .gitignore も付けない）
2. `python tools/build-public-copy.py` で複製を作り直す
3. `migration-v2` の中身を、新しい作業フォルダへ複製する
4. **`git init` から始める**（このリポジトリの履歴は持ち込まない。後述）
5. `git add -A && git commit`（最初のコミット）
6. `git remote add origin <新しいリポジトリ>` して push

### 履歴を持ち込まない

**このリポジトリの履歴には、コミットの作成者情報と、共同作業の記録が
すべて残っている。** `git clone` や `git subtree` で持ち込むと、ファイルを
削っても履歴からたどれる。**新しい履歴として始める**こと。

### 最初のコミットの作成者

`user.name` と `user.email` は、公開して差し支えない値にしてから
コミットする（既定のままだと社内のアドレスが入る）。

```
git -c user.name="<公開名>" -c user.email="<公開アドレス>" commit -m "..."
```

## 5. 載せる前に確かめること

```powershell
# 禁止語が残っていないか
python tools/build-public-copy.py --check

# 複製だけでビルドと試験が通るか（本体を参照していないか）
cd migration-v2
cargo clippy --all-targets -- -D warnings
cargo test
```

**「本体を参照していないか」が要点。** 複製だけで完結していないと、
公開先で初めて気づくことになる。

## 7. 2 回目以降の反映（公開済みのリポジトリを更新する）

§4 は最初の 1 回の手順である。**公開済みのリポジトリへ版を足すときはこちら。**
履歴は公開側のものを続ける（`git init` し直さない）。

### 7-1. 手順（2026-10-14 から。公開用 PC ではふつうにコミットして push する）

**公開用 PC には本体のリポジトリも本体の ZIP も置かない**（git と `gh` は公開用のアカウントで
認証してある）。**本体の ZIP は落とさない**（2026-10-13 に禁止。`migration-v2/` の外の文書も入る）。
公開側の clone に `migration-v2/` の中身だけを置き、確かめてからコミットして push する。
手順は [リリース手順](リリース手順.md) §3。

|順|どこで|やること|
|---|---|---|
|1|この PC|複製を作り直す（`python tools/build-public-copy.py`）→ コミット → push（利用者）|
|2|本体の CI|**「公開用の複製が最新か」を見る**（作り直し忘れで落ちる）|
|3|公開用 PC|clone に `migration-v2/` の中身を置き、`git status` で確かめてコミット・push|
|4|公開側の CI|版数が新しければタグを打って Release を作る|

**`publish.ps1` はやめた**（v2.2.0）。タグと Release を CI が作るようになり、スクリプトで包む手間が要らなくなった。

**ファイルは自動では消えない。** 本体で消したファイルは、置くときに clone からも消す。
公開側で直接直したものは本体へ戻してから置き直す。

### 7-2. 手書きの `.github/` を本体と突き合わせる

公開側の `ci.yml` と `release.yml` は手書き（`KEEP`）で、本体を直しても追従しない。
**段の中身がずれていないか**を、版を出すたびに見る。

**Actions の版も揃える**（2026-10-13）。公開側の Dependabot はやめたので、公開側の Actions
（`checkout` など）は誰も上げない。本体の Dependabot が上げたら、公開側の 2 つにも同じ版を入れる。
複製を作り直すと、版が違う Action を「（知らせ）… の版が違う」と出す（止めはしない）。

```powershell
git diff --no-index .github/workflows/ci.yml migration-v2/.github/workflows/ci.yml
```

**意図して違うもの**（これ以外の差分があれば、公開側へ入れ忘れている）:

|ファイル|違い|
|---|---|
|`ci.yml`|公開側は 3 OS で常に回し、**組んで包むところまで行い、push で版数が新しければ Release を作る**。本体は push・PR では Linux の検査だけで、**手で起動して Linux 以外を選んだときだけ**組んで包み、本体の Release（`v<版数><英字>`）を作る（`os` の入力・「公開用の複製が最新か」の段）。コメントの文書名・実行分の記述|
|`release.yml`|**公開側にしか無い**（作り直し用。本体は ci.yml の release ジョブで作る）|

`ci.yml` の検査の段（書式・Lint・試験）は本体と揃える。包む段と `release.yml` は公開側にしか無い。
Actions の版の更新（Dependabot の PR）は本体で取り込んだら、公開側の `ci.yml` にも入れる。

## 載せる順序（いま実行するなら）

1. 上の「先に決めること」を決める
2. 決めたアカウントで **public の空リポジトリ**を作る
3. `python tools/build-public-copy.py` で複製を作り直す
4. `migration-v2` の中身を、**新しい作業フォルダへ複製する**
   （`target/` は 4GB あるので写さない）
5. **`git init` から始める**（履歴を持ち込まない。§4）
6. `user.name` / `user.email` を上書きして最初のコミット
7. `git remote add origin <新しいリポジトリ>` して push
8. 版数を上げた状態で `main` へ push すると、公開側の CI がタグと Release を作る（[リリース手順](リリース手順.md) §3）
9. 出来た `.deb` で **WSL のファイル選択を確かめる**
   （[手順](Linux版をWSLgで確認する.md)。R-06）
