# リリース手順

対象: v2.0.0 以降
最終更新: 2026-10-14（v2.2.0: `publish.ps1` をやめ、公開用 PC ではふつうにコミットして push する）

> **配るときは §3 を上から順に行う。** 本体で版数を上げて push し、公開用 PC の
> 公開側の clone に `migration-v2/` の中身を置いてコミット・push すると、公開側の CI が組んで、**タグと Release まで作る**。

---

## 0. この手順の考え方

**配布物は GitHub Actions が作る。** 手元の端末でビルドしない。

v1 では Windows でビルドし、WSL で deb を作り、macOS 実機で dmg を足していた。
v2 では 3 OS ぶんを runner が組むので、**手元でやるのは版数の更新とタグ打ちだけ**
である（基本設計書 §27）。

|やること|どこで|
|---|---|
|版数の更新・CHANGELOG の確定・複製の作り直し|手元（この PC）|
|本体へ push|利用者|
|公開側の clone に `migration-v2/` の中身を置き、コミット・push|**公開用 PC**（git。§3-1）|
|タグ|**公開リポジトリの CI**（版数が新しいときだけ）|
|3 OS のビルド・パッケージ・煙試験|**公開リポジトリの CI**（`main` への push で走る）|
|Release の作成・成果物の添付|**公開リポジトリの Release**（CI の成果物を載せるだけ）|
|**目で見る確認**|手元（§4）|

**署名はしない**（基本設計書 §27.4）。代わりに SHA-256 の照合値を添える。

## 1. 組み立てる場所（2026-10-06 に移した）

**配布物は公開リポジトリ側で組む。**

|リポジトリ|実行分|リリースの引き金|
|---|---|---|
|**公開**（public）|**無料**|**`main` への push で、版数が新しければ自動**（CI の `release` ジョブがタグと Release を作る）|
|本体（private）|**課金される**|**無い**（2026-10-13 に Release をやめた。CI だけ）|

公開側のワークフローは 2 つで、**3 OS のビルドはリリース 1 回につき 1 回ずつ**（2026-10-13 から）。

|ワークフロー|いつ走るか|やること|
|---|---|---|
|**CI**（`ci.yml`）|`main` への push・PR・手動|3 OS で検査（書式・Lint・単体試験・GUI 試験）→ **組む → 包む**（インストーラ・`.deb`・AppImage・`.dmg`）→ 煙試験。出来たものを成果物 `dist-<OS>` として残す|
|**Release**（`release.yml`）|`v<major>.<minor>.0` のタグ・手動|**組まない。** タグのコミットで走った CI を探し（走っていれば終わるまで待つ）、`dist-<OS>` を落として、照合値と説明文を添えて載せる|



CI（`ci.yml`）も公開側と本体側で違う。**公開側は 3 OS で常に回して包むところまで行い、本体側は
push と PR では検査だけを Linux で行う**。本体側を手で起動したときは OS を選べ、Linux 以外を選ぶと
組んで包み、**本体の Release を作る**（§1「本体の Release」。2026-10-15）。公開側の `ci.yml` と `release.yml` は
手書き（`KEEP`）なので、**本体の `ci.yml` の検査の段を変えたら、公開側の `ci.yml` にも手で入れる**
（[公開用リポジトリへの移行手順](公開用リポジトリへの移行手順.md) §7-2 で差分を見る）。

### なぜ移したか

実行分の**倍率が OS で違う**（Linux ×1 / Windows ×2 / **macOS ×10**）。
3 OS を 1 回組むと**160 分を超える**。実測では、25 日ぶんの CI 全体
（130 分）よりも**1 回のリリースのほうが重かった**。

公開側は public なので無料である。**同じものを無料で組めるなら、
そちらで組む。**

### 本体の Release（手で起動したときだけ。2026-10-15）

2026-10-13 に本体の Release（退避路）をやめたが、**利用者が明示的に起動したときに限って**戻した。
本体の Actions → CI → Run workflow で OS を選ぶ。

|選ぶもの|検査|組んで包む・Release|課金の目安|
|---|---|---|---|
|`linux`（既定）|Linux|しない|約 8 分|
|`windows`|Windows|する|約 40 分|
|`linux-windows`|Linux・Windows|する|約 50 分|
|`all`|3 OS|する|約 120 分|

- **push と PR では作らない**（費用を抑える）。これまでどおり Linux の検査だけ
- **名前は版数に英字を付ける**: `v2.2.1a`。同じ版数で作り直すと `v2.2.1b`、`c` …（使った中で
  いちばん後ろの英字の次。消したものの穴は埋めない）。**公開側の `v2.2.1` と区別するため**
- **配る物は `dist`（fat LTO）で組む**（`cargo build --profile dist`。2026-10-16）。普段の push と PR は
  `release`（thin）で組んで試験する。fat は実行ファイルが小さくなるが、組み立てが約 2.6 倍かかる
- Windows がそろえば作る（Linux / macOS が欠けたら説明文の先頭に書く。選ばなかった OS も同じ）
- **あとから OS を足せる**: 起動するときに「足す先」へ `v2.2.1a` のように書くと、新しく作らずに
  その Release へ載せる（`linux` を選べば Linux 版だけを組む。課金は約 10 分）。照合値と説明文は
  全部の配布物で作り直す。**そのタグとアプリのソース（`src`・`Cargo.*`・`packaging` など）が同じ
  ときだけ**足せる（CI や文書だけを直したコミットからは足せる。中身が変わっていたら止まる）
- 本体の Release は**本体に入れる人にしか見えない**。外へ配るのは公開側の Release
- 包む段は公開側の `ci.yml` から写した。**包む段（`.deb`・インストーラなど）を直したら、本体と
  公開側の両方の `ci.yml` を直す**。公開側の `release.yml` は手書き（`KEEP`）で、本体には無い

### Windows がそろえば配る（2026-10-13）

|OS|落ちたときどうなるか|
|---|---|
|**Windows**|**Release を作らない**（実機で確かめている OS。不完全なものを配らない）|
|Linux|**作る。** Linux の分だけが入らず、説明文の先頭に書かれる|
|macOS|同じく作る|

判断は `tools/release/make-release.sh`（CI の `release` ジョブと、作り直し用の `release.yml` が呼ぶ）。

> **v2.0.0 のときは、macOS が落ちると Release が 1 つも作られなかった**（`needs: build` の
> ため）。実機が無く確認もできない OS が、確認できる OS の配布を止めるのはおかしい。
> 2026-10-13 に Linux も同じ扱いにした。

### 公開側にも手順書を置いてある

**公開側で実行する手順は、公開側の文書に書く**（`docs/release.md`）。
本体の文書を見ないと配れない状態にしておくと、**公開側だけを触る人が
手順を知れない。**

|どちらに書くか|内容|
|---|---|
|公開側 `docs/release.md`|版数の上げ方・タグ・出来るもの・目で見る確認・署名の扱い|
|本体側（この文書）|**組み立てる場所の切り分け**と、公開側へ反映する段取り|

重なる内容（版数の出どころ・走る条件・目視の必須）は、**公開側が正**である。
こちらを直したら、あちらも直す。

### 公開側の Release が使えないとき

本体を手で起動して `windows`（または `all`）を選べば、本体の Release に配布物が出来る。
**外へは配れない**（本体は非公開）。公開側の Actions が直るのを待つ。

## 2. 版数を上げる

### 2-1. `Cargo.toml`

```toml
version = "2.1.3"
```

**版数の出どころはここだけ。** インストーラも Release の名前も、
すべてここから取る。

### 2-2. `CHANGELOG.md`

`[Unreleased]` を版数の節へ繰り下げ、日付を入れる。

```markdown
## [2.1.3] - 2026-10-13
```

### 2-3. 確かめる

```powershell
cargo build --release
.\target\release\mdview.exe --version   # 上げた版数（例: mdview 2.1.3）と出ること
python tools/automation/smoke_test.py     # 試験の口が動くこと（約 30 秒）
python tools/automation/spec_test.py --perf   # 要件の試験（約 10 分。失敗・未網羅が 0 件であること）
```

GUI 試験の決まりは [GUI 自動テストの方針](GUI自動テストの方針.md)。CI も同じ試験を回すが、
**手元でも一度通してからタグを打つ**（CI の Windows は 1 回 20 分かかり、落ちてから直すと遅い）。

## 3. 配る（2026-10-13 から）

**公開用 PC には本体のリポジトリも、本体の ZIP も置かない。** 公開用 PC の git と `gh` は
公開用のアカウントで認証してあり、本体は clone できない。**本体の ZIP は落とさない**
（2026-10-13 に禁止。ZIP には `migration-v2/` の外の設計書や社内向けの文書も入る）。
公開用 PC には公開側の clone だけを置き、そこへ **`migration-v2/` の中身だけ**を置く。

|順|どこで|やること|
|---|---|---|
|1|この PC|版数と `CHANGELOG.md` を上げる（§2）。確かめる（§2-3）|
|2|この PC|**複製を作り直す**: `python tools/build-public-copy.py`（「禁止語は残っていない」で終わること）|
|3|この PC|コミットする|
|4|利用者|本体へ push する。**本体の CI が「公開用の複製が最新か」を見る**（作り直し忘れで落ちる）|
|5|公開用 PC|公開側の clone（`main`・最新）に、`migration-v2/` の中身だけを置く。**消したファイルは clone からも消す**|
|6|公開用 PC|変わったものを確かめて、コミットして `main` へ push する（§3-1）|
|7|公開側の CI|3 OS で検査 → 組む → 包む → 煙試験 → **版数が新しければタグを打って Release を作る**|
|8|手元|目で見る確認（§4）。問題があれば Release を下書きに戻す（§3-2）|

**本体のタグは、手で起動して Release を作ったときだけ出来る**（`v2.2.1a` の形。§1「本体の Release」）。
どの版をどのコミットで配ったかは、公開側のタグと CHANGELOG で分かる。

### 3-1. 公開用 PC でコミットして push する

**`publish.ps1` はやめた**（v2.2.0）。タグと Release は公開側の CI が作るので、公開用 PC では
ふつうにコミットして push するだけでよい。push の前に、次の 3 つを目で確かめる。

```powershell
cd <公開側の clone>
git pull                                  # origin/main に遅れていないこと
gh repo view --json isPrivate             # 公開リポジトリであること（false）
git status                                # 公開しないもの（migration-v2/・doc/・design/・poc/）が混じっていないこと
git add -A
git diff --cached --stat                  # 変わったものの一覧。消したファイルは D の行で出る
git commit -m "chore: v<版数>"
git push origin main
gh run watch "$(gh run list --workflow ci.yml --branch main --limit 1 --json databaseId --jq '.[0].databaseId')"
```

**ファイルは自動では消えない。** 本体で消したファイルは、置くときに clone からも消す。

**開発用 PC のユーザー名や本体のアカウント名は、公開用 PC では分からない。** それらは本体側で
止める（複製の作り直しの禁止語に、作り直した PC のユーザー名とユーザーのフォルダを実行時に足す）。

### 3-2. 問題があったら下書きに戻す

**承認は挟まない**（配る速さを優先する）。配ったあとで問題が分かったら、公開用 PC で:

```powershell
gh release edit v<版数> --draft=true     # 見えなくする（タグは残る）
```

直したものは**版数を上げて配り直す**（同じ版数は作り直さない。受け取った人の手元と中身が変わる）。
下書きのまま要らなくなったら `gh release delete v<版数> --cleanup-tag` で消す。

### 3-3. 作り直したいとき

Release を消して同じタグで作り直すときは、公開側の Actions から **Release（`release.yml`）を手で
起動する**（`gh workflow run release.yml --ref main -f tag=v<版数>`）。組まずに、タグのコミットの
CI の成果物を載せる。CI の成果物は 90 日で消えるので、古いタグは先に CI を起こし直す。

#### v2.2 で目で見るもの（§4 に足す）

[受入確認チェックリスト](受入確認チェックリスト.md) の L 節と同じもの。2026-10-14 の目視確認で見た。

|見るもの|やり方|
|---|---|
|右クリックの「mdview で開く」|インストーラで入れ、`.md` を右クリック →「その他のオプションを確認」。`.txt` には出ない|
|右端で折り返す|設定 → エディタで入れ、長い行のある文書で打つ・↑↓・クリック・ドラッグ・**日本語入力**。512 KB を超える文書では折り返さない|
|テキストのファイル|`.txt` を開き、`#` や `-` が見出し・リストにならない。名前を付けて保存で `.md` が付かない|
|プレビューで選んで写す|ドラッグで選び、`Ctrl + C` でメモ帳へ貼る|
|題名とステータスバーの書式|設定 → 外観で `{path}` や `{time:hh:mm:ss}` にする。「既定」で戻る|
|はみ出し・ミニマップ|プレビューを途中まで送る。ミニマップを最後まで送る|

#### v2.1.3 で目で見るもの（§4 に足す）

|見るもの|やり方|
|---|---|
|**Windows で起動してもコンソールの窓が出ない**|エクスプローラーから `.md` を開く・スタートメニューから起動する|
|**`mdview -v` が端末に版数を出し、プロンプトはその後ろ**|インストールしたものを cmd・PowerShell 5.1・7 で `mdview -v`（拡張子無し。`mdview.com` が起きる）|
|`mdview -h \| more` が化けない|PowerShell 7 と 5.1 で|
|窓とタスクバーのアイコン|2 つのファイルを渡して 2 つの窓を開き、題名の左端とタスクバーの両方が mdview のアイコン|
|最終行の先まで送れる|最終行が画面の 1 行目に来るまでホイールで送れる。最終行の下は空いている|
|`-g` / `-r` / `-t`|`mdview -r -t -g 120 <文書>` で、**120 行目が画面の先頭**・題名とステータスバーに「読み取り専用」・最前面|
|読み取り専用で打っても変わらない|打つ・貼る・`Ctrl + S`・画像を落とす。知らせが出て、ファイルは変わらない|
|ミニマップで最後まで行ける|1 万行ほどの文書で、枠を掴んで下端まで動かすと最終行が見える|

#### v2.1.1 で起きたこと（2026-10-09）

v2.1.1 は公開側で Release を作成済みである。**その `.deb` は依存が足りず、最小構成の Linux
（まっさらな Debian・WSL など）では `libXcursor.so.1` が無いと言って起動直後に落ちる。**
直した `.deb` は v2.1.2 で配った。**Release が出来たタグは打ち直さない**（受け取った人の手元と中身が変わる）。

v2.1.2 から、Linux の段は**まっさらな `debian:stable-slim` に `.deb` の依存だけを入れ、
窓を出して描けるか**を確かめる（`tools/automation/launch_check.py`）。依存が漏れていればここで落ちる。
2026-10-13 からは CI（`ci.yml`）がこれを行う。

### 出来るもの

```
mdview-<版数>-windows-x86_64-setup.exe   インストーラ
mdview-<版数>-windows-x86_64.exe         単一実行ファイル
mdview-<版数>-linux-x86_64.deb
mdview-<版数>-linux-x86_64.AppImage
mdview-<版数>-linux-x86_64               単一実行ファイル
mdview-<版数>-macos-aarch64.dmg
mdview-<版数>-macos-aarch64              単一実行ファイル
mdview-<版数>-android.apk                Android 版（v3.0.0 から。署名あり。§8）
SHA256SUMS.txt
```

**iOS 版は配らない**（v3.0.0。Apple の開発者登録が要る）。CI はシミュレーター向けの `.app` を組み、成果物 `mobile-ios-simulator` に残すだけ。

**インストーラには `mdview.exe` と端末用の入口 `mdview.com` が入る**（v2.1.3）。
端末で `mdview -v` と打つと `mdview.com` が起き、端末は答えが出るまで待つ。
単一実行ファイルには `mdview.com` が無い（拡張子まで打つと版数がプロンプトの後ろに出ることがある）。

CI（`ci.yml`）の中で確かめていること（失敗したら成果物が出来ず、Release は配れない）:

|OS|確かめていること|
|---|---|
|Windows|入れて・`mdview.exe --version`・**`mdview.com --version` が同じ版数を返す**・消すと両方消える|
|Linux|`.deb` を `apt-get install ./…` で入れて・`--version` が `Cargo.toml` の版・`.desktop` が妥当・消せる。**まっさらな `debian:stable-slim` に依存だけを入れて、実行時に読み込むライブラリがそろい、窓を出して描ける**（`check-runtime-libs.sh`・`launch_check.py`）。AppImage は展開して `--version`|
|macOS|`.dmg` を開いて、2 つのバンドル・アイコン・`Info.plist`・`--version`|
|Android（`mobile` ジョブ）|書式・Lint・試験・著作権表示の一覧が最新・APK が組める・**署名して `apksigner verify` が通る**（署名の鍵の秘密が無い実行では署名せず、Release に載せない）|
|iOS（`mobile` ジョブ）|シミュレーター向けの `.app` が組める（配らない）|
|Release（CI の `release` ジョブ）|**タグが無い版だけ**配る・**Windows の配布物がそろう**・版数の違うものが混ざっていない（`tools/release/make-release.sh`）|

## 4. 目で見る確認（**省けない**）

**CI が確かめるのは「組み立てられること」と「自動試験が通ること」だけである**
（§27.5）。v2.1.0 から GUI 試験（`spec_test.py`）も回すが、見た目の判定は画素の比べ方に頼っており、字形の崩れや操作の感触までは見ない。網羅の表で `手動` と出る項目は、ここで人が見る。画面のあるアプリで最も壊れやすいところは、そのどちらでもない。

落として [受入確認チェックリスト](受入確認チェックリスト.md) の
**「実機」印の項目**を実施する。

|OS|実機|やること|
|---|---|---|
|Windows|**ある**|チェックリストの実機項目をすべて|
|macOS|**無い**|実機が手に入るまで未確認。§5 の断り書きを入れる|
|Linux|**無い**|**WSLg で画面だけ見る**（[手順](Linux版をWSLgで確認する.md)）。性能・IME・デスクトップ統合は埋まらないので §5 の断り書きは残す|
|Android|**ある**|APK を入れて、開く・読む・直す（日本語の変換）・自動の保存と元に戻す・PDF と HTML の出力・共有を見る（v3.0.0）|
|iOS|**無い**|配らないので見ない（macOS 版と同じ扱い）|

## 5. 実機で見ていない OS があるとき

**配る前に、見た人がいない版であることを伝える。**
これは省いてよい手順ではない——字形の問題（受入条件 A2-03）は
技術選定書 §6.5.5 で実際に踏んだものである。

**この断り書きはワークフローが自動で載せる**（2026-10-05 から）。
手で足す決まりにしていたが、説明文を自動で作る以上、忘れるためである。
**消さないこと。**

いまワークフロー（`release.yml` の「説明文を作る」）が載せている文（2026-10-13）:

```markdown
> **macOS 版は画面を誰も見ていません。**
> 組み立てと自動試験は通っていますが、実機が無いため、
> 見た目（字形・描画）は未確認です。
>
> **Linux 版は WSLg で画面を確認しています。**
> 字形・レイアウト・図・数式・画像・導入と削除は見ていますが、
```

## 7. 失敗したとき

|状態|見るところ|
|---|---|
|push したのに Release が出来ない|版数を上げていない（そのタグが既にある）、または Windows の CI が落ちた。CI の `release` ジョブのログを見る|
|本体の CI の「公開用の複製が最新か」で落ちる|作り直し忘れ。`python tools/build-public-copy.py` を実行してコミットする|
|作り直し用の Release（`release.yml`）が「このコミットの CI が無い」「欠けている」で落ちる|**組むのは CI。** そのコミットの CI のログを見る（公開側 `docs/release.md` §9）。CI の成果物が 90 日で消えていないか|
|最後の「Release へ載せる」で落ちる|同じタグの Release が既に在る。**作り直さない**。欠けた OS は公開側 `docs/release.md` §3「あとから足したいとき」|
|Linux の GUI 試験が全項目「mdview が終わりました」|`libxkbcommon-x11-0` が無い（v2.1.1 で CI に足した）|
|Windows の GUI 試験が結果の表示で `UnicodeEncodeError`|試験の道具の出力が cp1252 になっている（v2.1.1 で UTF-8 に固定した）|
|CI のビルドだけ失敗|CI のログ。手元で `cargo build --release` が通るか|
|CI の煙試験で失敗|インストーラの中身が壊れている。`packaging/` を手元で試す|
|Windows の煙試験で「入ったはずの `mdview.com` が無い」・答えが違う|`mdview-console.exe` が組まれていない、またはインストーラへ渡っていない（`build-installer.ps1` の `-ConsoleExe`。既定は `mdview.exe` の隣）|
|「検査・照合値・説明文」で止まる|`Cargo.toml` の版とタグが違う・Windows の配布物が欠けている・版数の違うものが混ざっている|
|「まっさらな環境で deb を起動する」で `cannot open shared object file`|`.deb` の `Depends` から漏れている。`packaging/linux/build-deb.sh` に足す|
|Linux の段で `You are running out of disk space`・`dpkg returned an error code (2)`|ランナーの空きが足りない（1 つのジョブで 3 通りに組み、包み、docker で試すため）。検査のジョブの最初の「ランナーの空きを広げる（Linux）」で使わない道具を消している（2026-10-20）。前後の `df -h /` で空いた量を見る。まだ足りなければ、消すものを足す|
|Release を作る段で `HTTP 403: Resource not accessible by integration`・「main の先頭ではない」で止まる|走っている間に main へ push した。Actions のトークンは、ブランチの先頭でないコミットに Release（タグ）を作れない。**Release を作る手動起動の間は main へ push しない。** 踏んだら、main の先頭から起動し直すか、その実行の成果物（`gh run download <実行> --pattern 'dist-*'`）を `tools/release/make-release.sh` に通し、手元の `gh release create --target <コミット>` で作る（v2.3.0b はこれで作った）|
|フォントの取得で失敗|`tools/fetch-fonts.py` の取得元。キャッシュを消して再実行|

**タグは手で打たない・打ち直さない**（CI が打つ）。問題があれば Release を下書きに戻し（§3-2）、
直したものは版数を上げて配る。同じタグで載せ直すときは §3-3。

## 8. Android の署名の鍵（v3.0.0）

**鍵は 1 度作ったら作り直さない。** 署名の鍵が変わると、入っている mdview の上へ新しい版を入れられない
（端末は「別のアプリ」と見て拒む。消してから入れ直すことになる）。鍵と合言葉は失くさないよう、手元の安全な所に控える。

**鍵はリポジトリに置かない。** 公開側のリポジトリの Actions の秘密（Settings → Secrets and variables → Actions）に置く。

1. 手元で鍵を作る（JDK の `keytool`。Android Studio は要らない）。合言葉は聞かれたときに打つ

   ```powershell
   keytool -genkeypair -v -keystore mdview-release.jks -alias mdview -keyalg RSA -keysize 4096 -validity 36500 -dname "CN=mdview"
   ```

2. 鍵を 1 行の文字にする

   ```powershell
   [Convert]::ToBase64String([IO.File]::ReadAllBytes("mdview-release.jks")) | Set-Clipboard
   ```

3. 公開側のリポジトリに 4 つの秘密を作る

   |名前|中身|
   |---|---|
   |`ANDROID_KEYSTORE_BASE64`|2 で写した文字|
   |`ANDROID_KEYSTORE_PASSWORD`|1 で決めた鍵束の合言葉|
   |`ANDROID_KEY_ALIAS`|`mdview`|
   |`ANDROID_KEY_PASSWORD`|1 で決めた鍵の合言葉（聞かれなかったときは鍵束と同じ）|

4. `mdview-release.jks` はリポジトリの外の安全な所へ移す（作業のフォルダに残さない）

秘密が無い実行（PR など）では、CI は署名せず、Release にも Android 版を載せない（説明文の先頭に「入っていません」と出る）。
確かめ用に、署名していない APK を成果物 `mobile-android-unsigned` に 14 日残す。
