# v3 モバイル対応の実現可能性検証

作成日: 2026-10-27
対象: mdview v3（メジャーバージョンアップ）でのスマートフォン・タブレット対応
ブランチ: `research/mobile-feasibility`（調査用。版数を含めない）

---

## 0. この文書の位置づけ

v3 でスマートフォン・タブレット（Android・iOS）に対応できるかを、**作りの分析・文献・試作・CI での組み立て**で確かめた記録。
Dioxus などのフレームワークへの移行も候補に含める。**v3 の要件定義書ではない**（ここでの結論を受けて、v3 の要件を利用者と決める）。

### 0.1 決めたこと（2026-10-27。利用者の選択）

|論点|決めたこと|
|---|---|
|モバイルで目指す範囲|**閲覧中心＋軽い編集**（プレビュー・検索・目次・出力が主。編集は原文を直す程度。WYSIWYG と 10MB の編集は PC 版だけ）|
|手元の道具|**入れない**。Android・iOS 向けに組めるかは GitHub Actions で確かめる|
|iOS|**GitHub Actions で組めるかまで**（手元に Mac が無い。画面は見られない）|

### 0.2 結論（要約）

|問い|答え|
|---|---|
|いまのコードをモバイルへ持っていけるか|**UI に依存しない部分（約 3.8 万行）は持っていける。** iced の値の型（`iced_core`）だけで組め、本体の単体試験 686 件のうち 683 件が通る（§4.2）。UI 層（約 4.5 万行）は持っていけない|
|iced のままモバイルに出せるか|**勧めない。** iced はモバイルを公式には扱わず（0.14 が 2025-12 から最新）、Android で日本語の IME が働かない（winit が変換中の字を渡さない。§2.2）。**Android 向けにも iOS 向けにも `iced_winit` 0.14 がそのままでは組めない**（CI で確かめた。§5.3）|
|勧める作り|**案 B: 土台（core）を共有し、PC は iced のまま、モバイルは Dioxus（端末の WebView）で別の殻を作る**（§3）|
|Dioxus へ全面移行するか|**しない。** PC 版まで WebView にすると、v1 で抜け出したメモリと 10MB の問題（§3）に戻る|

**CI での組み立ての結果は §5.3 に書く**（利用者が push して流す）。

## 1. いまの作りの分析

### 1.1 UI への依存の大きさ（2026-10-27。`src/` の行数。試験を含む）

|層|モジュール|行数|iced への依存|
|---|---|---|---|
|UI|`app`|33,514|強い（Elm 型の状態と更新・ウィジェット）|
|UI|`render`|10,997|強い（エディタとプレビューを自前のウィジェットで描く）|
|UI 以外|`edit`・`io`・`export`・`parse`・`layout`・`embed`・`diff`・`document`・`marp`・`search`・`paginate`|37,575|**値の型だけ**（`iced::Color`・`Rectangle`・`Font` など）|
|窓の外の入口|`mcp`・`ipc`・`main`・`worker`|2,815|MCP・名前付きパイプ・起動（PC だけのもの）|

**レイアウト層は測る口（`Measurer`）を抽象化してある**（§3.1）。字の幅を測るのは描画層なので、レイアウトは窓が無くても動く。
この作りが、土台を切り出せる理由になる。

### 1.2 UI 以外から UI 層へ伸びている継ぎ目

試作（§4）で、UI 以外の部分が UI 層を呼んでいる所は次の 3 か所だけだった。v3 で土台をクレートに切り出すとき、ここを動かす。

|継ぎ目|使う側|移し方の案|
|---|---|---|
|`render::fonts`・`render::slides`・`render::backdrop`|図・数式・PDF・PPTX の書き出し|字体の一覧と見開きの組み方を土台へ移す（`iced_core` の型だけで書かれている）|
|`render::token_color`（`render/preview.rs`）|PPTX の書き出しの色|配色の表を土台へ移す|
|`app::COMMAND_RECENT_MAX`|設定（コマンドの履歴）|定数を設定の側へ移す|

### 1.3 PC だけのもの（モバイルでは置き換えるか、外す）

|もの|クレート・場所|モバイルでの扱い|
|---|---|---|
|ファイルの選択・確認のダイアログ|`rfd`|端末の書類の選択（Android の SAF・iOS の Files）。WebView の `<input type="file">` でも足りる|
|クリップボードの画像|`arboard`|外す（閲覧中心）|
|OS の外観|`dark-light`|WebView の `prefers-color-scheme`|
|MCP サーバー・窓の間の通り道|`rmcp`・`hyper`・`ipc`|**外す**（端末の中で他のアプリから呼ぶ使い方は無い）|
|中継の設定・ごみ箱・起動の制御|`io::system_proxy`・`io::trash`・`io::launch`|中継は端末に任せる。ほかは外す|
|同梱の字体（22.4 MB）|`render::fonts`|PDF の出力に要る。**アプリが大きくなる**（§5.3）。画面は端末の字体で足りる|

## 2. 候補のフレームワーク（2026-10-27 時点）

### 2.1 比べた結果

|候補|版（crates.io）|Android|iOS|日本語の入力|いまのコードの使い回し|主な懸念|
|---|---|---|---|---|---|---|
|**A. iced を続ける**|0.14.0（2025-12-07 から更新なし）|非公式。`iced_winit` が Android で組めず、自前の殻が要る（例: Antiphon の PR）|非公式。例はわずか|**Android で変換中の字が来ない**（§3.2）|UI 層まで使える見込み（殻は自作）|公式の対応が無い。IME が致命的|
|**B. Dioxus（WebView）**|0.7.10（0.8 は alpha.3）|**公式**（`dx` で APK）|**公式**（Mac・Xcode が要る）|**端末の WebView と IME がそのまま働く**|土台（§1.1）。UI は作り直し|WebView の重さ（PC で v1 が踏んだもの）。描き方が PC 版と別になる|
|C. Dioxus Native（Blitz）|blitz-dom 0.3.0-beta|実験的。モバイルの記述が見当たらない|同左|未確認|土台|まだ作りかけ（公式も "work in progress"）|
|D. Slint|1.18.1|**公式**（1.5 から。Rust だけ）|初期の対応（1.12 から）|モバイルの IME は 2026-01 に土台の PR|土台。UI は `.slint` で作り直し|日本語の変換の成熟度が未確認|
|E. egui（eframe）|0.37.0|eframe で可（非公式寄り）|非公式|モバイルの IME が直ったのは Web 版だけ（0.36）|土台。UI は作り直し|PoC で iced に負けた（§6）|
|F. Tauri 2|2.12.5（3.0 は alpha）|**公式**|**公式**|WebView のまま働く|土台（Rust の命令として呼ぶ）。UI は JS で作り直し|v1 の作り（Tauri）に戻る。UI の言語が増える|

### 2.2 日本語の入力がいちばんの分かれ目

軽い編集でも、日本語の変換（変換中の字の表示と確定）が働かないと使えない。

- **winit（iced・egui・Slint の窓の部品）は、Android で IME の字を渡さない**。`set_ime_allowed` は空の実装で、ソフトウェアキーボードも上がらない。
  GameActivity の部品を使って自前でつなぐ例はあるが、上流には入っていない（android-activity の PR は 2026-01 時点で未確認）
- **WebView 系（Dioxus・Tauri）は、端末のブラウザーの入力欄をそのまま使う**ので、日本語の変換・自動補正・貼り付けが最初から働く

PC 版が iced を選んだ決め手の 1 つが IME の合格（§6.5）だったのと同じ理由で、モバイルでは WebView 系が有利になる。

## 3. 案と勧める作り

### 3.1 3 つの案

|案|作り|作る量|PC 版への影響|
|---|---|---|---|
|案 A|iced のまま、モバイル用の殻（winit・wgpu を直に回す）を作る|殻と IME の橋渡し（Java/Kotlin か JNI）|無し|
|**案 B（勧める）**|**土台を共有し、モバイルは Dioxus（WebView）で別の殻**|モバイルの UI（閲覧・原文の編集・目次・検索・設定）。描くのは HTML の書き出し|土台の切り出し（§1.2 の継ぎ目）だけ|
|案 C|PC もモバイルも Dioxus へ全面移行|UI 4.5 万行の作り直し|**大きい**。10MB の編集とメモリの目標（§4.2）を守れる見込みが無い|

### 3.2 案 B を勧める理由

1. **日本語の入力が最初から働く**（§2.2）。閲覧中心でも、検索欄と原文の編集で要る
2. **描く中身を新しく作らない**。本体の HTML の書き出し（`export::html`）が、Mermaid を SVG に、数式を描いた形で 1 つの HTML にするので、それを WebView に渡せば表・図・数式まで出る（試作で確かめた）
3. **PC 版はいまのまま**。10MB・WYSIWYG・MCP は PC 版の強みとして残す
4. Android・iOS とも公式に対応し、`dx` 1 つで APK と .app を組める

### 3.3 案 B の懸念と対処

|懸念|対処の案|
|---|---|
|PC 版とモバイル版で見た目が違う（自前のレイアウトと HTML）|HTML の書き出しの CSS をモバイル用に整える。見た目をそろえるのは目次・配色・字体の大きさまでにとどめる|
|**全文を HTML にし直す描き方は 300 KB で約 1 秒**（§5.1）|**ブロックごとに HTML を作り、直したブロックだけ差し替える**（§5.2）。入力が止まってから描き直す。大きい文書は閲覧だけにする上限を設ける|
|アプリが大きい（同梱の字体 22.4 MB）|PDF の出力を使うときだけ字体を読み込む作りにする。画面は端末の字体を使う|
|UI が 2 つになる（保守の手間）|モバイルの機能を絞る（閲覧中心）。試験は土台の単体試験を共有する|
|iOS の画面を誰も見られない|配布の前に、iOS の端末を持つ人の目視を要件にする（いまの macOS 版と同じ扱いは、モバイルでは避けたい）|
|配布（ストア・署名）|Google Play と App Store の開発者登録・署名の鍵の扱いが要る。v3 の要件で決める|

## 5. 計測と CI の結果

### 5.1 HTML の書き出しの重さ（手元の PC・release）

`core/examples/render_cost.rs`。見本（`samples/sample.md`。Mermaid・数式などを 3 つ含む）を繰り返して大きさをそろえ、
`Document::from_text` と `export::html::export` を 5 回ずつ流した。

|原文|HTML|中央|最悪|
|---|---|---|---|
|5.4 KB|85 KB|4.5 ms|13.7 ms|
|301 KB|4.7 MB|927 ms|1,078 ms|
|1.0 MB|15.7 MB|9,344 ms|9,762 ms|
|10 MB|—|—|—|

10 MB は計測の途中で止まった（端末全体のメモリが足りなくなり、作業の道具が背景の処理を止めた。計測そのものの不具合かは未確認）。

### 5.2 分かったことと、モバイルでの見込み

- **全文を毎回 HTML にする描き方は、300 KB で 1 秒かかり、大きさに比例するより速く重くなる**（3.3 倍の大きさで 10 倍）。
  見本は図と数式が多く、その描画（SVG）を毎回やり直していることと、HTML が原文の 15 倍に膨らむことが効いている見込み（内訳は未計測）
- 端末の CPU は手元の PC より遅い（数倍とみる）ので、**この描き方のままでは 100 KB 程度が上限**になる
- **対処の案**: 土台にはすでにブロック単位の解析と、図・数式のブロック単位の作り置き（`embed`）がある。モバイルでは
  **ブロックごとに HTML を作り、直したブロックだけを差し替える**（WebView 側も見えている所だけを置く）。PC 版が 10MB を扱うために
  入れた「全文を触らない」考え方（§3.3）を、モバイルの描き方にも持ち込む。v3 の最初の試作で確かめる

### 5.3 CI（GitHub Actions）の結果

公開用のリポジトリ（`research-v3/` の中身）で流した。

#### 1 回目（2026-10-28）

|段|Android|iOS|落ちた理由|
|---|---|---|---|
|1. `core` を組む|失敗|失敗|**試作の誤り**。`lib.rs` の中に `mod render { #[path] … }` と書いたため、実在しない `core/src/render/` から `..` を辿った。Windows は文字の上で縮めて通るが、Linux・macOS は読めない|
|2. iced 0.14 を型検査|失敗|失敗|Android: **試作の誤り**（`android-activity` の起動の方式をアプリが選んでいない）。**iOS: `iced_winit` 0.14.1 が iOS の winit に無い機能（`modifier_supplement`）を使っていて組めない**（本当の結果）|
|3. `dx` を入れる|成功|成功||
|4. Dioxus の APK・.app|失敗|失敗|段 1 と同じ（`core` が読めない）。`core` 以外の依存（ring・boa_engine・merman など 700 余り）は Android（x86_64）・iOS シミュレーターとも組めていた|
|要約の段|失敗|失敗|**作業の流れの誤り**。組めた物が無いと `du` が落ち、表を書く前に終わった|

直したもの: `core/src/render/mod.rs` を本物のファイルにした・`iced-android` に `android-activity`（`native-activity`）を足した・要約の段が組めた物の無いときも表を書くようにした。

#### 2 回目（2026-10-28）

|段|Android|iOS|
|---|---|---|
|1. `core` を組む|**成功**|**成功**|
|2. iced 0.14 を型検査|**失敗（本当の結果）**|**失敗（本当の結果）**|
|3. `dx` を入れる|成功|成功|
|4. Dioxus の APK・.app|**成功**（成果物に APK）|**成功**（成果物にシミュレーター向けの .app）|

- **土台（UI 以外の約 3.8 万行）は Android・iOS 向けに組める。Dioxus の試作は APK と .app に組める**（案 B が組み立ての上で成り立つ）
- **iced 0.14 は Android 向けにも iOS 向けにも組めない**。1 回目の Android は起動の方式（`android-activity`）の選び忘れで手前で止まっていたが、
  直して先へ進むと iOS と同じ所で落ちた: `iced_winit` 0.14.1 が winit の `modifier_supplement`（`key_without_modifiers`・`text_with_all_modifiers`）を使い、
  これは winit 0.30 では Windows・macOS・X11・Wayland・Web にしか無い。iced をモバイルに持ち込むには、`iced_winit` を使わない自前の殻が要る（Antiphon の例と同じ）
- APK・.app の大きさと、端末での動きはまだ見ていない（成果物を端末へ入れて確かめる）

## 6. まだ確かめていないこと・次の段取り

1. **CI を流す**（§5.3）。落ちた段があれば、原因を調べて直す
2. **PC で `dioxus-app` を目視**する（`target\v3core\debug\mdview-mobile-poc.exe`。窓の幅を 900 px の前後で変える）
3. **Android の端末かエミュレーターで APK を目視**する（CI の成果物。日本語の入力・タッチのスクロール・図と数式）
4. iOS は CI で組めるかまで（§0.1）。画面を見る手段は v3 の要件で決める
5. 画面と操作の案は [v3 モバイルの UI 検討](v3モバイルのUI検討.md)（ブロック単位で直す・キーボードの上の道具の帯）
6. 結論（案 B）を利用者と決めたら、**v3 の要件定義書**を作る。最初の段は「土台をクレートに切り出す（PC 版の動きは変えない）」
