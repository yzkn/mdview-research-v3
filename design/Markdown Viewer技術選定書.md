## 1. はじめに

### 1.1 本書の目的

本書は、v1 系（Tauri + React + WebView2）の実装を破棄し、v2.0.0 として全面再実装するにあたり、
採用する言語・フレームワーク・主要ライブラリを選定するものである。

v1 系の設計書が「何を作るか」「どう作るか」を定義するのに対し、本書は
**「なぜ作り直すのか」「何を土台にするのか」**を定義する。

### 1.2 v2.0.0 の位置づけ

v1.0.1 をもって v1 系の機能開発を終了し、v2.0.0 は既存実装を引き継がない
**フルスクラッチ**とする。ただし次のものは資産として引き継ぐ。

- 基本設計書の機能要件・画面仕様・キーバインド（§8 の出力品質を含む）
- 実装方針書 §8.4 の性能計測手順（比較の基準として同じ文書生成ロジックを使う）。
  **実装方針書は v1 系専用のため v2.0.0 の起票時に削除した。git 履歴を参照する**
- `src-tauri/` のファイル入出力・エラー型・起動時ファイル受け渡しの設計

### 1.3 前提条件

次はユーザー決定事項であり、本書ではこれを所与として扱う。

|ID|前提|決定日|
|---|---|---|
|PRE-001|ネイティブアプリケーションであること。**単一ファイルの実行形式**をビルドできること|2026-09-14|
|PRE-002|中間コードを介する言語（.NET / C# ・ Java 等）は採用しない|2026-09-14|
|PRE-003|**Mermaid の見た目が v1 から変わることを許容する**|2026-09-14|
|PRE-004|**対象 Markdown サイズの上限 300KB を撤廃する。将来的に 10MB オーダーに対応する**|2026-09-14|
|PRE-005|UI フレームワークの 2 択は PoC の実測で決める|2026-09-14|

## 3. v1 の何が問題だったか

### 3.1 実測値（v1 基本設計書 §20.1 ／ 実装方針書 §8.4）

v1 の値である。基本設計書は v2.0 で全面改訂したため、**この表の出典は git 履歴の
v1.7 までを参照する**。

|項目|目標|v1 実測|判定|
|---|---|---|---|
|起動時間|3 秒以内|283ms|達成|
|ライブプレビュー（300KB）|150ms 以内|変換 139.7ms|達成（上限ぎりぎり）|
|ライブプレビュー（1MB）|—|**変換のみで 417ms**|未達|
|メモリ（アイドル）|200MB 以下|**WorkingSet 580MB / Private 294MB**|**未達**|
|PDF 出力（300KB・283 ページ）|15 秒以内|10.70 秒|達成（当初目標の一律 10 秒には未達）|
|PDF ブックマーク|—|Windows のみ|制約|

### 3.2 原因の切り分け

課題は原因別に 3 つに分かれ、**対処の可否が異なる**。

|課題|原因|v2 で解決するか|
|---|---|---|
|メモリ 580MB|WebView2 のプロセス群そのもの|**する**。§6.2 の PoC では 10MB 文書を開いて 157〜185MB|
|PDF 10.70 秒|WebView2 の `PrintToPdf`。自前処理は 26.2ms＝全体の 0.3% 未満|**する**。印刷エンジンを自前に置き換える|
|変換 139.7ms|markdown-it が遅い **＋ 変更のたびに全文を作り直す設計**|**半分だけ**（§3.3）|

### 3.3 言語変更だけでは解決しないもの

**パーサを速くしても、全文再解析という構造が残れば 10MB では成立しない。**
これは §6.3 の実測で裏づけられた。

|入力|v1 markdown-it|v2 comrak|v2 pulldown-cmark|
|---|---|---|---|
|0.3MB|139.7ms|**9.5ms**|2.2ms|
|1.0MB|417ms|36.4ms|6.3ms|
|10.0MB|（未計測・上限外）|**431.5ms**|73.9ms|

パーサ単体では 11〜15 倍速くなるが、**10MB の全文解析は comrak でも 431ms** であり、
1 キー入力ごとに走らせられる値ではない。60fps を保つには 1 フレーム 16.6ms しかない。

したがって v2 では、言語の置き換えと**同時に「全文を触らない」構造を設計に入れる**
（§8）。これを省くと、書き直しの効果はメモリと PDF だけに留まる。

なお当初はこれを tree-sitter-md の増分解析で実現する想定だったが、**PoC で否定された**。
採用する方式は §8.3 を参照。

## 4. v2.0.0 の要求

### 4.1 機能要求

v1 の機能を引き継ぐ。基本設計書の機能要件を正とし、本書では差分のみ記す。

|分類|v1 からの変更|
|---|---|
|Markdown|変更なし（GFM・Mermaid・KaTeX・ローカル画像）|
|図|**見た目が変わる**（PRE-003）。HTML ラベル・ブラウザのフォント代替に由来する差が出る|
|対象サイズ|**300KB → 10MB**（PRE-004）|
|出力|PDF のブックマークを**全 OS で**提供する（v1 は Windows のみ）|
|安全性|DOMPurify・CSP・asset プロトコルの設計が**不要になる**（HTML を描画しないため）|

### 4.2 非機能要求（暫定目標値）

**v1 の目標をそのまま流用しない。** 10MB を扱う以上、区分を引き直す必要がある。

|項目|v2 暫定目標|v1 実測|備考|
|---|---|---|---|
|起動時間|**2 秒以内**|283ms|**v1 より悪化する見込み**。§9.5|
|ライブプレビュー（1MB まで）|100ms 以内|—|増分更新が前提|
|ライブプレビュー（10MB）|150ms 以内|—|**達成**。中央値 22.58ms・最悪 50.45ms（詳細設計書 §10.7）|
|メモリ（300KB 文書）|200MB 以下|580MB|v1 の未達項目|
|メモリ（10MB 文書）|**600MB 以下**|—|**暫定達成**。ピーク 193〜198MB（図・数式のキャッシュは未実装。詳細設計書 §10.7）|
|ファイル読込（10MB）|1 秒以内|—|PoC のロープ構築は 12〜17ms|
|PDF 出力|ページ数に比例。**100 ページあたり 1 秒以内**|283 ページで 10.70 秒|**達成**。283 ページ 0.73 秒＝100 ページ 0.26 秒（§8.5）|
|配布物|単一実行ファイル。**約 47〜57MB**|NSIS 4.5MB（+ WebView2 ランタイム必須）|§7.6。うち**フォント 22.4MB は実測**、実行コード 25〜35MB は推定。v1 は別途 WebView2 ランタイムを必要とした点に注意|

### 4.3 制約

- 完全オフラインで動作すること（v1 から継続）
- Windows / macOS / Linux の 3 系統を配布すること（v1 から継続）
- PRE-001 / PRE-002 のとおり、単一ファイル・非中間コード

## 5. 言語・実行形態の選定

### 5.1 候補と評価

|候補|単一ファイル|中間コード|評価|
|---|---|---|---|
|**Rust**|可（`+crt-static` で VC++ ランタイムも不要）|該当せず|**採用**|
|C++ / Qt|**実質不可**|該当せず|静的リンクでの単一ファイル配布が LGPL の再リンク条項と衝突し、商用ライセンスが必要になる。不採用|
|Go / Gio・Fyne|可|該当せず|数式・Mermaid・PDF 組版のライブラリが Rust より明確に薄い。GC 停止も編集応答に不利。不採用|
|Dart / Flutter|**不可**|該当せず（AOT ネイティブ）|実行時にアセットディレクトリを伴い、単一ファイルにならない。不採用|
|C# / Java / Kotlin(JVM)|—|該当する|PRE-002 により対象外|

### 5.2 Rust を選ぶ理由

1. **PRE-001 / PRE-002 を素直に満たす。** 単一の実行ファイルを生成でき、実行時ランタイムを要求しない。
   PoC の実行ファイルは egui 6.3MB / iced 9.9MB（`lto = "thin"` ・ `strip = true`）。
2. **v1 の Rust 資産（`src-tauri/` 1,974 行）と設計判断が活きる。**
   ファイル入出力・エラー型・起動時のファイル受け渡し・PDF アウトライン付与は移植できる。
3. **2026 年時点で、必要なライブラリが出揃った。** とくに Mermaid と数式の純 Rust 実装
   （§7.1）は本選定の成立条件であり、これが無かった時期なら Tauri 継続を選んでいた。
4. **ツールチェーンが導入済み**（rustc 1.97.1 / cargo 1.97.1。実装方針書 DEC-005）。

なお **WebView を持たないこと自体が目的**である（DEC-203）。Rust を採用しても
WebView 上に描画する限り、§3.2 のメモリと PDF の課題は解消しない。

## 6. UI フレームワークの選定（PoC）

PRE-005 に基づき、`iced` と `egui` を実測で比較した。PoC 一式は
[`poc/v2-ui/`](../poc/v2-ui/) に置いてある。

### 6.1 PoC の設計

**同一条件で走らせることを最優先した。** 両者で異なるのはツールキットだけになるよう、
文書生成・テキストバッファ・スクロール軌道・可視行数を共有クレート
[`poc/v2-ui/core`](../poc/v2-ui/core/src/lib.rs) に置いた。

|項目|内容|
|---|---|
|文書|最悪ケース 10MB（見出し・日本語の散文・表・コードブロック・箇条書きを一巡）。380,812 行|
|バッファ|`ropey`（両者共通）|
|描画|**可視 44 行のみ**を毎フレーム描き直す（仮想化）|
|スクロール|1 フレームあたり 7 行。フレームレートに依存させない|
|測定時間|15 秒|
|CPU・メモリ|**プロセスの外から** PowerShell で測る（[`run-bench.ps1`](../poc/v2-ui/run-bench.ps1)）。アプリ内計測では計測範囲が揃わないため|
|ビルド|`opt-level = 3` / `lto = "thin"` / `codegen-units = 1` / `strip = true`|

**計測上の注意点（1 回目の失敗）**: 当初 iced 側は `update()` の呼び出し回数を
フレーム数として数えており、vsync 上限（60fps）を超える「75.1fps」という値が出た。
タイマー刻みを数えていたためである。`view()` の呼び出し回数＝実描画回数を
別に数えるよう修正した。以下は修正後の値である。

### 6.2 計測結果（2026-09-14 / Windows 11・リリースビルド・10MB）

2 回の実測値を併記する。

|項目|egui (eframe 0.36)|iced 0.14|
|---|---|---|
|実描画回数 / 15 秒|894 / 896|903 / 902|
|実効フレームレート|59.6 / 59.7 fps|60.2 / 60.1 fps|
|**CPU 時間（1 フレームあたり）**|**17.93 / 18.89 ms**|**11.59 / 10.97 ms**|
|**ピークメモリ（WorkingSet）**|**156 / 158 MB**|**184 / 185 MB**|
|実行ファイルサイズ|**6.3 MB**|9.9 MB|
|ロープ構築（10MB）|16.5 / 14.2 ms|12.4 / 17.0 ms|
|1 文字挿入|0.076 / 0.022 ms|0.061 / 0.019 ms|
|起動〜初回描画|1,434 / 1,088 ms|1,390 / 1,275 ms|
|日本語フォント|**手動で組み込みが必要**|コードは書いていないが、**拾われる字形が誤る**（§6.5.5）|

読み取れること:

- **どちらも 10MB で 60fps を維持した。** 仮想化さえすれば、文書サイズは
  描画性能の制約要因にならない。PRE-004 の 10MB は UI ツールキットの選択とは独立している。
- **iced の CPU 消費は egui の約 6 割**（11.3ms 対 18.4ms、中央）。
- **egui のメモリは iced より約 28MB 少なく、実行ファイルは 3.6MB 小さい。**
- **1 文字挿入はどちらも 0.1ms 未満**で、ロープ側は 10MB でも問題にならない。
- **起動〜初回描画が 1.1〜1.4 秒**と、どちらも v1（283ms）より大幅に遅い（§9.5）。

### 6.3 パーサ計測結果（同日・同環境）

[`poc/v2-ui/parse-poc`](../poc/v2-ui/parse-poc/src/main.rs) による。§3.3 の表を再掲する。

|入力|comrak（AST + HTML 生成）|pulldown-cmark（AST のみ）|生成 HTML|
|---|---|---|---|
|0.3MB|9.5ms|2.2ms|0.3MB|
|1.0MB|36.4ms|6.3ms|1.1MB|
|10.0MB|431.5ms|73.9ms|11.5MB|

v1 の markdown-it は 0.3MB で 139.7ms、1MB で 417ms（実装方針書 §8.4）。
**同じ文書構成での比較ではないため厳密な倍率ではない**が、桁が 1 つ違うことは明らかである。

### 6.4 評価と結論

**iced を採用する（DEC-202。§6.5 の確認を経て確定）。**
当初の根拠は次の 2 点だったが、**2 点目は実機確認で否定された**（下記）。

1. **CPU の余力。** PoC が描いているのは装飾なしの等幅テキスト 44 行だけであり、
   これは実アプリの負荷の**下限**である。実際にはシンタックスハイライト・
   プレビュー面・画像・数式・図が上に載る。1 フレーム 16.6ms の予算に対し、
   下限の時点で 18.4ms（egui）と 11.3ms（iced）の差は、後から効いてくる。
2. ~~**日本語の扱い。** egui は既定フォントに CJK を含まず、アプリ側でフォントを
   読み込む必要があったが、iced は `cosmic-text` のフォールバックによりフォント
   関連のコードを書かずに動作した。~~
   **→ この根拠は §6.5 の実機確認で否定された（§6.5.5）。** iced のフォールバックは
   働くが、**拾うフォントが中国語のものになる**。結局どちらも日本語フォントの
   同梱が必要であり（DEC-208）、両者に差は無い。

**したがって DEC-202 の根拠は上記 1 点（CPU の余力）のみである。** 根拠が 1 本に
減ったことは明記しておく。ただし 11.3ms 対 18.4ms という差は 1 フレームの予算
16.6ms に対して十分大きく、結論は変わらないと判断した。

egui を採らない判断の代償は、**メモリ +28MB と実行ファイル +3.6MB**、および
カスタムウィジェット API の複雑さである。いずれも許容範囲と判断した。

### 6.5 IME の手動確認（DEC-202 の通過条件。2026-09-14 実施・合格）

**日本語入力（IME）の品質は PoC の自動計測では判定できない。** かな漢字変換は
OS の IME・ウィンドウ・アプリの三者がやりとりするため、実際に人が入力して
目で見るしかない。**この確認が通らない場合、DEC-202 は取り消し、
§11 OPEN-203 の代替案に移る。**

所要時間は両ツールキット合わせて 15 分程度である。

#### 6.5.1 起動

```powershell
cd poc/v2-ui
cargo build --release

# どちらか一方ずつ確認する（同時に起動しない。どちらの候補窓か分からなくなる）
.\target\release\iced-poc.exe --ime
.\target\release\egui-poc.exe --ime
```

**必ず `--ime` を使う。** 環境変数 `POC_MODE=ime` も受け付けるが、cmd.exe で
`set POC_MODE=ime && ...` と書くと**値に末尾の空白が入り**（`"ime "`）、
一致判定から外れて計測モードで起動する。計測モードでは文字が流れ続け、
15 秒で勝手に終了するため確認できない。

起動できたかの見分け方:

|状態|意味|
|---|---|
|見出し「IME 確認」と入力欄が出て、**文字が流れない**|IME モード。正しい|
|等幅の文字がスクロールし続け、15 秒で閉じる|計測モード。`--ime` が渡っていない|

#### 6.5.2 確認手順

IME は Microsoft IME（既定）で行う。入力する語は**変換候補が複数出るもの**が
よいので、以下では「にほんご」（日本語／二本後／…）を使う。

**項目 1: 日本語の字形が出るか**

|||
|---|---|
|操作|起動直後の画面を見る。何も入力しない|
|**合格**|見出しと説明文の日本語が**字として読める**|
|**不合格**|□（豆腐）や空白の連なりになる|
|不合格の意味|iced がシステムフォントへフォールバックしていない。**フォント同梱が必須**になり、単一ファイルのサイズが数 MB 増える（OPEN-205 に直結）。ただし選定を覆すほどではない|

> egui 側はアプリから `meiryo.ttc` を明示的に読み込んでいるため、この項目は
> 合格して当然である。**見るべきは iced 側**である。

#### 6.5.5 所見: フォールバックは働くが、字形が中国語になる

**§6.4 で iced を推した根拠の 1 つが、この確認で否定された。**

iced（`cosmic-text` + `fontdb`）は日本語のフォールバックそのものは行う。
豆腐（□）にはならない。しかし**拾われるのが中国語用のフォントであり、
`入` のような字が日本語の字形で表示されない**。

原因は Unicode の**漢字統合（Han Unification）**である。日中韓で字形が異なる漢字にも
同じコードポイントが割り当てられているため、フォント選択だけでは字形が決まらない。
言語の指定が無ければ、フォント探索は日本語用と中国語用を区別できない。

影響は UI ツールキットに留まらない。**同じ問題が出力側にも出る。**

|経路|対処|
|---|---|
|画面|日本語フォントを同梱し、フォールバック任せにしない（DEC-208）|
|PDF|生成する PDF に**同じフォントを埋め込む**。埋め込まなければ閲覧環境側で同じことが起きる|
|HTML エクスポート|`font-family` に日本語フォントを明示する。v1 の `fontEmbedding.ts` と同じ考え方が要る|

**3 経路すべてで同一のフォントを使う**ことが、§9.2 の「見た目が 3 通りになる」
リスクへの対処にもなる。使用する書体は **§7.6（DEC-209）で確定した**。

### 7.3 Mermaid（DEC-207）の実測

[`poc/v2-ui/mermaid-poc`](../poc/v2-ui/mermaid-poc/src/main.rs) による
（2026-09-14 / merman 0.8.0-alpha.6 + resvg 0.45）。

**8 種すべてが描画に成功し、所要は 0.2〜2.5ms** だった。プレビューの更新に
載せても問題にならない速さである。SVG は 4〜21KB。

しかし **SVG が出ることと、描けることは別だった。**

#### 判明した問題: HTML ラベルが silently 欠落する

merman は既定で mermaid と同じく**ラベルを `<foreignObject>`（HTML）で出力する**。
**resvg は foreignObject を描けない**ため、ラスタライズは「成功」するのに
**ノードのラベル文字だけが消える**。サイズは返るので、size を見ただけでは気づけない。

実際に描かれた暗い画素を数えて確認した（日本語ラベルの flowchart・166x422px）。

|設定|foreignObject|`<text>`|暗い画素|
|---|---|---|---|
|既定|12 箇所|**0 箇所**|278（枠線と矢印だけ）|
|`%%{init:...htmlLabels:false}%%`|6 箇所|3 箇所|543|
|**サイト設定で一括無効化**|**0 箇所**|6 箇所|**1,649**|

#### 対処: サイト設定で HTML ラベルを一括無効化する

`%%{init: ...}%%` を文書ごとに書かせるのは現実的でないため、
**アプリ側で `Engine::with_site_config` を使って一括で切る**。

```rust
let config = MermaidConfig::from_value(json!({
    "htmlLabels": false,
    "flowchart": { "htmlLabels": false },
    "class":     { "htmlLabels": false },
    "state":     { "htmlLabels": false },
    "er":        { "htmlLabels": false },
}));
let renderer = Renderer::new().with_engine(Engine::new().with_site_config(config));
```

これで **8 種中 7 種の foreignObject が 0 になった**。

|図種|foreignObject|`<text>`|暗い画素|
|---|---|---|---|
|flowchart（v1 サンプル）|0|7|1,229|
|flowchart（日本語）|0|6|1,649|
|sequenceDiagram|0|6|2,475|
|classDiagram|0|5|1,742|
|stateDiagram-v2|0|4|1,316|
|**erDiagram**|**12**|1|**191**|
|gantt|0|15|4,239|
|pie|0|7|6,057|

#### 残る制約

- **erDiagram だけラベルが欠ける。** `er.htmlLabels: false` を渡しても
  foreignObject が 12 箇所残る。対処は OPEN-210 とする。
  暫定は「erDiagram はコードブロック表示に退避」（§7.2 の逃げ道）。
  **2026-09-20 に実装時へ再測定し、いまも再現することを確認した**
  （foreignObject 4 箇所・`<text>` 1 箇所）。暫定案を採用した（詳細設計書 §10.13）。
- **resvg には別途フォントを渡す必要がある。** `usvg::Options::default()` の
  フォントデータベースは空で、そのままでは `<text>` も一切描かれない。
  §6.5.5 と同じ話であり、同梱フォント（DEC-209）を指定する。

> **実装時に判明: フォントの指定は merman 側と usvg 側の両方が要る**
> （2026-09-20）。merman は既定で `"trebuchet ms", verdana, arial, sans-serif`
> を出し、同梱フォントには無い名前ばかりで総称名 `sans-serif` に落ちる。
> usvg の総称名の既定も "Arial" などで同梱フォントには無く、**片方だけ直しても
> 字形が 1 つも引けない**。merman に `fontFamily` を渡し、usvg の `fontdb` で
> `set_sans_serif_family` 等も向ける（詳細設計書 §10.13）。
>
> **本 PoC の `load_system_fonts()` をそのまま使ってはいけない。**
> それでは §6.5.5 の漢字統合の問題が図の中で戻る。

### 7.4 数式（DEC-210）

[`poc/v2-ui/math-poc`](../poc/v2-ui/math-poc/src/main.rs) による
（2026-09-14 / latex-rust 1.0.2 + resvg 0.45）。

当初候補は RaTeX だったが、crates.io の `ratex` は placeholder（0.0.1）であり、
実体は `ratex-layout` / `ratex-svg` 等に分割された 0.1.x である。
より単純に扱える **latex-rust 1.0.2**（MIT OR Apache-2.0）を検証し、採用する。

#### 結果

**16 ケース中 15 件が成功し、所要は 0.04〜1.44ms** だった。

|ケース|結果|
|---|---|
|v1 サンプル（`E = mc^2` / `\int_0^\infty e^{-x^2}dx = \frac{\sqrt{\pi}}{2}`）|成功|
|分数・総和・総乗・極限・根号|成功|
|ギリシャ文字・添字・演算子・関係子・上下線・帽子|成功|
|`aligned`（2 行・`&` あり）|成功（2 行ぶんの高さ 25px を確認）|
|`pmatrix`（2 行・1 列）|成功（30px）|
|**`\text{日本語}`**|**失敗**|

**重要な利点**: 出力はすべて `<path>` で、`<text>` は 0 件だった。
**数式はアウトライン化されて出るため、描画に外部フォントが要らない。**
§7.3 の Mermaid（`<text>` にフォント指定が必須）とは対照的で、
画面・PDF・HTML のどの経路でも同じ結果になる。

数式用フォント（STIX Two Math Regular・839KB）はクレートに同梱されており、
**§7.6 の同梱フォントとは別に 0.8MB 程度が加算される**。

#### 判明した制約

1. **`\text{}` に日本語を入れられない**（`missing glyph for '面'`）。
   STIX Two Math に CJK が無いため。社内文書では `\text{面積}` のような
   使い方が想定されるため、**同梱の日本語フォント（DEC-209）へ
   フォールバックさせる仕組みが要る**（OPEN-211）。
   **→ 2026-09-20 解消（案 A）。** 実装時に測ったところ、latex-rust には
   フォールバックの口が無く（`MathFont::from_bytes` は差し替え）、CJK フォントは
   MATH テーブルが無いため数式フォントにできない（`unsupported: OpenType MATH table`）。
   **枠内では解決できない。** 数式内の日本語は非対応とし、理由が読める形で
   失敗させる（詳細設計書 §10.14）。
2. ~~**複数列の `pmatrix` が 1 行に潰れる疑いがある。**~~
   ~~`\begin{pmatrix} a \\ b \end{pmatrix}`（2 行 1 列）は 30px と正しく積まれるが、~~
   ~~`\begin{pmatrix} a & b \\ c & d \end{pmatrix}`（2 行 2 列）は 15px しかない。~~
   **→ 2026-09-20 解消。再現しなかった。** 実装時の測定では 2 行 2 列が 39x32 で
   正しく積まれている（1 行は 36x11）。PoC の測定値の取り違えと考えられる
   （詳細設計書 §10.14）。

### 7.5 コードブロックの着色（DEC-211）

[`poc/v2-ui/hl-poc`](../poc/v2-ui/hl-poc/src/main.rs) による
（2026-09-15 / syntect 5 / 2 回実測）。

§8.3 で Markdown の文法解析に tree-sitter を使わないと決めたが、
**フェンス内のコードの着色は別の話**である。comrak は言語名を返すだけなので
着色は自前で行う必要がある（OPEN-206）。

|項目|1 回目|2 回目|
|---|---|---|
|構文定義の読み込み（75 種）|1.7ms|1.6ms|
|テーマの読み込み（7 種）|1.5ms|1.4ms|
|**起動時コスト 合計**|**3.2ms**|**3.0ms**|
|1 ブロック着色: Rust（52 行）|4.78ms|3.97ms|
|1 ブロック着色: Python（65 行）|6.74ms|5.30ms|
|1 ブロック着色: JavaScript（52 行）|2.83ms|3.13ms|

**syntect を採用する（DEC-211）。** 判断は次の 2 点による。

1. **起動時コストは無視できる。** 3ms であり、§9.5 で問題にしている起動時間
   （1.1〜1.4 秒）に影響しない。**遅延読み込みは不要**で、起動時にまとめて
   読み込んでよい。
2. tree-sitter を言語ごとに用意する案に対し、**構文定義 75 種が最初から入る**。
   多くの言語をまとめて賄える。

> **訂正（2026-09-20）**: 当初ここに「社内文書に現れる言語を個別に手当てする
> 必要がない」と書いたが、**成り立たなかった**。実装後の実測で
> **`powershell` `toml` `typescript` が既定の構文集合に無い**ことが分かった。
> 別名の読み替えで `sh` `py` `rs` などは救えるが、PowerShell と TOML は
> 追加の構文定義を同梱しない限り着色できない（詳細設計書 §10.9 / DD-OPEN-12）。
> **採用の判断自体は変わらない**——tree-sitter を言語ごとに用意するより
> 手当ての量は依然として小さい。

#### 設計上の含意: 着色結果はブロック単位でキャッシュする

**1 ブロックあたり 3〜7ms は、無条件に許容できる値ではない。**
1 フレームの予算は 16.6ms であり、**可視範囲にコードブロックが 3 つあれば
それだけで予算を使い切る**（Python 相当なら 3 × 5.3ms ≒ 16ms）。

したがって、§8.3 の「可視範囲のみ再解析」と同じ考え方を着色にも適用する。

- 着色結果は**ブロック単位でキャッシュ**し、**編集されたブロックだけ**破棄する
- スクロールだけで可視範囲が変わった場合は**再着色しない**（キャッシュを引く）
- キャッシュが無い状態（ファイルを開いた直後）は、可視ぶんだけ着色すればよい

この前提が崩れる（毎フレーム全可視ブロックを着色し直す）と、
コードブロックの多い文書でフレーム落ちする。

### 7.6 同梱フォント（DEC-209）

§6.5.5 のとおり、フォールバック任せにすると中国語の字形が出るため同梱する（DEC-208）。
構成は次のとおり。

|用途|フォント|ウェイト|
|---|---|---|
|エディタ・コードブロック|**PlemolJP**（通常版）|Regular / Bold|
|本文・見出し・PDF 本文・HTML 出力|**IBM Plex Sans JP**|Regular / Bold|

**2 書体を組み合わせる理由**: PlemolJP は等幅のプログラミングフォント
（半角:全角 = 1:2）であり、エディタとコードには最適だが、**等幅で組んだ日本語の
散文は読みにくく、PDF 成果物として不自然**になる。本文にはプロポーショナルの
和文が要る。

**この 2 つを選ぶ理由**: PlemolJP の和文部分は IBM Plex Sans JP そのものである
（ASCII に IBM Plex Mono を合成したもの）。したがって**エディタとプレビューで
漢字の字形が一致する**。§6.5.5 で問題にした字形のブレを、出力経路をまたいで
起こさないための組み合わせである。

#### 方針

|項目|決定|理由|
|---|---|---|
|グリフのサブセット化|**行わない**|PlemolJP v3.x は IBM Plex Sans JP 1.003 を用いており **Adobe-Japan1-7 を完全網羅**する（JIS X 0213:2004 / JIS X 0212-1990 対応）。削れば稀な漢字でシステムフォントに落ち、**中国語字形が出る事故が戻る**|
|ウェイト|**Regular / Bold のみ**|8 ウェイト全部入りは配布サイズが非現実的。文書表示に必要なのはこの 2 つ|
|イタリック|**同梱しない**|必要な箇所は合成斜体で表現する。和文にイタリックの需要は小さい|
|版|**通常版**（HS 版・NF 版は使わない）|HS 版は全角スペースが不可視。**Markdown エディタでは全角スペースが見えるほうが有用**。NF 版のアイコンは不要|

#### ライセンス上の義務

両フォントとも **SIL Open Font License 1.1**。アプリへの同梱・PDF への埋め込み・
ソフトウェアと一緒の再配布はいずれも明示的に許可されている。守るべきは次の 2 点。

1. **著作権表示とライセンス全文を配布物に含める**（アプリ内の「ライセンス表示」と
   配布アーカイブの双方）
2. フォント単体での販売はしない

PlemolJP は Reserved Font Name として `PlemolJP` を宣言しているため、**改変した
場合は同名を使えない**。本件は**サブセット化を行わない＝改変しない**ため、
この制約には抵触せず、名称をそのまま使える。**サブセット化を後から採用する場合は
改名が必須**になる点に注意する。

#### サイズ（2026-09-15 実測。OPEN-205 解消）

[`poc/v2-ui/font-size.py`](../poc/v2-ui/font-size.py) で実測した。配布 zip は
PlemolJP が 211.5MB、IBM Plex Sans JP が 302.5MB あるため、**zip の中央ディレクトリ
（末尾 1MB）だけを HTTP Range で取得**し、各エントリの非圧縮サイズを読んでいる。
ダウンロード量は合計 2MB で済む。

|ファイル|実サイズ|
|---|---|
|`PlemolJP-Regular.ttf`|**5.34MB**|
|`PlemolJP-Bold.ttf`|**5.33MB**|
|`IBMPlexSansJP-Regular.ttf`（hinted）|**5.44MB**|
|`IBMPlexSansJP-Bold.ttf`（hinted）|**5.45MB**|
|**同梱フォント計**|**21.56MB**|

**IBM Plex Sans JP は hinted と unhinted の両方が配布されている**（サイズはほぼ同じ）。
**hinted を採る。** Windows では小さい字送りでの輪郭補正が効き、
本文表示の可読性で有利なためである。

数式用の STIX Two Math（0.82MB）は latex-rust に同梱されており、これとは別に加算される
（§7.4）。**フォント総計は約 22.4MB** となる。

当初の推定（23〜25MB）に対し実測は 21.6MB で、**推定はやや過大だった**。

#### 配布サイズの見込み（**フォントは実測、実行コードは推定**）

|内訳|値|根拠|
|---|---|---|
|同梱フォント|**21.6MB**|実測（上表）|
|STIX Two Math|**0.8MB**|実測（§7.4）|
|実行コード|**25〜35MB**|**推定**。PoC の実行ファイル（iced 9.9MB / mermaid + resvg 25.1MB / 数式 4.1MB）からの見積もり|
|**単一実行ファイル**|**約 47〜57MB**|—|

**§4.2 に書いていた 33〜35MB は過小だった。** 最大の要因は **merman + resvg** で、
この 2 つだけの PoC 実行ファイルが 25.1MB ある。依存が重複するため単純な足し算には
ならないが、**40MB 台後半から 50MB 台**を見込むべきである。

v1 の配布物（NSIS 4.5MB）からは大きく増えるが、v1 は**別途 WebView2 ランタイムを
必要としていた**ため、利用者から見た導入物の総量で比較すべきである。

さらに削る手は 2 つある。いずれも**実装が動いてから判断する**（OPEN-213）。

|案|効果|代償|
|---|---|---|
|TTF を woff2 で同梱し起動時に展開|フォント 21.6MB が概ね半減|起動時間（§9.5 で既に悪化）を更に悪くする|
|merman の図種を絞る（feature 削減）|実行コードを削減|対応する図種が減る|

## 8. 10MB 対応のアーキテクチャ

PRE-004 は本書で最も影響の大きい前提である。**10MB は「300KB の 33 倍」ではなく、
設計方式が変わる境界**である。

### 8.1 成立しない方式

§6.3 の実測より、次の方式は 10MB で成立しない。

- 変更のたびに全文を解析する（comrak で 431ms。60fps の予算 16.6ms の 26 倍）
- **増分解析ライブラリに頼る**（tree-sitter-md は増分でも 2,953〜3,360ms。§8.3）
- 文書全体をウィジェット化・レイアウトする（380,812 行ぶんの構築が毎回走る）
- 生成 HTML を文字列で持つ（10MB 入力に対し 11.5MB の HTML。文字列連結だけで負荷）

### 8.2 エディタ層

- テキストは `ropey` で保持する（DEC-206）。PoC の実測で 10MB のロープ構築 12〜17ms、
  1 文字挿入 0.1ms 未満を確認済み。
- 描画は**可視行のみ**。PoC と同じ仮想化を本実装でも土台にする。
- 行番号・折り返し位置は行単位でキャッシュし、編集された行のみ無効化する。

### 8.3 解析層（DEC-204。v1.2 で全面改訂）

#### 当初案とその失敗

当初は「画面は tree-sitter-md の増分解析、出力は comrak」という二本立てを想定していた。
**PoC で検証したところ、この前提は成り立たなかった。**

計測は [`poc/v2-ui/incparse-poc`](../poc/v2-ui/incparse-poc/src/main.rs) による
（2026-09-14 / Windows 11・リリースビルド・3 回実測）。

|項目（10MB）|1 回目|2 回目|3 回目|予算 16.6ms に対して|
|---|---|---|---|---|
|tree-sitter-md 全解析|6,725ms|6,190ms|4,985ms|**約 300〜400 倍**|
|tree-sitter-md 増分（1 文字挿入）|3,360ms|3,218ms|2,953ms|**約 180〜200 倍**|
|同・最悪ケース（未閉鎖の ``` 挿入）|5,432ms|2,946ms|3,365ms|—|

**増分にしても全解析の半分にしかならない。** しかも comrak の全解析（431ms・§6.3）より
**10 倍以上遅い**。増分解析という看板に反して、文書サイズに比例して悪化する。

原因を切り分けるため、インライン木を作らずブロック文法だけで測り直した
（tree-sitter-md はブロック木に加え、インライン内容を持つブロックごとに別の木を作る）。

|項目（10MB）|1 回目|2 回目|3 回目|
|---|---|---|---|
|ブロックのみ全解析|2,760ms|4,283ms|3,253ms|
|ブロックのみ増分|302ms|557ms|439ms|

**インライン木は主因ではなかった。** ブロック文法そのものが遅く、増分でも 300〜560ms で
予算の 20〜30 倍である。**tree-sitter-md は不採用とする。**

#### 採用する方式: 全文の文法解析をしない

失敗を踏まえ、**そもそも全文を文法解析する必要があるのか**を問い直した。
必要なものは 3 つに分解でき、それぞれ全文解析を要しない。

|必要なもの|方式|10MB での実測|
|---|---|---|
|目次・プレビューの高さ推定に使う**ブロック境界**|**自前の行走査**。行頭とコードフェンスの内外だけを見る|**5.1 / 16.4 / 8.7ms**|
|エディタと**プレビューの再描画**|**可視範囲 64KB だけ** comrak で再解析|**0.55 / 2.02 / 1.41ms**|
|PDF / HTML 出力|comrak の全解析|431ms（§6.3。1 回だけ）|

行走査は 10MB からブロック 82,785 件・見出し 16,557 件を抽出して 1 桁 ms である。
可視範囲の再解析は**打鍵ごとに走っても 16.6ms の予算に対し 1 割以下**に収まる。

参考までに、同じ 64KB の窓を tree-sitter のブロック文法で解析すると
**13.1 / 43.9 / 26.2ms** かかり、**comrak で窓を解析するより 20 倍以上遅い**。
tree-sitter を部分適用しても利点が無いことが確認できた。

#### この方式の代償

|項目|内容|
|---|---|
|構造の粒度|行走査で分かるのはブロック境界と見出しまで。表やリストの入れ子は分からない。**目次と高さ推定にはこの粒度で足りる**が、それ以上が必要になったら可視範囲の comrak 結果を使う|
|安全な再解析開始点|Markdown はブロックの解釈が前方の文脈（フェンスの内外・リストの継続）に依存する。**窓の開始位置は行走査が記録したブロック境界に合わせる**必要がある。実装上の要点はここに集約される|
|コードブロックのハイライト|comrak は言語名を返すだけである。着色は別途必要（OPEN-206）|

**計測時の注意**: 3 回の値が最大 3 倍ばらついている。他の処理と並行させると悪化する
（v1 の実装方針書 §8.4 にも同じ記録がある）。**桁は安定しており、結論は変わらない。**

### 8.4 レイアウト層（プレビューの仮想化）

**ここが新規実装の最大の難所である。** エディタと違い、プレビューは行の高さが
一定でない（見出し・表・画像・図で変わる）。仮想化には次が要る。

1. ブロック単位の**高さの推定値**を持ち、スクロールバーの長さを決める
2. 可視範囲に入ったブロックだけ**実測してレイアウト**し、推定値を実測値へ置き換える
3. 置き換えによるスクロール位置のずれを補正する

ブラウザが肩代わりしていた部分であり、v1 には存在しなかった層である。

### 8.5 出力層

- **PDF**: 自前のページ分割と PDF 生成（DEC-205）。実装は **krilla 0.8**。
- **HTML**: comrak で生成する。v1 の単一ファイル HTML（CSS・画像埋め込み）の
  仕様はそのまま維持できる。

#### PDF 生成の実測（2026-09-14 / 同環境）

[`poc/v2-ui/pdf-poc`](../poc/v2-ui/pdf-poc/src/main.rs) による。A4 縦・本文 44 行・
ページ番号・ページごとの見出しとしおりを付け、日本語フォントを埋め込んだ条件。

|ページ数|生成時間|100 ページ換算|出力サイズ|しおり|
|---|---|---|---|---|
|**283**（v1 と同条件）|**0.73 秒**|0.26 秒|0.3MB|283 件|
|1,000|2.32 秒|0.23 秒|1.1MB|1,000 件|
|5,000|9.69 秒|0.19 秒|5.7MB|5,000 件|

**v1 は同じ 283 ページで 10.70 秒だった。0.73 秒は約 15 分の 1 である。**
§4.2 の目標「100 ページあたり 1 秒以内」に対して 4〜5 倍の余裕がある。
所要時間はページ数にほぼ比例し、ページ数が増えるほど 1 ページあたりは速くなる。

生成物は構造を検査して確認した。

|確認項目|結果|
|---|---|
|形式|`%PDF-1.7`|
|**しおり**|`/Outlines` あり・283 件。**OS を問わない**（v1 は Windows 限定）|
|**日本語フォントの埋め込み**|`/FontFile2` あり|
|テキスト抽出|`/ToUnicode` あり|
|ページ数|283|

**未確認**: 本 PoC の環境に PDF のレンダラ（poppler 等）が無いため、**目視での
字形確認は行っていない**。同梱フォント（DEC-209）を用意した時点で確認する。

**所見**: krilla は埋め込み時にフォントを自動でサブセット化する（283 ページ・
日本語で出力 0.3MB に収まっていることから分かる）。§7.6 では
「サブセット化しない」と決めたが、それは**アプリが画面描画に使うフォント**の話であり、
**PDF 埋め込み時のサブセット化は PDF の一般的な動作**である。OFL の Reserved Font Name
との関係（文書への埋め込みは改変にあたるか）は、配布前に確認しておく（OPEN-208）。

## 9. 新しく生じるリスク

**v2 は v1 より良くなるだけではない。** 失うもの・新しく抱えるものを明記する。

### 9.1 IME とフォント

**IME 自体は 2026-09-14 の確認で合格した**（§6.5.4）。候補窓の位置・未確定文字列・
確定 `Enter` の扱い・`Esc` の取り消しはいずれも問題なかった。

残るのは**フォントが自前責任になる**点である。WebView では OS とブラウザが
言語に応じた字形を選んでいたが、v2 では漢字統合により**放置すると中国語の字形が
出る**（§6.5.5）。画面・PDF・HTML の 3 経路すべてで同梱フォントを使う必要がある。

また、PoC で確認できたのは**既製のテキスト入力ウィジェット**の挙動である。
v2 では自前のエディタウィジェットを書くため（§7.1）、**そこで IME を正しく
扱えるかは別問題**として残る。OPEN-207 で再確認する。

### 9.2 レンダラが 3 系統に分かれる

v1 は画面・PDF・HTML のすべてを WebView2 が描いていたため、見た目は自動的に一致した。
v2 では次の 3 つが別実装になる。

|出力|描画|
|---|---|
|画面|自前レイアウトエンジン|
|PDF|自前ページ分割 + PDF 生成|
|HTML|comrak + ブラウザ|

**同じ文書が 3 通りの見た目になり得る。** 一致の検証を継続的に行う仕組み
（代表文書のスナップショット比較）を、v2 の早い段階で用意する必要がある。

### 9.3 Mermaid のパリティ

merman は「Chromium とのピクセル一致は約束しない」と明記している。
PRE-003 で許容済みであり、§7.3 の PoC で 8 種中 7 種が描けることを確認した。

残る具体的な差は 2 点である。

1. **HTML ラベルを使えない。** サイト設定で無効化する前提のため、
   ラベル内の HTML 表現（改行タグ・書式）は v1 と同じにはならない。
2. **erDiagram のラベルが欠ける**（OPEN-210）。暫定はコードブロック表示への退避。

**目視での比較は未実施**である（OPEN-209 と同じく PDF / 画像レンダラが無いため）。

### 9.4 アクセシビリティ

ブラウザ標準の支援技術対応を失う。AccessKit で補えるが、v1 と同等にはならない。

### 9.5 起動時間と PDF のページ数

**正直に記録しておくべき悪化が 2 点ある。**

1. **起動時間は v1 より遅くなる見込み。** PoC の起動〜初回描画は 1.1〜1.4 秒で、
   v1 の 283ms を大きく上回る。GPU まわりの初期化が主因と考えられる。
   §4.2 の目標を 2 秒としたのはこのためであり、**v1 の 283ms には戻せない**。
   窓を先に出して内容を後から描く等の緩和策は基本設計で検討する。
2. **10MB の PDF 出力はページ数が現実的でない。** v1 の計測では 300KB が 283 ページ
   だった。単純比例なら 10MB は約 9,400 ページになる。§8.5 の実測（5,000 ページで
   9.69 秒）から**約 18 秒**と見積もられる。生成速度は改善したが、
   **9,400 ページの PDF が成果物として妥当か**は別問題であり、
   **出力範囲の指定**等の機能側の手当てが要る（OPEN-204）。
