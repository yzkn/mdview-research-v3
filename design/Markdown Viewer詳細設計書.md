### 2.1 DD-03 の根拠（フォント読み込みの実測）

基本設計書 §20.3 で「未計測」としていた項目である。
[`poc/v2-ui/font-poc`](../poc/v2-ui/font-poc/src/main.rs) で実測した
（2026-09-15 / Windows 11・リリースビルド）。

同梱予定の PlemolJP / IBM Plex Sans JP は手元に無いため、
**サイズの近いシステムフォント 6 件（合計 58.99MB）で代用**し、
`fontdb` への登録時間を測った（iced が内部で通る経路）。

|項目|実測|
|---|---|
|登録（58.99MB・18 フェイス）|**16.4ms**|
|1MB あたり|**0.28ms**|
|**同梱予定 21.6MB への外挿**|**約 6ms**|

**起動時間の目標 2 秒に対し、フォントは問題にならない。**
GPU / ウィンドウ初期化の 1.0〜1.3 秒に比べて 3 桁小さい。
**遅延読み込みの複雑さを負う理由が無い**ため、起動時に一括で読む。

> **ただしこの 6ms は「登録」までである。** `fontdb` の登録はフェイス情報の
> 読み取りまでで、**字形の実際のラスタライズは初回使用時に遅延して起きる**。
> その分は初回描画に乗る。§10 の P1 完了時に、実アプリの起動時間として
> 測り直す（§11 の DD-OPEN-01）。

## 3. レイアウトエンジン詳細設計

基本設計書 §16 の方式を実装できる粒度にする。

### 3.1 データ構造

```rust
/// 1 ブロックのレイアウト結果。キャッシュの値でもある。
struct LaidOutBlock {
    /// このブロックの総高さ
    height: f32,
    /// 描画プリミティブ（基本設計書 §16.10）
    primitives: Vec<Primitive>,
    /// 行の境界。検索の強調とスクロール同期に使う
    lines: Vec<LineBox>,
    /// このブロックが参照する埋め込み（図・数式・画像）
    embeds: Vec<EmbedRef>,
}

struct LineBox {
    /// ブロック先頭からの相対 Y
    top: f32,
    height: f32,
    /// この行が対応する原文のバイト範囲
    source: Range<usize>,
}

/// レイアウトの入力。幅とテーマ以外に環境を持ち込まない（テスト可能にするため）
struct LayoutContext<'a> {
    width: f32,
    zoom: f32,
    metrics: &'a FontMetrics,
    embeds: &'a EmbedCache,
}
```

**`LayoutContext` にウィンドウや iced の型を入れない。**
レイアウトを描画層から独立させる（基本設計書 §4.2）ための具体的な担保である。

### 3.2 インライン要素の行分割

段落・見出し・リスト項目・表のセル・引用の中身はすべてこの処理を通る。

```text
入力: インライン要素の列（テキスト・強調・コード・リンク・画像・数式）と利用可能幅

1. 要素を「整形の単位」へ分解する
     テキスト  → 書体（本文 / 太字 / 等幅）が同じ範囲ごとに 1 単位
     コード    → 等幅の 1 単位
     画像/数式 → 寸法が確定した 1 個の箱（分割しない）
2. 各単位を cosmic-text で整形し、字送り位置を得る
3. 改行可能位置を求める（UAX #14 の行分割規則）
4. 貪欲法で行を詰める
     現在行の幅 + 次の単位の幅 <= 利用可能幅 なら同じ行
     超えるなら、直前の改行可能位置で折る
5. 1 単位が単独で幅を超える場合は、その単位の中で改行可能位置を探して折る
6. どこでも折れない場合（長い英単語・URL）は、文字単位で強制的に折る
```

#### 日本語の禁則処理

**UAX #14 の規則をそのまま使う。** 日本語の基本的な禁則（`、` `。` `）` `」` を
行頭に置かない、`（` `「` を行末に置かない）は UAX #14 に含まれる。

> **追い出し・追い込みによる調整は行わない。** 行末の約物を半角詰めするような
> 組版上の調整は、実装量に見合わない。**折り返し位置が正しいことを優先する。**

#### 強調（斜体）の扱い

**基本設計書 §16.11 は「斜体は合成する（同梱しない）」としている。**
同梱フォントは Regular / Bold の 2 ウェイトに絞っている（技術選定書 DEC-209）
ため、斜体の字形そのものは持たない。

**合成斜体（せん断変形）が日本語の字形に耐えるかは、フォントを同梱する P3 まで
検証できない。** 現在はまだシステムフォントで描いており、ここで合成の可否を
判断すると誤った結論になる。

そこで、レイアウト層は**字形と装飾を分けて**返す。合成するか否かは描画層の
判断に閉じ込め、レイアウト結果には「強調である」という事実だけを残す。

|記法|字形（`TextStyle`）|装飾（`RunDecoration`）|
|---|---|---|
|`**太字**`|`Bold`（見出しの中では据え置き）|なし|
|`*強調*`|**据え置き**|`Emphasis`|
|`` `コード` ``|`Mono`|`Code`|
|`[本文](url)`|据え置き|`Link`|

装飾をどう見せるかは描画層が決める。**暫定で色で区別**し、インラインコードだけ
地を敷く。P3 でフォントを同梱したあと、合成斜体を試して見た目を確かめる
（DD-OPEN-09）。レイアウト層はどちらでも変わらない。

#### 折り返しは装飾の境界をまたぐ

`**太**字` のような境界で不自然に切れないよう、**行頭記号とインライン要素を
1 本の文字列につないでから**折り返す（`StyledText`）。幅の測定だけを区間ごとに
行って足す。リスト項目の 2 行目以降は、行頭記号の幅だけ右へぶら下げる。

#### 字下げは解析層が決める

引用の深さもリストの入れ子も、解析層が段数（`LogicalLine::indent`）として返す。
**レイアウト層でブロック種別を見て字下げを足してはいけない。**
引用ブロックで二重に効き、字下げが 2 段になる（実際に踏んだ）。

#### 箱の扱い

画像・数式・図は**分割しない 1 個の箱**として扱う。

|状況|扱い|
|---|---|
|箱が利用可能幅に収まる|そのまま置く|
|箱が利用可能幅を超える|**縦横比を保って縮小する**|
|インライン数式|行の高さに合わせてベースラインを調整する|

### 3.3 表の列幅の決定

**2 パスで決める。**

```text
パス 1: 各セルの「自然幅」を測る（折り返さない場合の幅）
        列 i の自然幅 = その列の全セルの自然幅の最大値
        列 i の最小幅 = その列の全セルの「これ以上縮められない幅」の最大値
                        （日本語は 1 文字幅、英数は最長単語の幅）

パス 2: 列幅を決める
        S = Σ 自然幅、 W = 利用可能幅
        if S <= W:
            列幅 = 自然幅（表を左寄せし、余白は右に残す）
        else:
            列幅 = 最小幅 + (W - Σ最小幅) * (自然幅_i - 最小幅_i) / Σ(自然幅 - 最小幅)
            （Σ最小幅 > W の場合は最小幅のまま置き、表を横スクロールさせる）
```

**自然幅の測定は全行を見る必要がある。** 表が非常に長い場合（数千行）は
コストが問題になるため、**先頭 200 行だけを見て決める**。
以降の行がはみ出す場合はそのセル内で折り返す。

> 200 行という値は、数千行の表が社内文書に現れる想定が薄いことによる暫定値である。
> 実運用で問題が出たら調整する（§11）。

#### 「これ以上縮められない幅」の求め方

**UAX #14 の改行可能位置で切った断片の、いちばん広いもの**とする。
§3.2 の行分割と同じ規則なので、別の規則を持ち込まずに済む。
結果として日本語は 1 文字、英数は最長の単語になり、設計の意図どおりになる。

#### 表の描画

|要素|扱い|
|---|---|
|見出し行|太字にする|
|寄せ|区切り行の `:` から決める（`CellAlign`）|
|行の高さ|**いちばん背の高いセル**に合わせる|
|罫線|行の下ごとに 1 本。`LaidOutBlock::rules` に位置だけ持ち、描画層が引く|
|セルが足りない行|空として扱う。**列を詰めない**（以降の列がずれるため）|

**表は等幅ではなく本文の書体で描く。** 列幅が決まるので、原文の `|` を
揃えて見せる必要が無くなった。

### 3.4 リストと引用の入れ子

```text
インデント幅 = 深さ * indent_unit（既定 24px）
マーカー幅   = 箇条書きは固定、番号付きは桁数に応じる

リスト項目の利用可能幅 = 親の利用可能幅 - インデント幅 - マーカー幅
```

- **入れ子の深さ上限を 8 とする。** 超える場合は 8 として扱う。
  異常な文書でレイアウトが破綻しないようにするため
- 引用（`>`）は左に縦線を引き、`indent_unit` ぶん内側へ寄せる
- **リスト項目の中にブロック（コード・表・図）が来る場合も同じ規則で幅を狭める**

### 3.5 ブロック種別ごとの高さ

|kind|レイアウト|
|---|---|
|Heading(n)|§3.2 の行分割。上下に見出し用の余白|
|Paragraph|§3.2 の行分割|
|Code|**行分割しない**（横スクロール）。行数 × 等幅行高 + 余白。着色は §16.13|
|Table|§3.3 で列幅を決め、各セルを §3.2 で行分割。行高はセルの最大高|
|List / Quote|§3.4 で幅を決め、子を再帰的にレイアウト|
|Image / Mermaid / Math|埋め込みの実寸（未着なら §16.5 のプレースホルダ）|
|Rule|固定高|

**コードブロックを折り返さない**のは、エディタ側と同じ理由（DD-01）と、
コードは折り返すと読みにくいためである。

### 3.6 高さ索引の実装（DD-07）

```rust
struct HeightIndex {
    /// 1-origin の Fenwick 木。tree[0] は使わない
    tree: Vec<f32>,
    /// 各ブロックの現在の高さ（差分計算に使う）
    heights: Vec<f32>,
}

impl HeightIndex {
    fn build(heights: Vec<f32>) -> Self;          // O(n)
    fn set(&mut self, index: usize, height: f32); // O(log n)
    fn prefix_sum(&self, index: usize) -> f32;    // O(log n) 先頭から index-1 まで
    fn total(&self) -> f32;                        // O(1)
    /// 文書 Y を含むブロックを探す
    fn find(&self, y: f32) -> (usize, f32);        // O(log n) 二分探索
}
```

#### ブロック数が変わる編集への対応

**Fenwick 木は要素数の増減に向かない。** 編集でブロックが増減したら**作り直す**。

|項目|値|
|---|---|
|作り直しの計算量|O(n)|
|10MB（82,785 ブロック）での見込み|**1ms 未満**|
|発生頻度|ブロックが増減する編集のみ（改行の追加・削除、フェンスの開閉）|

**セグメント木や平衡二分木で挿入削除を O(log n) にする必要はない。**
1ms 未満なら 16.6ms の予算に対して十分小さく、Fenwick 木の単純さのほうが価値がある。

> **ここでいう「作り直し」は Fenwick 木だけである。**
> **高さの推定値まで測り直してはいけない。** 推定にはブロックごとの本文が要り、
> ロープの切り出しと文字列化が件数ぶん走る。10MB で 74ms かかった（実測）。
> **走査し直したブロックだけ測り、残りは前の値を使い回す。**
>
> 同じ理由で、**ブロック列も丸ごと作り直してはいけない。** 変わっていないブロックまで
> 複製すると 14ms かかる。`Vec::splice` で入れ替える範囲だけを触る。

> ただし**連続入力で毎回作り直すと積み上がる**。改行を押しっぱなしにした場合を
> 想定し、**作り直しは 1 フレームに 1 回へまとめる**（同一フレーム内の複数編集は
> 最後にまとめて再構築する）。

### 3.7 アンカー補正の手順

基本設計書 §16.7 の実装手順である。

```text
毎フレーム:
  1. anchor.block_id から文書 Y を求める
       doc_y = height_index.prefix_sum(anchor.block_id) + anchor.offset_in_block
  2. doc_y から可視範囲のブロックを列挙する
  3. 可視ブロックをレイアウトし、高さが変わったものを height_index.set で更新する
  4. **anchor は変更しない**（これが「内容が動かない」ことの担保）
  5. スクロールバーは doc_y / height_index.total() から描く

スクロール操作を受けたとき:
  1. 現在の doc_y を求める
  2. doc_y += 移動量
  3. height_index.find(doc_y) で新しい (block_id, offset) を求め、anchor を更新する
```

**ステップ 4 が要点である。** 高さの更新後に anchor を再計算すると、
補正した意味が無くなる。

#### 例外: 可視範囲より上で高さが大きく変わった場合

TOC ジャンプや検索移動の直後は、上方の推定が実測と大きく食い違うことがある。
このとき**スクロールバーのつまみが不自然に飛ぶ**。

対処として、**上方のブロックを 1 フレームあたり最大 200 件だけ先行してレイアウトし、
推定を実測へ寄せる**（バックグラウンド補正）。可視範囲の描画が終わったあとの
余り時間で行い、16.6ms を超えそうなら打ち切る。

### 3.8 キャッシュの実装

struct LayoutCache {

struct BlockKey {

## 4. エディタウィジェット詳細設計

### 4.0 画面に出すもの

**設計書に規定が無く、実装で漏らした**（P1 の確認で指摘を受けた）。明記する。

|要素|規定|
|---|---|
|**キャレット**|カーソル位置に**幅 2px の縦棒**を描く。**0.5 秒周期で点滅**する|
|キャレットの位置|**文字数 × 固定幅では求めない。** 等幅でも日本語は半角 2 文字分の幅があるため、行頭からカーソル桁までを**実際に整形して測る**|
|変換中のキャレット|**未確定文字列の末尾**へ置く。ここが変換候補窓の位置にもなる（§4.5）|
|点滅の位相|キー操作・クリックの直後は**必ず表示**にする。位置が変わった瞬間に消えていると分かりにくい|
|カーソル行が画面外|**描かない**|
|**マウスポインタ**|テキスト領域の上では **I ビーム**にする|
|行番号|カーソル桁が左へはみ出す場合、**行番号の欄へキャレットを描かない**|

### 4.0.1 カーソル移動の規定

**ウィジェットは「どう動かしたいか」だけを伝え、解決はアプリ層で行う。**
行の長さや行数の判断を 1 か所へ集めるためである。

|操作|動き|
|---|---|
|←|1 文字戻る。**行頭では前の行の末尾へ**|
|→|1 文字進む。**行末では次の行の先頭へ**|
|↑ / ↓|1 行動く。**目標桁を保つ**（下記）|
|Home / End|行頭 / 行末|
|クリック|その位置。行・桁とも範囲へ丸める|

#### 目標桁（`goal_column`）

**上下移動では、最後に横方向で決めた桁を覚えておく。**

短い行を通り越したときに桁へ戻せるようにするためで、これが無いと
短い行を通過した時点で桁が失われる。横移動・編集・クリックで解除する。

```text
aaaaaaaa   ← 桁 7 にいる
bb         ← ↓ で桁 2 へ寄る（goal_column = 7 は保つ）
cccccccc   ← ↓ で桁 7 へ戻る
```

### 4.1 状態

```rust
struct EditorView {
    /// 画面最上部の行番号（固定行高のため行番号で持てる）
    top_line: usize,
    /// 横スクロール量（DD-01 により折り返さない）
    scroll_x: f32,
    cursor: Position,
    /// 選択の始点。None なら選択なし
    anchor: Option<Position>,
    /// 矩形選択かどうか
    block_selection: bool,
    /// IME の状態（§4.5）
    ime: ImeState,
    /// 目標桁。上下移動で桁位置を保つために使う
    goal_column: Option<usize>,
}
```

**`goal_column`** は、短い行を通り越して上下移動しても桁が戻る挙動のために要る。
これが無いと、短い行を通過した時点で桁が失われる。

### 4.2 折り返しを提供しない決定（DD-01）

|案|効果|代償|
|---|---|---|
|**折り返さない（採用）**|行高が一定。可視行の算出が割り算だけ。高さ索引が不要|**長い行を読むのに横スクロールが要る**|
|折り返す|長い行が読みやすい|380,812 行に対する高さ索引がもう 1 つ必要。幅変更のたびに全行を推定し直す|

**v1（CodeMirror）は折り返していたため、これは機能の後退である。**
散文を書く用途では折り返しが欲しくなる可能性が高いため、
**実運用の反応を見て v2.1 以降で再検討する**（§11）。

緩和策として、**長い行があることを視覚的に示す**（右端に印を出す）。
実装は §10.21。`Shift` + ホイールと水平ホイールで横へ送り、
キャレットは打鍵に合わせて追う。

> **2026-09-20 の確認**: 分割表示で境目を動かすと、右のプレビューは
> 幅に応じて折り返しが変わるのに左のエディタは変わらない、という指摘を受けた。
> これは DD-01 の帰結であり仕様どおりである。**v2.1 以降で折り返しを
> 再検討する**（DD-OPEN-03）。あわせて、長い行がプレビュー側へ
> 描き込まれる不具合（切り抜き漏れ）を §10.21 で直した。

> **v2.2.0 の決定（2026-10-14）**: **512 KB 以下の文書に限って**、設定で折り返せるようにした
> （既定は折り返さない）。大きい文書では上の代償（全行の段数の数え直し）が重いので、
> 設定が入っていても折り返さない。作り方は §10.61。最初は 1 MB としたが、目視確認で応答が
> 遅かったため 512 KB に下げた（段の表の作り直しは 512 KB で約 3 ms）。

### 4.3 入力処理

```text
キー入力を受けたとき:
  1. IME が変換中なら、Enter / Esc はアプリで処理しない（§4.5）
  2. ショートカットに一致すればコマンドを実行する
  3. 文字入力なら:
       選択があれば削除してから挿入する
       編集を Document へ適用する
       履歴へ積む（§4.7 のまとめ規則に従う）
       cursor を更新し、goal_column をクリアする
  4. 可視範囲にカーソルが入るようスクロールする
```

### 4.4 選択

|操作|動作|
|---|---|
|**クリック**|**その位置へキャレットを置く。** 桁は、行頭からの幅を測って最も近い文字境界へ寄せる|
|ドラッグ|`anchor` を押下位置に置き、`cursor` を追従させる|
|`Shift` + 移動|`anchor` が無ければ現在位置に置き、`cursor` を動かす|
|ダブルクリック|単語を選ぶ（§4.6）|
|3 回クリック|行を選ぶ|
|`Alt` + ドラッグ|**矩形選択**|

#### 矩形選択

```text
矩形選択の範囲 = (anchor.line..cursor.line) × (min(桁)..max(桁))

- 各行について、行の長さが桁範囲に満たない場合はその行の選択は空とする
- 入力は各行の同じ桁へ同時に適用する
- 履歴には 1 件としてまとめて積む
```

**v1 には無かった機能である。** 表の列を揃える等で有用なため追加する。

### 4.5 IME の状態機械

```text
        ┌──────────────┐
        │    Idle      │
        └──────┬───────┘
               │ Ime::Preedit（未確定文字列あり）
               ▼
        ┌──────────────┐  Ime::Preedit（更新）
        │   Preedit    │◄─────────┐
        │  text, range │──────────┘
        └──┬────────┬──┘
           │        │
  Ime::Commit    Ime::Preedit("")（取り消し）
           │        │
           ▼        ▼
        ┌──────────────┐
        │    Idle      │
        └──────────────┘
```

|状態|挙動|
|---|---|
|`Idle`|通常のキー入力を受ける|
|`Preedit`|**未確定文字列を描画のみ**行う。ロープには入れない。`Enter` / `Esc` / 矢印キーをアプリで処理しない|

確定時の処理:

```text
1. 選択があれば削除する
2. 確定文字列を挿入する
3. 履歴へ 1 件として積む（未確定中の更新は積まない）
4. ime を Idle へ戻す
```

**毎フレーム、キャレットの矩形を OS へ通知する**（候補窓の位置決め）。
これを怠ると候補窓が画面の隅に出る（技術選定書 §6.5 の確認項目 2）。

### 4.6 単語境界（DD-08）

v1 は `Intl.Segmenter`（ブラウザの ICU・辞書ベース）を使っていた。
v2.0.0 はブラウザを持たないため、次の規則で代用する。

```text
1. UAX #29 の単語境界で区切る
2. さらに、**文字種の切り替わり**でも区切る
     文字種 = { ひらがな, カタカナ, 漢字, 英数, 記号, 空白 }
3. 区切り文字（空白・句読点・記号）の上ではダブルクリックの補正を行わず、
   その 1 文字だけを選ぶ
```

**v1 より粗い。** 辞書を持たないため「東京都庁」は 1 語になり、
「今日はいい天気」は「今日」「はいい」…ではなく文字種境界で
「今日」「はいい」「天気」のように切れる。

|方式|「今日はいい天気」|判定|
|---|---|---|
|v1（ICU 辞書）|今日 / は / いい / 天気|最良|
|**v2.0.0（文字種境界）**|**今日 / はいい / 天気**|**実用範囲**|
|UAX #29 のみ|今日はいい天気（1 語）|**不可**|

辞書（例: mecab 系）を同梱すれば v1 相当にできるが、**配布サイズが数十 MB 増える**。
すでに 47〜57MB あるため採らない。**体感は実装後に確認する**（§11）。

### 4.7 編集履歴（DD-05）

```rust
struct History {
    undo: Vec<Transaction>,
    redo: Vec<Transaction>,
    /// 保持している removed / inserted の合計バイト数
    bytes: usize,
}

struct Transaction {
    edits: Vec<Edit>,          // 矩形選択などで複数になる
    cursor_before: Position,
    cursor_after: Position,
    timestamp: Instant,
}
```

#### まとめ規則

**次のすべてを満たすとき、直前のトランザクションへ統合する。**

1. 直前から 500ms 以内
2. 1 文字の挿入である（削除・貼り付け・矩形編集は統合しない）
3. 挿入位置が直前の挿入の直後である
4. 挿入文字が改行でない

**改行で区切る**のは、行単位で undo できたほうが実用的なためである。

#### 上限（DD-05）

- **保持バイト数 64MB を超えたら、古いトランザクションから捨てる**
- **圧縮しない。** 10MB 文書でも、通常の編集で 64MB に達するには相当の操作量が要る。
  圧縮の複雑さに見合わない

## 5. PDF のページ分割規則

基本設計書 §17.7 を具体化する。

### 5.1 用紙とマージン

|項目|値|
|---|---|
|用紙|A4 縦（595 × 842 pt）|
|余白|上 56pt / 下 56pt / 左右 56pt|
|ヘッダー領域|上余白の中に文書タイトル|
|フッター領域|下余白の中にページ番号（中央）|
|本文幅|**483pt**|

### 5.2 分割の基本規則

```text
現在ページの残り高さ = 本文領域の高さ - 積んだ高さ

各ブロックについて:
  if ブロック高 <= 残り高さ:
      そのまま積む
  elif ブロック高 > 本文領域の高さ:
      分割可能なら行単位で分割して積む（§5.3）
      分割不可なら（図・画像）縮小して 1 ページに収める
  else:
      改ページして次ページの先頭へ積む
```

### 5.3 分割可能なブロック

|kind|分割|
|---|---|
|Paragraph / List / Quote|**行単位で分割する**|
|Code|**行単位で分割する。** 分割後のページに「(続き)」を示さない|
|Table|**行単位で分割し、分割後のページにヘッダー行を繰り返す**|
|Heading|**分割しない**|
|Image / Mermaid / Math|**分割しない**。1 ページに収まらなければ縮小する|

### 5.4 引き離しの禁止

```text
1. 見出しの直後で改ページしない
     見出しを積んだあと、次のブロックの先頭 2 行が入らないなら、
     見出しごと次ページへ送る
2. 段落の 1 行だけを次ページへ送らない（孤立行の禁止）
     分割後の残りが 1 行になるなら、2 行送る
3. 段落の 1 行だけをページ末に残さない
     分割後の先頭が 1 行になるなら、段落ごと次ページへ送る
```

**2 と 3 は、段落が 3 行未満の場合は適用しない**（適用すると無限に送られる）。

### 5.5 明示的な改ページ

`<!-- pagebreak -->` を改ページとして扱う（v1 から継続）。
行走査（基本設計書 §12.6）でこのコメント行を `BlockKind::PageBreak` として拾う。

### 5.6 出力範囲の指定 UI（DD-06）

SCR-005 に排他選択で 3 つ置く。

```text
出力範囲
  (•) 文書全体            （推定 約 9,400 ページ）
  ( ) 見出しを選ぶ...     → TOC から選択
  ( ) ページを指定        [ 1 ] ページから [ 50 ] ページ
保存先  [ ............................. ] [参照]
                                   [ 出力 ] [ キャンセル ]
```

- **推定ページ数を常に表示する。** 行走査の結果から概算できる
  （総高さ ÷ 本文領域の高さ）
- 推定が 500 ページを超える場合、**「文書全体」の右に所要時間の目安を出す**

## 6. モジュール間の API 境界

### 6.1 方針

**層をまたぐ型は最小限にし、下位層は上位層の型を知らない。**
これにより、レイアウト層を iced 無しで単体テストできる（基本設計書 §22.1）。

### 6.2 主要なインタフェース

```rust
// ── parse → layout ───────────────────────────────
/// 可視範囲の解析結果。comrak の型を層の外へ出さない
pub struct ParsedRange {
    pub blocks: Vec<ParsedBlock>,
}
pub struct ParsedBlock {
    pub block_id: usize,
    pub content: BlockContent,   // 段落・表・コード…の構造
}

pub trait Parser {
    fn scan_lines(&self, text: &Rope) -> BlockIndex;
    fn parse_range(&self, text: &Rope, range: Range<usize>) -> ParsedRange;
}

// ── layout → render ──────────────────────────────
pub trait LayoutEngine {
    fn layout_block(&mut self, block: &ParsedBlock, cx: &LayoutContext) -> LaidOutBlock;
    fn visible(&mut self, anchor: &ScrollAnchor, viewport: Size, cx: &LayoutContext)
        -> VisibleLayout;
}

pub struct VisibleLayout {
    pub primitives: Vec<Primitive>,
    pub doc_y: f32,
    pub total_height: f32,
}

// ── embed（非同期） ───────────────────────────────
pub trait EmbedRenderer: Send {
    fn request(&self, key: EmbedKey, source: EmbedSource) -> JobId;
    fn poll(&self) -> Vec<(EmbedKey, Result<RenderedEmbed, EmbedError>)>;
}
```

**`EmbedRenderer` は `Send`** である。ワーカースレッドで動かすため。

### 6.3 描画プリミティブの色

```rust
/// 実際の色ではなく「役割」を持つ（基本設計書 §10.3）
enum ColorRole {
    Text, TextMuted, Heading, Link, CodeText, CodeBackground,
    Border, Selection, SearchMatch, SearchCurrent, Quote,
    /// 着色結果は役割に還元できないため直接色を持つ
    Direct(Rgba),
}
```

**当初は「コード着色だけは `Direct` を使う」としていたが、やめた。**
syntect から色ではなく**スコープを取り出して役割へ写す**ことにしたため
（§10.9）、着色結果にテーマは含まれない。

したがって `Direct` は使わず、字句の役割（`TokenRole`）を持つ。
**テーマを切り替えても着色キャッシュを破棄しなくてよい**
（基本設計書 §10.3 もあわせて改訂した）。

### 6.4 メッセージ

```rust
enum Message {
    // 入力
    Key(KeyEvent), Mouse(MouseEvent), Ime(ImeEvent),
    // 文書
    Edit(EditCommand), Undo, Redo,
    // 表示
    Scroll(ScrollDelta), SetMode(ViewMode), SetTheme(ThemePreference), Zoom(f32),
    // 非同期の完了
    FileLoaded(Result<LoadedFile, IoError>),
    FileSaved(Result<(), IoError>),
    EmbedReady(EmbedKey, Result<RenderedEmbed, EmbedError>),
    HighlightReady(HighlightKey, Vec<StyledRange>),
    SearchProgress(SearchBatch),
    ExportProgress(ExportProgress),
    // その他
    Tick,
}
```

**`Message` に本文（`String`）を載せない。** 10MB のコピーが発生するため、
編集は `EditCommand`（範囲と差分）として運ぶ（基本設計書 §13.1）。

### 6.5 エラー型

```rust
#[derive(Debug, thiserror::Error)]
enum AppError {
    #[error("ファイルを読み込めません: {0}")]
    Io(#[from] IoError),
    #[error("フォントを読み込めません: {0}")]
    Font(FontError),          // 起動を中止する（基本設計書 §18.1）
    #[error("図を描画できません: {0}")]
    Embed(EmbedError),        // 該当箇所のみ原文表示
    #[error("出力に失敗しました: {0}")]
    Export(ExportError),
}
```

**層ごとにエラー型を分け、`AppError` へ集約する。**
利用者に見せる文言は `Display` に持たせ、記録用の詳細は `source()` に残す。

## 7. 設定ファイルの項目定義

### 7.1 保存先

|OS|パス|
|---|---|
|Windows|`%APPDATA%\mdview\settings.toml`|
|macOS|`~/Library/Application Support/mdview/settings.toml`|
|Linux|`$XDG_CONFIG_HOME/mdview/settings.toml`（既定 `~/.config/...`）|

同じフォルダに、窓どうしが設定を同時に読み書きしないための `settings.lock`（中身は空）を置く（v2.3.0。§10.60）。

**名前を変える前（`markdown-viewer`）の置き場も読む**（2026-10-02）。
見ないと、名前を変えただけでテーマや分割比が初期値へ戻る。次に保存した
ときに新しい置き場へ移り、古いほうは消さない——消して失敗すると戻せない。

### 7.2 項目

|キー|型|既定値|範囲・注記|
|---|---|---|---|
|`theme`|文字列|`"system"`|`light` / `dark` / `system`|
|`view_mode`|文字列|`"split"`|`edit` / `preview` / `split`|
|`toc_visible`|真偽|`true`|—|
|`zoom`|小数|`1.0`|**0.5〜3.0**。範囲外は丸める|
|`scroll_sync`|真偽|`true`|—|
|`toc_width`|小数|`280.0`|**120.0〜600.0**|
|`split_ratio`|小数|`0.5`|**0.2〜0.8**|
|`config_version`|整数|`1`|**書式変更時の移行に使う**|

### 7.3 読み込みの規則

```text
1. ファイルが無い → 既定値ですべて埋める（エラーにしない）
2. 解析に失敗   → 既定値で起動し、ステータスバーに知らせる。
                  **壊れたファイルは config.toml.bak へ退避して上書きする**
3. 未知のキー   → 無視する（前方互換）
4. 既知のキーで値が範囲外 → その項目だけ既定値にする
5. config_version が未来の値 → 既定値で起動し、警告する
```

**設定の破損でアプリが起動しない事態を避ける**（基本設計書 §13.5）。

### 7.4 書き込み

- **変更から 1 秒のデバウンス**
- 一時ファイルへ書いてから置き換える（本文の保存と同じ。基本設計書 §14.3）
- 終了時は必ずフラッシュする

|Undo / Redo|`Ctrl + Z` / `Ctrl + Y`（`Ctrl + Shift + Z` も可）|`Cmd + Z` / `Cmd + Shift + Z`|
|終了|`Alt + F4`|`Cmd + Q`|

#### 入力欄が受け取ったものは横取りしない

`Ctrl + X` / `C` / `V` / `Z` / `Y` は、**どの部品も受け取らなかったときだけ**
アプリの操作として扱う。検索欄に焦点があるときは入力欄自身が処理するため、
横取りすると**検索欄へ貼り付けたつもりが本文にも入る**。

新規・開く・保存・検索の開始は、入力欄が扱わないので無条件に受ける。

#### キー配列への対応（v1 の知見を引き継ぐ）

- **拡大・縮小は物理キー位置ではなく入力文字で判定する。**
  `+` / `=` / `-` のいずれかを受け取る。物理キー位置で指定すると JIS 配列で入力できない
- **拡大の `=` は Shift 併用時を除外する。** JIS では `Shift` + `-` が `=` になるため
- **macOS では Command を押している間、Shift が入力文字へ反映されない。**
  v1.0.1 で踏んだ不具合であり、macOS では修飾キーの状態を別に見る

|条件|描画回数 / 15 秒|CPU / 回|ピークメモリ|
|---|---|---|---|
|Edit のみ|801|4.68ms|194MB|
|**Split（エディタ + プレビュー）**|**1,585**|**5.63ms**|**194MB**|

**メモリは 194MB で、目標 600MB（§20.2）に対して十分な余裕がある**
（ただし図・数式・画像のキャッシュはまだ無い）。

#### 判明した非効率: 1 表示につき 2 回描画している

Split では描画回数が Edit の **約 2 倍**になった。原因は次のとおり。

```text
再描画要求 → update() で可視範囲をレイアウト → 高さの更新を publish
          → update() が走る → view() → 再描画要求 → レイアウトし直し（更新なし）
```

**高さの更新をメッセージで返すため、1 回の表示につきレイアウトが 2 回走る。**
2 回目は更新が出ないので収束はするが、CPU を 2 倍使っている
（Edit 3.75 秒に対し Split 8.92 秒 / 15 秒）。

対処として**レイアウトキャッシュ（§3.8）を実装した**。2 回目はキャッシュを引くだけになる。

|条件|描画回数 / 15 秒|CPU / 回|CPU 合計|
|---|---|---|---|
|Edit のみ|817|4.70ms|3.84 秒|
|Split（キャッシュ**なし**）|1,585|5.63ms|8.92 秒|
|**Split（キャッシュ**あり**）**|1,572|**3.65ms**|**5.74 秒**|

**1 回あたり 35%、合計で 36% 減った。** 描画回数そのものは減っていない
（高さの更新をメッセージで返す構造は変わらないため）が、2 回目が安くなった。

**キャッシュの鍵に添字を使ってはいけない。** ブロックが削除されると別の内容が
同じ添字を取り、古い結果を引いてしまう。`Block::revision`（走査時に採番する
一意な番号）を鍵にし、位置がずれただけのブロックは番号を引き継ぐ。
これにより、スクロールだけでは再レイアウトが起きない（基本設計書 §16.6）。

> **番号は実行中で一意でなければならない**（2026-09-20 追記）。
> 当初は文書ごとに 0 から振り直していたため、**別のファイルを開くと
> 新しい文書のブロックが前の文書と同じ番号を取り、キャッシュが古い結果を
> 返した**（Split で左は新しい内容、右は前の内容のまま。実際に踏んだ）。
>
> エディタは本文を直接描いてキャッシュを経由しないため、
> **片側だけ正しく見える**という分かりにくい出方になる。
>
> `revision` は「ブロックの同一性」であって文書内の通し番号ではない。
> **添字を鍵にしてはいけないという上の注意と同じ誤り**を、
> 対象を変えて繰り返したことになる。

> **描画回数が 2 倍のままである点は残る。** CPU は 1 回 3.65ms で予算 16.6ms の
> 22% であり実害は小さいが、高さの更新をメッセージ経由で返す構造自体は
> 見直す余地がある（DD-OPEN-08）。

#### インライン要素を入れたあとの実測（2026-09-19）

プレビューが「整形された原文」ではなく**本当のプレビュー**になった。
その代償を測る。

### 10.9 P3: コードブロックの着色（2026-09-20）

技術選定書 DEC-211 のとおり **syntect 5** を使う。

#### 色ではなく「役割」を取り出す

**syntect から色そのものを取り出さない。** 基本設計書 §16.10 のとおり、
色は役割（`ColorRole`）で持ち、実際の色は描画時にテーマで解決する。

そこで `HighlightLines`（色を返す API）ではなく `ParseState` + `ScopeStack`
を直接使い、スコープ（`keyword.control.rust` など）を役割へ写す。

|役割|スコープの前置き|
|---|---|
|`Comment` / `Str`|`comment` / `string`|
|`Number`|`constant.numeric`|
|`Keyword`|`keyword` / `storage`|
|`Function`|`entity.name.function` / `support.function`|
|`Type`|`entity.name.type` / `entity.name.class` / `support.type`|
|`Constant`|`constant`|
|`Punctuation`|`punctuation`|

この形にすることで、**テーマを同梱せずに済み**（実行ファイルが小さく起動も速い）、
PDF・HTML 出力でも同じ分類を使える。

> **コメントと文字列は「入れ物」として先に見る。** `// note` の `//` は
> `punctuation.definition.comment` であり、内側から順に見ると約物に当たって
> しまい、コメント 1 行が 2 つに割れる（実際に踏んだ）。

> **改行を区間に含めてはいけない。** コメントや文字列のスコープは改行まで伸びる。
> 切り詰めないと行からはみ出した範囲を返す（実際に踏んだ）。

#### フェンス行は表示しない

` ``` ` の行は出さず、中身だけを描く。記法を消すのはインライン要素（§12.7）と
同じ考え方である。閉じフェンスが無い場合（文書末尾で開いたまま。§12.3）も扱う。

#### 再着色が起きない構造

**着色は `layout_block` の中で呼ぶ。** レイアウトキャッシュ（§3.8）の内側なので、
ブロックの `revision` が変わらない限り再着色は起きない。
DEC-211 が要求する「スクロールだけでは再着色しない」はこれで満たされる。

#### 10MB での実測（3 回）

DEC-211 は「1 ブロック 3〜7ms であり、可視範囲にコードブロックが 3 つあれば
予算を使い切る」と警告していた。**実測ではフレーム落ちしていない。**

|条件|3 回の実測|中央値|ピークメモリ|
|---|---|---|---|
|着色**なし**（§10.7 時点）|3.80 / 3.96 / 3.88|3.86ms|196MB|
|**着色あり**|2.96 / 3.07 / 3.15|**3.07ms**|**245MB**|

**CPU はむしろ下がった。** フェンス行 2 本を描かなくなったぶんが、
着色のコストを上回っている。キャッシュが効いており、スクロール中に
再着色が起きていないことの裏づけでもある。

メモリは 196MB → 245MB（+49MB）。構文定義 75 種を常駐させるためである。
目標 600MB（§20.2）に対しては余裕がある。

実行ファイルは 33.6MB → **35.8MB**（+2.2MB）。

#### 言語名の解決（DEC-211 の判断の訂正）

技術選定書 DEC-211 は「**構文定義 75 種が最初から入るので、社内文書に現れる
言語を個別に手当てする必要がない**」と判断していた。**これは成り立たない。**

既定の構文集合に**入っていなかったもの**（実測）。

|言語名|結果|
|---|---|
|`powershell` / `ps1`|**無し**|
|`toml`|**無し**|
|`typescript` / `ts`|**無し**|
|`shell`|無し（`sh` / `bash` はある）|

`powershell` と `toml` はこのリポジトリの文書にも現れる。

対処として**別名の読み替え表**を置いた（`sh` / `shell` / `zsh` / `console` →
bash、`py` → python、`rs` → rust、`yml` → yaml、`c++` → cpp、`golang` → go ほか）。
大文字小文字も吸収する。`ts` は JavaScript で代用する——型注釈は素の字になるが、
無着色よりは読める。

**`text` / `txt` / `plain` / `none` は意図して着色しない。**
「解決できなかった」のと区別する。

**`powershell` と `toml` は着色しない**（DD-OPEN-12 で決着。2026-10-05）。

> **README.md で着色を確かめてはいけない。** フェンスは `powershell` `bash`
> `text` の 3 つで、色が付くのは**1 行の bash だけ**である。
> 目視で「着色が効いていない」と誤って判断した（実際に起きた）。
> 目視用の文書は [samples/p3-check.md](../samples/p3-check.md) に置いた。

### 10.10 P3 で見つけた不具合: ホイールの端数（2026-09-20）

**高解像度ホイールでゆっくり回すと 1 行も動かなかった。**

原因は、1 回ぶんの移動量を `round()` で丸めていたことである。
実測したデルタは次のとおりで、**1 ノッチが約 60 回に分割**されて届く。

|項目|実測|
|---|---|
|1 回のデルタ|`Lines { y: 0.016〜0.36 }`|
|エディタで `top` が変わらなかった回数|**375 件中 159 件（42%）**|

`y × 3.0` が 0.5 未満だと丸めて 0 になり、**端数が次回へ繰り越されない**ため
永久に動かない。ログには `top 14 -> 14` が 17 回連続していた。

対処は**端数の繰り越し**である。ウィジェットは丸めずに端数つきの行数を渡し、
アプリ層が `EditorState::scroll_carry` に貯めて、1 行たまった時点で動かす。
プレビューも 1 ノッチ = 本文 3 行ぶんに揃えた（従来は 60px 固定で不一致だった）。

#### なぜ今まで見つからなかったか

**性能計測はアンカーと `top_line` を直接動かしており、ホイールの経路を
一度も通していない。** 計測が通る経路と、利用者が操作する経路が食い違っていた。

> **試験の穴である。** 以後、入力経路の計算（端数の繰り越しなど）は
> 純関数へ切り出して単体試験する（`take_whole_lines`。試験 5 件）。
> 目視でしか確かめられないものは [samples/](../samples/) の文書に集める。

#### 調査で踏んだ手順の誤り

環境変数で診断を有効にする手順を示したが、**PowerShell では `set VAR=1` が
環境変数を設定しない**（`set` は `Set-Variable` の別名）。1 往復を無駄にした。
**この端末の既定シェルは PowerShell である**ことを前提に手順を書く。

### 10.11 P3: ワーカー基盤（2026-09-20）

図・数式・画像は 1 件あたり数百 ms〜秒単位になり得る。
**UI スレッドで描いてはいけない**（基本設計書 §4.3）。

|項目|決定|
|---|---|
|実装|標準スレッド + チャネル。**tokio は使わない**|
|ワーカー数|`available_parallelism() - 1` を 1〜4 に収める|
|結果の受け取り|毎フレーム `poll()`。**待たない**|
|終了|投入口を落とすとワーカーの `recv` が終わる|

**tokio を使わない理由**: 仕事は CPU を使う描画であり、待ちが主ではない。
非同期ランタイムの利点が無く、依存とビルド時間だけが増える。

#### 鍵は内容から作る

`EmbedKey` は **種類 + 本文のハッシュ + 量子化した幅**である。

**ブロック添字を使ってはいけない。** 編集でブロックが増減すると別の内容が
同じ鍵を取り、古い図が出る。レイアウトキャッシュ（§3.8）で同じ誤りを踏んでいる。

内容から作るので、**編集で内容が変われば鍵も変わる**。結果が遅れて届いても、
古い鍵の結果は誰も引かないだけで害がない。取り消しの仕組みが要らなくなる。

#### 埋め込みはレイアウトキャッシュに載せない

**結果が届いても鍵（`revision` と幅）は変わらない。** キャッシュに載せると
古いプレースホルダを引き続けてしまう。埋め込みは文書あたり数件なので、
毎回組み立てても安い。

#### 未確定のときも寸法を確保する（§16.5）

結果が届くまでは 240px のプレースホルダを置く。**失敗も画面に出す。**
黙って空白にすると、利用者は図を書き間違えたことに気づけない。

|状態|表示|
|---|---|
|依頼済み・未依頼|「図を描画中…」+ 240px の箱|
|届いた|実寸の箱（幅に合わせて縮小）|
|失敗|理由の文言のみ（箱は取らない）|

#### この段階での確認方法

**描画器はまだ挿していない**（`NotImplemented`）。画面に「未対応」と出れば、
**依頼 → ワーカー → 結果 → 高さ反映の往復が通った証拠**になる。
これを目視で確認した（[samples/p3-check.md](../samples/p3-check.md) §3.5）。

> **残っているもの**: `JobState::Done` のときに実際の画素を画面へ出す処理は、
> 画像を生成する次の段階（merman）と同時に入れる。いまは箱の寸法だけ確保する。

### 10.12 P3 で見つけた不具合: autolink が日本語を飲み込む（2026-09-20）

**裸の URL の後ろが、行末まですべてリンクになっていた。**

```text
Normal | 日本語の長い段落で、…や URL（
Link   | https://example.com/…/going）が幅を超えたときに、文字単位で折り返されること。
```

comrak の autolink は URL の終端を **ASCII の区切りで判定する**。
`）` `が` `。` などの全角文字は区切りとみなされず、URL の一部として飲み込まれる。
**日本語文書では裸の URL のたびに起きる。**

URL は RFC 3986 で ASCII のみと決まっている。**最初の非 ASCII 文字で打ち切り、
残りは地の文として出す。**

`[本文](url)` 形式は対象外である。本文と URL が一致しないことで、
裸の URL（autolink）と見分けられる。

> **見つけたのは目視確認の文書である。** §5 の折り返し確認用に書いた URL で
> 気づいた。この種の不具合は「記法が消えること」を見る自動試験では捕まらない。

### 10.13 P3: 図（merman + resvg）（2026-09-20）

技術選定書 DEC-207 のとおり merman で SVG を作り、resvg で画素へ落とす。

|項目|決定|
|---|---|
|HTML ラベル|サイト設定で一括無効化（§7.3）|
|書体|**merman 側と usvg 側の両方**に同梱フォントを指定する|
|寸法の上限|4,000px。gantt のような横長の図で画素がメモリを食うため|
|erDiagram|**図にせずコードブロック表示へ退避**（OPEN-210）|
|種類の振り分け|`Dispatch` で図・数式・画像を分ける|

#### 書体の解決は 2 段階で失敗する

**merman 側だけ、あるいは usvg 側だけでは足りない。**

1. merman は既定で `font-family: "trebuchet ms", verdana, arial, sans-serif` を出す。
   同梱フォント（DEC-209）に無い名前ばかりで、最後の総称名 `sans-serif` に落ちる
2. usvg の総称名の既定は "Arial" などで、**同梱フォントだけのデータベースには無い**。
   ここで字形が 1 つも引けず、**ラベルが消えて枠線だけになる**

対処は両方である。merman のサイト設定に `fontFamily` を渡し、
usvg の `fontdb` で `set_sans_serif_family` 等を同梱フォントへ向ける。

> **システムフォントを読んではいけない。** PoC は `load_system_fonts()` と
> `font_family = "Meiryo"` で通していたが、それでは漢字統合の問題（DEC-208）が
> 図の中で戻る。本文と同じ IBM Plex Sans JP を使い、
> **エディタ・プレビュー・図で字形を揃える。**

#### 種類ごとに描画器を振り分ける

**1 つの描画器に全部渡してはいけない。** 数式を merman へ渡して
「No Mermaid diagram type detected」と画面に出した（実際に踏んだ）。
`Dispatch` が種類で分け、未実装の種類は**その種類として**未対応を返す。

#### OPEN-210 の再測定（2026-09-20）

`er.htmlLabels: false` を渡しても foreignObject が残る問題は**いまも再現する**。

|図種|foreignObject|`<text>`|
|---|---|---|
|flowchart / sequence / class / state / gantt / pie|**0**|2〜16|
|**erDiagram**|**4**|**1**|

設計の暫定方針どおり、**erDiagram はコードブロック表示へ退避**させる。
壊れた図を出すより原文を見せるほうがよい。判定は `embed_source()` の 1 か所で、
merman 側が直れば数行消すだけで戻せる。

#### 測定を 2 回続けて誤った

**この節でいちばん重要な記録である。**

|誤り|内容|
|---|---|
|1 回目|ラベルの**有無**で画素を比較した。merman はラベルの文字数からノード幅を決めるため、**文字が 1 つも描かれなくても画素数が大きく変わる**。文字が消えているのに通る試験を作った|
|2 回目|**透明でない画素**を数えた。merman の SVG は `background-color: white` で全面を塗る（0.9 からはこちらで頼んでいる。§10.64）ため、常に「幅 × 高さ」になり**何も検出できない**|

正しい指標は技術選定書 §7.3 と同じ**暗い画素**である。
現在は「同じ SVG を**同梱フォントあり／なし**で描き比べ、差を字形とみなす」。
図形は両者で同じなので、差は字形の画素だけになる。

実測では図が 242 画素、`<text>` を除くと 73 画素で、**差の 169 画素が字形**である。

> **目視だけに頼ってもいけない。** 利用者から「ラベルが出ない」と指摘を受けた
> 時点で、試験は通っていた。**指標が誤っていると試験は無力である。**

#### 規模

実行ファイルは 35.8MB → **59.6MB**（merman + resvg + iced の image 機能）。

### 10.14 P3: 数式（latex-rust）（2026-09-20）

技術選定書 DEC-210 のとおり latex-rust で SVG を作り、図と同じ経路で画素へ落とす。

**図と違って外部フォントが要らない。** 出力はすべて `<path>` で `<text>` は 0 件である
（試験で担保した）。数式はアウトライン化されて出るため、画面・PDF・HTML の
どの経路でも同じ結果になる。§10.13 で苦労した書体の解決がここでは要らない。

#### OPEN-212 は解消した（再現しない）

PoC は「2 行 2 列の `pmatrix` が 1 行に潰れる疑い」としていたが、**再現しなかった**。

|式|寸法|
|---|---|
|1 行（`a = b`）|36x11|
|2 行 1 列の `pmatrix`|21x30|
|**2 行 2 列の `pmatrix`**|**39x32**|
|`aligned` 2 行|32x26|

正しく積まれている。**OPEN-212 を解消とする。**

#### OPEN-211 は latex-rust の枠内では解決できない

`\text{}` に日本語を入れられない問題は**いまも再現する**（`missing glyph for '面'`）。
推測で片づけず、逃げ道があるかを測った。

|試したこと|結果|
|---|---|
|latex-rust にフォールバックの口はあるか|**無い**。`MathFont::from_bytes` はフォントを**差し替える**もので併用できない|
|同梱の IBM Plex Sans JP を数式フォントにできるか|**できない**。`unsupported: OpenType MATH table`|

CJK のテキストフォントに MATH テーブルが無いため、数式フォントとしては使えない。
**latex-rust の枠内では解決できない。**

残る案は 3 つあり、利用者の判断で **A を採った**。

|案|内容|採否|
|---|---|---|
|**A**|数式内の日本語は非対応とし、**理由が読める形で失敗**させる|**採用**|
|B|`\text{}` の部分だけ別に描いて合成する|見送り。数式の組版と座標を自前で合わせる必要があり大きい|
|C|latex-rust を fork してフォールバック面を足す|見送り。上流追従の負担が続く|

「missing glyph for '面'」だけでは何をすればよいか分からないため、
**「数式の中では日本語を使えません。数式の外に書いてください」を添える。**

**OPEN-211 を A として解消とする。**

#### 規模

実行ファイルは 59.6MB → **61.1MB**（latex-rust + STIX Two Math）。

### 10.15 P3: 画像（2026-09-20）

基本設計書 §16.12 のとおり、**ローカルの画像だけ**を読む。

|---|---|

解析層で「画像だけの段落は行を空にする」としたところ、**外部の画像で画面が

レイアウト層が箱を置けたときだけ行を捨てる。

|ファイルが無い|パスと理由|

> **`［画像］` だけでは足りない。** 何が入るはずだったのかが分からない、と
> 利用者から指摘を受けて説明文を入れる形に改めた。

### 10.18 P4: ファイル入出力（2026-09-20）

#### 開いて保存しただけで差分を出さない

**これが入出力層の要点である。** 社内文書には BOM 付き・CRLF が普通にある。

|項目|扱い|
|---|---|
|BOM|**読み取り時に落とし、保存時に元の有無を戻す**|
|改行|**読み取り時に `\n` へ揃え、保存時に元へ戻す**|
|文字コード|**判定して開く**（基本設計書 §19.6 / §10.39）。指定して開き直せる|
|10MB 超|**開く。** 拒否せず警告して続ける（§19.3）|

本文に `\r` が混ざると桁数と検索がずれるため、編集中は必ず `\n` で揃える。
保存時は `\r\n` を一度 `\n` へ畳んでから置き換える（`\r\r\n` を作らないため）。

LF / CRLF / BOM+LF / BOM+CRLF の 4 通りで往復し、**バイト列が一致すること**を
試験した。

#### 確認ダイアログはアプリ内に描く

最初 OS のメッセージダイアログ（`rfd::MessageDialog`）を使ったところ、
**確認が出ないままウィンドウが固まった。** 親ウィンドウを渡していないため
モーダルが背面に出て、本体が答えを待つ状態になっていたと見られる。

基本設計書 §12 は「ツールバー・ステータスバー・**ダイアログ**・分割バー・
メニューは自前描画」としており、**設計を読み違えていた。**

自前描画のほうが設計に沿っており、副次的な利点もある。

- OS の 2 ボタン制約を受けず、**3 択**（保存 / 破棄 / 中止）をそのまま出せる
- 確認中は本文を覆うので、**答えるまで編集できない**
- 文言を日本語で統一できる

**ファイル選択だけは OS のものを使う。** 自前で描くと入力補完やネットワークの
場所など、利用者が慣れた機能を全部作り直すことになる。

#### 設定は壊れていても起動する

**1 行でも壊れていたら、その項目だけ既定値にする。** 全体を捨てると、
設定の一部が壊れただけで全部が戻ってしまう。範囲外の値（`zoom = 99.0` など）も
採らない。外部クレートは使わない——読むのは平らな 7 項目だけである。

保存は**変更から 1 秒のデバウンス**（§13.5）。ズームやパネル幅は連続して変わる。

#### 残る制限

|項目|状態|
|---|---|
|OS のテーマ変更の即時反映|**しない。** iced は OS のテーマを内部で追うが、アプリへ渡す口が公開されていない。基本設計書 §10.4 の「検知できない環境では次回起動時に反映する」に寄せた|
|分割幅のつまみ|**未実装。** 設定の比率は使うが、ドラッグで変えられない（§23.1 の「幅を変更でき」が未達）|

### 10.19 P4: 目次・つまみ・スクロール同期（2026-09-20）

#### 目次は「作らない」判断を持つ

目次は `app::toc` が作る。**閉じている間は作り直さない。**
10MB の文書では見出しの走査が全ブロックに及ぶため、見えていないものに
1 打鍵ぶんの時間を使わない。開いた瞬間と、開いている間の編集でだけ作る。

上限は 2,000 件。**青天井にしない**のは、見出しが数万ある文書で
目次を組み立てるだけで 1 フレームを使い切るためである。

見出しの文字からは `#` と記法（`**` / `` ` `` / `[...](...)`）を落とす。
目次に `## **重要**` と出ても読みにくい。

#### つまみは px の差分しか知らない

`render::divider` は**動かした量（px）だけを外へ渡す**。幅そのものを
持たないのは、設定へ保存するのがアプリ層の仕事だからである。

- 目次の幅は px をそのまま足す
- 分割比は px をその場の幅で割って比へ直す。そのために窓幅を
  `window::resize_events()` で追う
- **丸める範囲は設定ファイルが受け付ける範囲に合わせる**（幅 120〜800px、
  比 0.1〜0.9）。揃えないと、掴んで広げた幅が次回起動時に捨てられる

当たり判定は 6px、描くのは中央の 1px。細すぎると掴めない。

#### スクロール同期はブロック索引を介す（基本設計書 §16.14）

`app::sync` が両方向の対応づけを持つ。ブロック内の相対位置は
**ブロック内の行数に対する比**で近似する。行の高さはブロックごとに違うため
これは近似でしかないが、目的が「だいたい同じところを見る」ことなので足りる。

**§16.14 が警告するループは起きない。** 合わせる側の状態を直接書いており、
メッセージを投げ返さないためである。発火元を記録する仕組みは入れていない。

分割表示のときだけ効かせる。片方しか見えていないなら合わせる相手がいない。

### 10.20 P4: 検索（2026-09-20）

#### 走査はロープの塊をたどる

`search::find_all` はロープの塊（chunk）を順にたどる。**全文を 1 本の文字列へ
起こさない。** 10MB の文書でそれをすると、1 打鍵ごとに 10MB を確保することになる。

塊の境目にまたがる一致は、前の塊の末尾（`needle` より 1 バイト短いぶん）を
持ち越して拾う。持ち越しを外すと境目の一致を落とすことは試験で確かめてある
（外した状態で `matches_across_chunk_boundaries_are_found` が落ちる）。

**大文字小文字は ASCII の範囲だけ無視する。** 日本語に大小は無く、Unicode の
畳み込み（`to_lowercase`）はバイト長が変わりうるので、見つけた位置を原文の
バイト位置として返せなくなる。

一致は 2,000 件で打ち切る。10MB の文書で `の` を引くと数十万件になり、
一覧を作るだけで画面が止まる。打ち切ったことは件数の `+`（`1/2000+`）で示す。

#### 走査はワーカーで行う（基本設計書 §15.5）

打鍵のたびに UI の糸で 10MB を舐めると入力が止まる。別の糸へ投げ、
結果は `oneshot` で受けてメッセージにする。**ロープの複製は木を共有する**ので、
糸へ渡すために 10MB を写すことにはならない。

打鍵ごとに投げるため結果の追い越しが起きる。**世代番号を持たせ、古い結果は
捨てる。** これが無いと、遅れて届いた前の語の結果が新しい結果を上書きする。

#### キーは購読で受け、エディタの受け口を閉じる

エディタ（`render::editor`）は焦点の概念を持たない。**だから「まだ誰にも
捕まっていない打鍵」だけを扱う**（§10.40）。焦点のある入力欄は自分が扱う
打鍵を捕まえるので、これだけで検索語が文書へ入ることはない。

**当初は「検索バーを出している間は `accept_keys(false)`」としていたが、
これは誤りだった。** 出している間ずっと本文を編集できなくなるうえ、
出来事を捕まえた相手を見ていないので取りこぼす（§10.40）。

`Esc` は焦点のある入力欄が捕まえてしまうため、捕まった出来事も見える
`event::listen_with` で受けるのは `Esc` だけである（§10.40）。`Enter` は
入力欄に受け取らせる（`on_submit`）。**検索バーを出している間だけ**割り当てる。

#### プレビューの強調は表示文字を探す（DD-OPEN-10 の決着）

件数と移動は原文基準、プレビューの強調は表示文字基準とした。残る制限は次のとおり。

|制限|理由|
|---|---|
|ラン（同じ体裁の連なり）をまたぐ一致は強調しない|体裁の境目に語が跨がるのは稀で、またぐ判定を入れると描画のたびに連結が要る|
|記法そのもの（`**` など）への一致は強調しない|プレビューに記法は表示されていない|
|現在位置の別色がプレビューには無い|どの表示上の一致が原文の何件目かを決めるには、結局は対応表が要る|

エディタ側は原文のバイト範囲をそのまま使えるため、一致の強調と現在位置の
別色（橙）の両方を出す。

### 10.21 P4: エディタの横方向（2026-09-20）

#### 自分の領域の外へ描いていた（不具合）

折り返さない（DD-01）ため、長い行は右へ伸び続ける。**切り抜いていなかったため、
分割表示で長い行がプレビューの上に描かれていた。**

直し方は層を 2 つに分けること。

|層|切り抜く範囲|理由|
|---|---|---|
|行番号|ウィジェットの矩形|**本文が横へ動いても行番号は動かない**|
|本文・検索の強調・キャレット|行番号の欄を除いた矩形|横へ送ったとき、文字が行番号の上に乗らない|

文字を描くときに渡していた切り抜き範囲が**可視領域全体**だった点が原因である。
ウィジェットの矩形と取り違えると、ちょうど隣へ描き込む形になる。

#### 横スクロール（DD-01 の緩和策）

|操作|動き|
|---|---|
|`Shift` + ホイール|横へ送る（1 ノッチ = 3 行ぶんの px）|
|水平ホイール（チルト）|横へ送る|
|打鍵・カーソル移動|キャレットが見えるところまで自動で寄る|

**上限は可視行のうち最も長い行に合わせる。** 文書全体で決めると 10MB の
全行を測ることになる。上限が可視範囲で変わるが、読むのに困らない。

送る量の受け渡しは縦と同じく**差分**にした。絶対値にすると、高解像度ホイールが
1 フレームに何度も送ってきたときに最後の 1 回しか残らない（ウィジェットが見ている
位置はそのフレームのぶんで止まっているため）。**キャレット追従だけは絶対値**で、
何度届いても同じ結果になるようにしてある。

#### 長い行の印

右端に**右向きの三角**（▶）を出す。幅 4px の帯も試したが、
「そういう意味の印」だと伝わらなかったため三角に改めた（2026-09-20 の確認）。

**字形には頼らない。** `▶` を文字として描くと、同梱フォントにその字が
無かったときに豆腐（□）になる。横 1px の帯を左端を揃えて積み、
中心を最も長くすることで形を作る。

**ほとんどの行は測らずに判定する。** 等幅フォントでは
1 文字の幅が全角ぶんを超えないので、文字数から上限が出る。可視行すべてを
毎フレーム整形すると、印を出すためだけにレイアウトを 1 往復増やすことになる。

### 10.22 P5: ページ分割（2026-09-20）

§5 の規則を `paginate` に実装した。**描画も PDF も知らない層**とし、
入るのは「各ブロックが何行あり、各行が何 pt か」、出るのは「どのページの
どこへ何行目から何行目を置くか」だけにしてある。用紙を 1 枚も作らずに
規則を試験できる。

|規則|出典|試験|
|---|---|---|
|行単位の分割|§5.3|`a_long_paragraph_is_split_by_lines`|
|表のヘッダー繰り返し|§5.3|`a_table_repeats_its_header`|
|見出しの直後で改ページしない|§5.4 の 1|`a_heading_is_not_left_alone_at_the_bottom`|
|孤立行の禁止（前後）|§5.4 の 2・3|`a_single_last_line_is_not_sent_alone` ほか|
|3 行未満は対象外|§5.4|`short_blocks_are_exempt_from_the_widow_rules`|
|明示的な改ページ|§5.5|`an_explicit_page_break_starts_a_new_page`|
|収まらない図の縮小|§5.3|`an_oversized_figure_is_scaled_down`|

**規則を外すと落ちることを確かめてある。** 孤立行と見出しの 2 つを無効化すると
上表の 3 件が落ちる。通るだけの試験になっていないかは、毎回この手順で見る
（§10.13 で 3 度続けて取り違えたため、手順として残す）。

仕様に無い判断を 2 つ入れた。

|判断|理由|
|---|---|
|**白紙のページを作らない**|連続した `<!-- pagebreak -->` や文書先頭の改ページで白紙が並ぶ|
|**1 ページより高い行も、そのページへ置く**|置かずに送ると同じ判断を繰り返して終わらない|

### 10.23 P5: PDF 出力の骨格（2026-09-20）

krilla 0.8（DEC-205）で PDF を書き出す。**画面と同じレイアウトエンジンを
使う**（基本設計書 §17.3）ため、用紙幅（483pt）でレイアウトし直し、
その結果をページ分割（§5）へ渡し、置き場所が決まったものを krilla へ渡す。

|要素|状態|
|---|---|
|本文・見出し・リスト・引用・表・コード|**入った**|
|ヘッダー（題名）・フッター（`- n / 総数 -`）|**入った**|
|しおり（H1〜H6 の階層）|**入った**。v1 と違い全 OS で出る|
|フォントの埋め込み|**入った**（同梱の 3 本。サブセット化は krilla が行う）|
|図・数式・画像|**入った**（§10.24）|
|1 ページ目の題名と目次|**入った**（§10.24）|
|出力範囲の指定（§5.6 / SCR-005）|**入った**（§10.27）|
|出力の取り消し（§17.10）|**入った**（§10.26）|

#### 測定器は画面と同じものを使う

`render::PdfMeasurer` は画面の測定器（`IcedMeasurer`）に用紙の文字寸法を
渡しただけのものである。**別に作らない。** 別々に測ると、同じ文書でも
画面と PDF で折り返しが変わる。

窓が無くても測れるのは、測定に要るのが「どの整形器を使うか」という型だけで、
描画器そのものは要らないためである。

#### 基準線の置き方

krilla は文字の基準線（baseline）で位置を受ける。行の箱は文字の 1.6 倍
あるので、**箱の中で文字が中央に来るように**下げる。上端から文字の高さぶん
だけ下げると、行間が下に偏る。

#### 等幅の太字は埋め込まない

コードの中で太字になる書き方が無い（着色は色で表し、`**` はコードブロックの
中では記法にならない）。**使わないフォントを埋め込むと、その分だけ PDF が太る。**

### 10.24 P5: 題名・目次・埋め込み（2026-09-20）

#### 題名と目次は本文と同じ形にして作る

`export::front` は題名も目次も `LaidOutBlock`（本文と同じレイアウト結果）
として組み立てる。**専用の経路を作らない。** 作ると、ページを跨いだときの
規則（§5.4 の引き離し禁止など）が二重になる。

|項目|決まり|出典|
|---|---|---|
|題名|H1 見出し、無ければファイル名|§17.5|
|目次の対象|**H1〜H3**|§17.6|
|しおりの対象|**H1〜H6**|§17.6|
|目次の上限|500 件。超えたら「（以下省略）」|仕様に無い判断|

**目次の H1 は本文からも消さない。** 題名として 1 ページ目に出したうえで、
本文にもそのまま残す。黙って中身を削るほうが分かりにくい。

#### ページ番号は 2 回の割り付けで決める

目次にページ番号を入れるには、先に本文が何ページ目に来るかを知る必要がある。

```text
1 回目: 番号なしの目次 + 本文 → 見出しのページが決まる
2 回目: 番号入りの目次 + 本文 → これを出力する
```

**1 見出し 1 行と決めてある**ので、番号を入れても行数は変わらず、2 回目で
配置は動かない（`page_numbers_do_not_change_the_line_count` で押さえている）。
**本文のレイアウトはやり直さない。** 10MB では最も重い処理であり、
2 回走らせると出力時間が倍になる。

前付けのぶんだけブロックの添字がずれる。取り違えると目次が別の見出しの
ページを指すため、`toc_numbers_come_from_the_body_pages` で押さえている
（ずらしを外すと落ちることを確認済み）。

#### 埋め込みは出力の前に全部描く

画面は「描けたものから出す」ためワーカーへ投げるが、**出力は全部が
揃っていないと大きさが決まらず、ページへ割り付けられない。** そのため
出力の入口で順に描き、同じ鍵（内容 + 幅）のものは 1 度だけ描く。

#### PDF の中身を試験で見るときの注意

`/Image` を目印にすると**どの PDF でも当たる**。ProcSet の `/ImageB`
`/ImageC` が常に入っているためである（実際に踏んだ）。`/Subtype/Image` まで
見ること。あわせて、**画像を含まない文書と対で確かめる**——片方だけでは、
目印が常に出ているのか画像のおかげで出ているのかが分からない。

### 10.25 P5: 出力先を知らせる（2026-09-20）

出力したあとの知らせに、**そのファイルへのリンク**を付けた（利用者の要望）。
出力して終わりではなく、たいていは中身を確かめたいためである。

- パスが長いときは**真ん中を省く**（`…`）。窓の幅を押し広げないため
- 省くときは**末尾を多めに残す**。パスはファイル名のほうが手がかりになる。
  ただし先頭も残す（どのドライブかが消えると分からなくなる）
- 開くのは OS の既定のアプリ（`io::launch`）。**自前で開かない。**
  どのアプリで見るかは利用者の設定であり、アプリが決めることではない
- 基本設計書 §8.2 の「`http` / `https` は OS の既定ブラウザーで開く」も
  同じ口を使う

`io::launch` は**コマンドの組み立てと実行を分けてある**。実行まで一体にすると、
試験のたびにアプリが立ち上がる。

### 10.26 P5: 出力の進捗と取り消し（2026-09-20）

出力を**別の糸**へ移した（基本設計書 §17.10）。UI は操作できたまま、
「x / y ページ（経過秒）」を出し、取り消せる。

#### 文書はその時点のものを写して渡す

借りたまま渡すと、出力が終わるまで編集できなくなる。`Document` を複製して
渡すが、**ロープは木を共有する**ので 10MB の本文が複写されるわけではない。

これにより、出力中に本文を編集しても出力結果は変わらない（押した時点の姿が出る）。
編集した結果が欲しければもう一度出力する、という約束にした。

#### 進み具合は原子変数で渡す

1 ページごとにメッセージを投げると、9,400 ページの文書では画面の更新が
それだけで埋まる。**原子変数へ書き、画面は既にある 500ms の刻みで読む。**

#### 取り消しは「印を立てる」だけ

押した側は `AtomicBool` を立てるだけで、止めるのは出力側である。
**見る場所は 2 か所。**

|場所|間隔|理由|
|---|---|---|
|レイアウト|256 ブロックごと|10MB では割り付けより前が長い|
|ページの書き出し|1 ページごと|ここが本体|

**書き出すのは最後だけ。** 途中でファイルへ書くと、取り消したときに
書きかけが残る（§17.10 の「書きかけのファイルは残さない」）。

#### 試験

|確かめること|試験|
|---|---|
|取り消すと何も作らない|`a_cancelled_export_stops`|
|ページごとに知らせる|`progress_is_reported_for_every_page`|

進捗の試験では、**知らせた総ページ数と実際に出た `/Type /Page` の数を突き合わせる。**
知らせだけを数えると、知らせが間違っていても気づけない。

### 10.27 P5: 出力範囲の指定（2026-09-20）

PDF ボタンで**いきなり出さず**、範囲を選ばせる（SCR-005 / §17.11）。
10MB の文書は約 9,400 ページになるためである。

|範囲|決め方|
|---|---|
|文書全体|既定|
|見出しを選ぶ|目次から選び、**その配下も含める**（同じか浅い見出しの手前まで）|
|ページを指定|開始ページ（1 始まり）と枚数|

**推定ページ数は常に出す**（§5.6）。行走査の結果から `行数 ÷ 43` で概算する
（本文領域 730pt ÷ 行高 16.8pt）。500 ページを超えるときだけ所要時間の目安も
添える（技術選定書 §8.5 の実測から 1 ページ 2ms）。

#### 切る場所を分ける

|範囲|切る場所|理由|
|---|---|---|
|見出し単位|**レイアウトの前**|要らないブロックを測らない（10MB では測るのが最も重い）|
|ページ指定|**割り付けの後**|ページ番号は割り付けないと決まらない|

ページ指定で出したとき、**フッターの番号は文書全体のまま**にしてある
（`- 12 / 340 -`）。抜き出した紙と元の文書の対応が取れるようにするためである。

#### 入力は倒れない

開始ページや枚数に数でない文字が入っても既定値へ倒し、0 は 1 として扱い、
文書の端を越えた指定は詰める。**出力できないより、それらしく出すほうがよい。**

### 10.28 P5: HTML 出力（2026-09-20）

comrak で全文を HTML にし、**1 ファイルで完結**させる（基本設計書 §17A）。

|項目|扱い|
|---|---|
|CSS|`<style>` に埋め込む。**Light 固定**|
|画像|`data:` にする。4MB を超えるものと外部の画像は入れず、件数で知らせる|
|図・数式|**SVG のまま**入れる。画面と PDF は画素へ落とすが、ブラウザは描けるので落とさない|
|生 HTML|**原文をそのまま出す**（§16.1）。`render.escape` を立てる|
|外部参照|持たない（試験で `http` / `<link` / `<script` が無いことを見る）|

#### 目印を置いてから差し替える

図・数式・画像を入れるには生の HTML を混ぜる必要があるが、comrak に生 HTML を
通させると**利用者が書いた HTML まで出てしまう**（§16.1 に反する）。

そこで、木の中でそれらの節点を**目印だけの段落**に置き換え、HTML にしたあとで
目印を差し替える。目印は ASCII なので escape の影響を受けない。

**木を走査しながら変えない。** comrak は走査中の変更を検出して止める
（`tree modified during iteration`。実際に踏んだ）。先に節点を集めてから変える。

#### フォントは名前だけ明示する

§17A.2 の表のとおり `font-family` に同梱フォント名を書く。**ファイルは埋めない。**
埋めると 1 ファイルが 21MB 増え、配布物として成り立たない。同じ節の見出し文
（「CSS・画像・フォントを埋め込んだ単一の HTML」）とは食い違うが、表の指定を採った。

#### HTML は範囲を取らない

ページという単位が無く、1 ファイルで完結させるのが目的であるため、
出力ダイアログでは範囲を出さない（§17A.2）。

#### Base64 は自前で持つ

`data:` のために base64 が要るが、**依存を 1 つ増やすほどのものではない**
（20 行ほど）。RFC 4648 の例（`f` / `fo` / `foo` …）で詰めまで確かめている。

### 10.29 不具合: ダイアログが背面へ回る（2026-09-20）

**症状**: PDF を既存のファイルへ上書き出力しようとすると、上書きの確認が
出ないまま窓が固まったように見える（利用者の報告）。

**原因**: rfd に親ウィンドウを渡していなかった。rfd は Windows で
`IFileDialog::Show(parent.unwrap_or(null))` を呼ぶ。親が `null` だと
2 つのことが同時に起きる。

1. ダイアログがアプリの窓に所有されず、主窓を触ると**背面へ回る**。
   上書きの確認はダイアログの子なので、これも一緒に隠れる
2. 呼び出しは同期で UI の糸を塞ぐため、主窓は再描画も応答もできない

結果として「確認が出ないまま固まった」ように見える。実際には背面で
応答を待っている。**同じことを §10.18 の未保存確認でも踏んでいる**
（あちらは自前描画に切り替えた）。ファイル選択は OS のものを使うと
決めている（基本設計書 §14.1）ので、こちらは親を渡す。

**直し方**: `app::picker::Picker` を置き、**表示には親を引数で要求する**。

```rust
pub fn show(self, parent: &dyn iced::window::Window) -> Option<PathBuf>
```

親無しで出す道が型として無いので、同じ間違いを繰り返せない。
rfd を直に呼ぶのは `picker.rs` の 1 か所だけにしてある。

**副作用**: 窓の取っ手は iced の `Task` 越しにしか取れないため、
ダイアログは同期で呼べなくなった。選んだ結果はメッセージで戻る。
これに伴い、未保存確認からの「保存して続ける」を 2 段に分けた。

|段|すること|
|---|---|
|1|保存先を聞く（保留していた操作は持ったまま待つ）|
|2|書けたら保留していた操作を進める。**取り消し・失敗なら進めない**|

### 10.30 不具合: ページ指定の出力と erDiagram（2026-09-20）

利用者の報告 2 件。いずれも**同じ判断を 2 か所に書いた**ことが原因である。

#### ページ指定で出力すると「中断されました」

**症状**: 見出しのある文書でページを指定して出力すると、ファイルができず
「出力が中断されました」と出る。

**原因**: しおりの飛び先に**文書全体での番号**を渡していた。ページ指定では
出力した PDF が 1 枚でも、飛び先は「2 ページ目」を指すことになる。
krilla はこれを検出して落ちる。

```text
attempted to link to page 2, but document only has 1 pages
```

ワーカーの糸が落ちたので、結果を返す口が閉じ、アプリ側には
「中断されました」とだけ見えていた。**落ちた理由が画面に出ない**点は
§10.32 で直した。

**直し方**: 飛び先は**出力した PDF の中での位置**（`offset`）で数える。
フッターの番号は文書全体のまま（`number + 1`）で変えない。
抜き出した紙と元の文書の対応が取れるという §10.27 の狙いは保つ。

#### HTML だけ erDiagram が図になる

**症状**: erDiagram は図にせず原文を出すのが正しい（OPEN-210）が、
HTML 出力だけ図になり、ラベルが欠けていた。

**原因**: 「描けない図かどうか」の判断を、レイアウト層（`embed_source`）と
HTML 出力の 2 か所に書いていた。HTML 側は言語名が `mermaid` かどうかしか
見ていなかった。

**直し方**: 判断を `embed::diagram::is_supported` の 1 か所へ集め、
画面・PDF・HTML がそれを見る。

#### 学び

**同じ判断を 2 か所に書かない。** どちらも「片方だけ直す／片方だけ知らない」
形で表に出た。番号の基準（文書全体か、出力の中か）と、図を描くかどうかは、
いずれも 1 か所で決めて配る。

### 10.31 不具合: ダイアログが背面へ回る（続き。2026-09-20）

§10.29 で親ウィンドウを渡すようにしたが、**Markdown の上書き保存では
まだ背面へ回る**という報告を受けた。

#### 親は渡っていた

rfd の同期経路（`win_cid`）は `IDialog(dialog, parent)` に親を持ち、
`show()` で `Show(self.1)` へ渡している。PDF の出力先と Markdown の保存先は
同じ `app::picker` を通るので、**片方だけ親が抜けることはない。**

#### 残っていたのは「UI の糸が止まること」

同期版のダイアログは呼び出した糸を塞ぐ。その間、主窓は
**メッセージを処理しない = 応答しない窓**になる。Windows は応答しない窓の
代わりに**ゴースト窓**（「応答なし」と題名に付く複製）を前面へ出す。
ゴーストはダイアログの所有関係の外にあるため、**ダイアログを覆える。**

数秒でそうなるので、「出ることもあれば出ないこともある」という
断続的な見え方になる。§10.29 の親渡しは必要だが、**それだけでは足りない。**

#### 直し方: 出すのは別の糸

`rfd::AsyncFileDialog` を使う。Windows では専用の糸で自前のメッセージ
ループを回すため、**主窓は止まらない**（ゴーストが出ない）。
親は同じように渡すので、所有関係でダイアログは前面に留まる。

|やること|場所|
|---|---|
|窓の取っ手を借りる|主の糸（`window::run`）|
|ダイアログを出す|rfd が作る別の糸|
|結果を受け取る|`Task::future` → メッセージ|

**副作用**: 主窓が生きているので、選んでいる最中にもう一度ボタンを押せる。
`picking` の間はファイル操作の口を閉じて、2 つ開けないようにした。

#### 確認（2026-09-20）

`.md` と `.pdf` の双方で、**ダイアログを 10 秒ほど放置してから**操作して
確認した。前面に留まる。ゴースト窓が原因という見立てで合っていた。

主窓は**再描画される**（キャレットが点滅する）が、**利用者の操作は受け付けない**。
これは共通ダイアログが所有者の窓を無効化するためで、**意図どおり**である。
別の糸で出しても「主窓を触れてしまう」ことにはならない。

したがって `picking` の口閉じは OS の無効化と二重になるが、そのまま残す。
**OS の挙動に頼り切らない**ためで、無効化されない環境でも 2 つ開かない。

### 10.32 ワーカーが落ちた理由を画面に出す（2026-09-20）

§10.30 で困ったところの手当て。糸が落ちると**結果を返す口（チャネル）が
閉じるだけ**で、呼び出し側には「途中で終わった」ことしか分からない。

```text
krilla が落ちる → 出力の糸が死ぬ → 送り口が閉じる
  → 画面には「出力が中断されました」とだけ出る
```

実際の理由（`attempted to link to page 2, but document only has 1 pages`）は
試験で再現させるまで分からなかった。**理由はその場で拾って、そのまま人へ渡す。**

`worker::catch` を置き、3 か所を包んだ。

|場所|落ちたときの見え方|
|---|---|
|出力（PDF / HTML）|「出力が異常終了しました: 〜」を知らせに出す|
|検索|「検索が異常終了しました: 〜」を知らせに出し、件数は 0 にする|
|図・数式・画像|「描画に失敗: 図の描画が異常終了しました: 〜」をその場に出す|

#### 図の糸は殺さない

プールの糸は `loop` で仕事を取り続ける。1 件の落下で糸が死ぬと、**以後その分だけ
プールが痩せ**、図が「いつまでも描かれない」状態になる。包んで生かし続ける。
`a_panicking_render_reports_and_keeps_the_worker` で、
**理由が届くこと**と**同じ糸で次が描けること**の両方を見ている
（包みを外すと落ちることを確認済み）。

#### `AssertUnwindSafe` を使う理由

包む相手はどれも「落ちたらその結果を捨てる」ものだけである。落ちた後に触る
状態が無いので、途中まで書き換わった値を後から読む心配がない。

### 10.36 正式版: 取り消し・置換（2026-09-30）

#### 取り消し（A-1 の一部）

`document::history` を配線した。編集は**文書へ当てるのと同時に履歴へ積む**。

- 置換は**1 件としてまとめて積む**。`すべて置換` を 1 回で戻せる
- 文書を差し替えたら履歴を捨てる（別の文書の取り消しは当たらない）
- 選択と切り取り・貼り付けは §10.37 で入れた

#### 置換

`search::pattern` が探し方（そのままの文字／正規表現、大文字小文字）を、
`search::replace` が「どこを何に置き換えるか」を決める。**どちらも文書を
触らない**ので、窓無しで試験できる。

**後ろから当てる。** 前から当てると、1 件目で長さが変わって 2 件目以降の
位置がずれる（§4.7 の矩形編集と同じ理由）。並びが後ろからであること自体を
試験で見ている。

#### 不具合の追跡を誤った記録

`cargo test` が `0xc0000409`（`STATUS_STACK_BUFFER_OVERRUN`）で落ちた。

|試したこと|結果|
|---|---|
|`RUST_MIN_STACK` を 32MB / 128MB へ|**直らない**|
|`view()` を関数へ割る|**直らない**|
|**`cargo clean -p mdview`**（当時の名前は `markdown-viewer`）|**直った**|

**原因は、中断されたビルドが残した自クレートの中間成果物である。**
最初のクラッシュは、リリースビルドと別の `CARGO_TARGET_DIR` のビルドを
**同時に走らせた**ために起きた。

一度 `RUST_MIN_STACK` を入れて「直った」と判断したが、**そのときの成功は
たまたま作り直しが走っただけ**だった。入れた設定は取り消してある。

|学び|
|---|
|**ビルドを並行させない。** 依存の再構築が競合し、成果物が壊れる|
|**パイプを通すと終了コードがすり替わる。** `\| tail` の後ろの状態は `tail` のもの|
|rustc が理由なく落ちたら、まず `cargo clean -p <クレート>` を試す|

### 10.37 正式版: 選択とクリップボード（2026-09-30）

#### 選択（§4.4 / §4.6）

掴んだところ（`anchor`）といまの位置の 2 点で持つ。**どちらが前かは決めない**
——後ろから前へ引くこともあるため、範囲が要るときに並べ替える。

|選び方|入口|
|---|---|
|ドラッグ|押下で掴み、移動で伸ばし、離して確定|
|`Shift` + 移動|掴んでいなければ、その場で掴んでから動かす|
|ダブルクリック|語（§4.6 の文字種境界）|
|3 回クリック|行（**次の行頭まで**。改行を含めないと消しても空行が残る）|

**連続した押下は 400ms 以内を同じ組と数え、3 回で 1 に戻す。**
4 回目が「語」に戻らないと、行を選び直せない。

描画は**本文の層でだけ塗る**。行番号の桁と同じ層で塗ると、
桁の上まではみ出す（§10.19 で踏んだのと同じ形）。

#### 切り取り・コピー・貼り付け

- **選んでいなければ何もしない。** TeraPad は選択が無いと行をまるごと写すが、
  意図しない貼り付けは取り消しでも気づきにくいため採らない
- 切り取りは**写してから消す**。順を逆にすると写す元が無い
- 貼り付けの改行は **LF へそろえる**。他のアプリからは CRLF で来るため、
  そのまま入れると行末が混ざった文書になる（基本設計書 §3.2）
- **`\r` を含まないときは複製しない。** 10MB を貼るたびに写すのは無駄

貼り付けは選択があればそれを置き換える。入力と同じ道を通るので、
**1 回の取り消しで元へ戻る**。

### 10.38 不具合: 「すべて置換」で強制終了（2026-09-30）

```
panicked at src\render\editor.rs:390:
end byte index 1 is not a char boundary; it is inside 'い'
```

**原因は、編集したあとも古い一致の位置を控えたまま描いたことである。**
一致はバイト位置で持つため、置換で長さが変われば別の文字を指す。
指した先が多バイト文字の途中だと、行を切り出すところで落ちる。

「すべて置換」で出たが、**検索バーを開いたまま 1 文字打っても同じ**である。
走査し直すのは非同期のため、当てた直後の描画が古い位置を見る。

|決めたこと|理由|
|---|---|
|**文書を当てる 1 か所で捨てる**（`apply_edits`）|編集の入口は入力・後退・取り消し・置換と複数あり、それぞれで思い出すと必ずどれかを落とす|
|**走っている走査も世代を進めて無効にする**|編集前の文書を見ているので、遅れて届いた結果で同じことが起きる|
|**捨てたら、検索バーが開いているときだけ走査し直す**|`update` の出口 1 か所で見る|
|描画側でも文字境界を確かめる|描画で落ちると**編集中の文書ごと失う**ため、最後の砦として置く|

**同じ判断を 2 か所に書かない**（§10.28）の裏返しで、
**同じ後始末を 2 か所以上で思い出さない**。捨てる場所は 1 つにする。

### 10.39 正式版: 文字コードの判定と指定（2026-09-30）

基本設計書 §19.6 のとおりに入れた。判定は自前（`io::encoding`）で、
変換は `encoding_rs` に任せる。**判定を外へ出さない**のは、
外れたときに直す手立て（指定して開き直す）と対で設計するためである。

|決めたこと|理由|
|---|---|
|**判定は必ず何かを返す**|開けないより、開いてから直せるほうがよい|
|**指定は操作といっしょに運ぶ**（`SaveAs`）|状態に置くと、ダイアログを取り消したときに指定だけが残り、ステータスバーが嘘をつく|
|**表せない文字があったら保存しない**|`encoding_rs` は `&#12345;` へ逃がす。それは本文の書き換えである|
|**UTF-16 の書き出しは自前**|`encoding_rs` は仕様上 UTF-16 へ書き出せない（読むことはできる）|
|**新規だけ BOM 付き UTF-8**|既存へ当てると、開いて保存しただけで全行に差分が出る|

#### Shift_JIS と EUC-JP の見分け

辞書も統計表も持たない。**並びとして成り立つかを数える**だけである。

  1. 成り立たないバイトの少ないほう
  2. 同点なら、ひらがなに見える文字（SJIS `0x829F`〜`0x82F1` /
     EUC `0xA4xx`）の多いほう
  3. なお同点なら Shift_JIS（Windows の既定）

日本語の文書ならひらがなが最も多く出るため、2 が効く。

ページング ファイルが小さすぎるため、この操作を完了できません。

### 10.40 正式版: 検索中の焦点（2026-09-30）

検索バーを出している間、本文を編集できなかった。**探した場所を見ながら
直せないと、検索の意味が薄い**（利用者の指摘）。

原因は `accept_keys(!search.open)`、つまり**バーが開いていれば本文へ
入れない**としていたことである。正しくは「**入力欄に焦点があるとき**だけ
入れない」。

|決めたこと|理由|
|---|---|
|**焦点はアプリが持つ**（`search_focused`）|iced の焦点だけに任せると、本文を触っても入力欄が焦点を持ったままになり、打鍵が両方へ届く|
|本文を触ったら `unfocus()` する|自前の印と iced の焦点を**同時に**動かす。片方だけでは、どちらへ行くか分からなくなる|
|**巻き上げでは焦点を移さない**|読みながら検索語を直すことがある|
|バー全体を `mouse_area` で受ける|「次へ」を押してから打ち直すため、入力欄だけでは足りない|
|`Enter` の宛先は受け取ってから決める|`listen_with` は**捕まえない関数**しか取れず、購読の中で焦点を見られない|

#### 入力欄が受け取った打鍵は本文へ流さない

検索欄・置換欄へ打った文字や `BackSpace`・`Enter` が、**本文にも入る**
ことがあった（利用者の指摘）。

原因は、焦点の印（`search_focused`）を**押された出来事から立てていた**
ことである。入力欄やボタンが押下を先に捕まえると、その上に重ねた
`mouse_area` まで届かず、印が立たないまま入力欄だけが焦点を持つ。
本文はそれを知らないので、同じ打鍵を二重に処理していた。

|決めたこと|理由|
|---|---|
|**本文は「捕まっていない打鍵」だけを扱う**（`shell.is_event_captured()`）|焦点を持つ入力欄は自分が扱う打鍵を捕まえる。押下を数えるより確実|
|`Enter` は**入力欄に受け取らせる**（`on_submit`）|購読で拾うと、本文へ焦点があるときの改行と取り合いになる。検索欄は次の一致へ、置換欄は 1 件置換|
|`Shift + Enter`（前の一致へ）は**修飾キーを別に覚えて**実現する|`on_submit` は修飾キーを運ばない。`ModifiersChanged` を購読して覚えておき、受け取ってから前後を決める|
|入力が来たら焦点の印も立てる|本文を inert にして、取りこぼしを二重に防ぐ|

**印は近道であって、根拠ではない。** 根拠は「誰がその出来事を捕まえたか」
に置く。

#### キャレットを動かす操作は選択を解く

検索欄で `Enter` を押すと、**もと居た場所から一致までが選ばれて見えた**
（利用者の指摘）。

原因は、キャレットだけを動かす処理が**掴んだところ（`anchor`）を
そのままにしていた**ことである。本文を一度クリックすると、1 px でも
動けばドラッグとして掴みが立つ。幅 0 なので何も見えないが、
そのあとキャレットが飛ぶと、そこまでが選択として描かれる。

**規則を 1 つにし、`EditorState` の 2 つのメソッドに閉じ込めた。**

|メソッド|掴んだところ|使うところ|
|---|---|---|
|`place_caret`|**解く**|検索で飛ぶ・取り消す・行へ飛ぶ・目次から飛ぶ・括弧へ飛ぶ・入力後・後退後|
|`extend_caret`|**保つ**|`Shift` + 移動・ドラッグ・語選択・行選択・矩形|

**選びたいときは、動かしたあとで掴み直す。** 逆順にすると
`place_caret` が解いてしまう（「すべて選択」と「変換後の選択」が該当）。

同じ取りこぼしが**目次から飛ぶ経路にもあった**。1 か所に寄せたことで
両方まとめて直っている。

#### 閉じて開き直したら走査し直す

検索バーを閉じて開き直すと、**語が入っているのに「見つかりません」**と
出た（利用者の指摘）。

閉じるときに一致を捨てている（強調が残ると何が選ばれているか分からない）
のに、**開くときに走査し直していなかった**。語は次に開いたとき打ち直さずに
済むよう残しているので、捨てたものは開くときに取り戻す必要がある。

**捨てる側と取り戻す側は対で書く。** 片方だけ足すと、この形の抜けが出る。

|状態|閉じるとき|開くとき|
|---|---|---|
|語・置換後の語・正規表現/大小の指定|**残す**|そのまま使う|
|一致・現在位置|**捨てる**|**走査し直す**（`needs_rescan`）|

開き直したときは**1 件目へ飛ぶ**。語が残っているとはいえ、利用者が
「検索を実行した」場面であり、結果を見せないほうが不親切である。

#### 編集で走査し直すときは飛ばない

本文で `Enter` を押すと、改行の直後ではなく**一致の場所へキャレットが
飛んだ**（利用者の指摘）。

編集すると一致が古くなるので走査し直す（§10.38）が、その結果が届いた
ときに「1 件目へ飛ぶ」処理まで一緒に走っていた。**飛ぶかどうかを走査に
持たせ**、編集で走査し直すときは飛ばないようにした。

ただし**「置換」だけは明示の操作なので、走査のあと次の一致へ移る**。
置換のあとに動かないと、どこを直したのか・次はどこかが分からない。
`stale`（走り直す）と `jump_after`（飛ぶ）を別の印として持ち、
出口で両方を見る。

あわせて、**置換のあとの走査し直しも `update` の出口 1 か所に寄せた**。
置換の中でも呼んでいたため二重に走り、どちらの結果が残るかで挙動が
変わっていた（§10.38 の「後始末は 1 か所」と同じ）。

### 10.42 正式版: 表せない文字の場所を出す（2026-09-30）

「Shift_JIS で表せない文字があります」だけでは、**10MB の文書から探せない**
（利用者の指摘）。行・桁・文字を添えるようにした。

```
Shift_JIS で表せない文字があります: 2 行 6 桁 '🙂'、14 行 3 桁 '𠮷' ほか
```

|決めたこと|理由|
|---|---|
|**書けないと分かってから探す**|毎回 1 文字ずつ試すと、10MB の保存が桁違いに遅くなる|
|**ASCII は飛ばす**|扱うどの文字コードでもそのまま書ける。ほとんどが ASCII の文書ではこれで大半を省ける|
|**先頭 5 件で打ち切る**|全部数えても、直すのは結局 1 つずつである|
|桁は**文字単位**|画面の桁表示（§7.4）と揃える|

### 10.43 正式版: TeraPad 由来の編集機能（2026-09-30）

v1 の利用者が TeraPad から移ってくるため、**日常的に使う編集操作**を
取り込んだ。

|入れたもの|割り当て|効く範囲|
|---|---|---|
|すべて選択|`Ctrl + A`|—|
|行の複製 / 削除 / 連結|`Ctrl + D` / `L` / `J`|いまの行（連結は選択があればその範囲）|
|字下げ / 戻す|`Tab` / `Shift + Tab`|選んだ行|
|大文字 / 小文字|—|**選んだ範囲だけ**|
|半角 / 全角|—|**選んだ範囲だけ**|
|ひらがな / カタカナ|—|**選んだ範囲だけ**|
|タブ↔空白|—|**選んだ範囲だけ**|
|日付 / 時刻の挿入|—|キャレット位置|
|指定行へジャンプ|`Ctrl + G`|—|
|対応する括弧へ|`Ctrl + ]`|—|

#### 決めたこと

|決めたこと|理由|
|---|---|
|**変換は選んだ範囲にしか効かない**|文書全体へ効くと、押し間違いを取り消すまで気づけない。メニューも選択が無ければ押せない|
|**変換は 1 つの編集として積む**|一括変換が 1 回の取り消しで戻る（§4.7）|
|**変換のあとも選んだままにする**|続けて別の変換を掛けられる（半角へ→大文字へ、など）|
|**全角→半角でカナを触らない**|半角カナは環境によって化ける。TeraPad も別項目にしている|
|**タブ→空白はタブ止めを保つ**|一律に 4 個へ置き換えると、桁が揃わなくなる|
|**空白→タブは行頭だけ**|文中まで変えると、表の桁揃えが壊れる|
|**字下げは空行を飛ばす**|空白だけの行が残ると、見えない差分になる|
|**行の連結で空白を入れない**|日本語の文章では、改行を空白に替えると不自然な隙間になる|
|**日付は ISO 8601 に寄せる**|文書へ書くものなので、読む人の地域設定に左右されない|

#### 括弧の対応は数えるだけ

文字列もコメントも見ない。Markdown には言語ごとの規則が無く、見ようと
すると**埋め込みコードの言語ごとに別の規則が要る**。数えるだけでも、
実際の文書ではほぼ当たる。外れたときは押し直せばよい。

#### 地方時のために `chrono` を足した

`std` だけでは端末の時刻帯を取れない。既定の機能を切り、`clock` だけを
入れている。

### 10.44 正式版: タブ幅・不可視文字・怪しい文字（2026-09-30）

#### タブ幅（§4.10）

**もとの行と表示は別物になった。** タブを空白へ広げるため、
`Rendered` が「もとのバイト位置」「もとの桁」「表示の桁」を橋渡しする。

|どこ|どの桁を使うか|
|---|---|
|キャレット・選択・一致の描画|**表示の桁**（広げたあと）|
|クリックの受け口|表示の桁で当て、**もとの桁へ戻す**|
|アプリ側の `cursor_column`|**もとの桁**（変えない）|

混ぜると、タブを含む行だけキャレットと選択がずれる。試験は
「行き来して戻ること」と「タブの途中を押したらそのタブへ乗ること」を見る。

#### 不可視文字（§4.11）

**本文と同じ幅で並ぶ「印だけの行」を作り、1 回で重ねて描く。**
文字ごとに位置を測ると 1 行あたり O(n²) になる。

- 空白 `·` / タブ `»`（**全角スペースには印を置かない**。フォントが
  破線の枠として描くため。§10.50）。**どちらも半角に描かれる字**（§10.51）
- **行末は改行コードで形を変える**（2026-10-02。利用者の要望）

|改行コード|印|
|---|---|
|`CR` + `LF`|`↵`（Enter キーのような直角の矢印）|
|`LF`|`↓`（下向きの矢印）|
|最終行|**置かない**（改行が無い）|

  本文は読み取り時に `
` へ揃えてあるので、**どちらで保存されるかは
  本文から分からない。** 保存時に戻す形（`FileFormat::line_ending`）が
  唯一の答えなので、そこから決める。
- 全角の位置には**全角の空白**を置く（半角だと、その先の印がずれる）
- **幅の無い文字には何も置かない**（印は §4.12 の側で描く）
- **最終行に `¶` は置かない**（改行が無い）

#### 怪しい文字（§4.12）

Gremlins tracker（VS Code）と同じ狙いで、**見えないのに悪さをする文字**に
箱を描く。貼り付けで紛れ込んだものを、保存する前に気づけるようにする。

|拾うもの|例|
|---|---|
|幅の無い空白・制御|ZWSP / ZWNJ / ZWJ / BOM / 単語結合子 / 書字方向の制御|
|紛らわしい空白|ノーブレークスペース / 全角スペース / 欧文用の空白|
|読めなかった跡|置換文字 `U+FFFD`|

|決めたこと|理由|
|---|---|
|**普通の空白とタブは拾わない**|ここに入れると、ほとんどの行が印だらけになる。それらは §4.11 で別に扱う|
|**幅の無い文字にも読める幅の箱を描く**|幅どおりだと 0 px になり、「在ることが分かる」目的を果たさない|
|**既定で出す**|気づく前に保存させない|
|赤系の色|直すべきものだと分かるように|

#### ツールバーを外した

メニューに同じ操作が並んでおり、**二重に持つと片方だけ直して食い違う**
（利用者の要望）。§7.3 の「頻度の高いものだけ重ねて置く」は取り下げる。

### 10.45 正式版: 矩形選択（2026-09-30）

§11 で「工数が逼迫したら最初に落とす」としていたものだが、
TeraPad からの移行で要る（利用者の要望）ため入れた。

|決めたこと|理由|
|---|---|
|**行と桁で持つ**（バイト位置ではない）|バイト位置では「行をまたいで同じ桁」が表せない|
|**普通の選択とは同時に持たない**|どちらが効いているのか分からなくなる。矩形を始めたら普通の選択は捨て、普通の移動で矩形は解ける|
|**後ろの行から当てる**|前から当てると、1 行目の長さが変わって 2 行目以降の位置がずれる（§4.7 と同じ）|
|**まとめて 1 つの編集として積む**|1 回の取り消しで元へ戻る|
|**幅 0 でも選択として扱う**|桁をそろえて打ち込む使い方があり、「何も選んでいない」とすると 1 行にしか入らない|
|**幅 0 でも細い線を描く**|打ち込む位置が見えないと、どこに入るか分からない|

|操作|振る舞い|
|---|---|
|`Alt` + ドラッグ|矩形を選ぶ。**途中で `Alt` を離しても続く**|
|コピー / 切り取り|行ごとの中身を**改行でつないで**写す|
|文字を打つ / 貼り付け|**各行の同じ桁へ同じものを入れる**|
|`BackSpace`|矩形を消す|

**貼り付けは「各行へ同じものを入れる」**とした。クリップボードの行数と
矩形の行数が合ったときだけ割り振る作りも考えたが、合わないときの
振る舞いが説明しづらく、**どちらになるか押すまで分からない**ためやめた。

### 10.47 正式版: 効かないキーの洗い出し（2026-10-02）

`Delete` が効かないという指摘を受け、**鍵盤からの操作を 1 つずつ
突き合わせた**。抜けは 1 つではなかった。

|抜けていたもの|直し方|
|---|---|
|`Delete`|キャレットの右を消す。選んでいればそれを消す|
|`Ctrl + Delete` / `Ctrl + BackSpace`|語ごと消す|
|`PageUp` / `PageDown`|1 画面ぶん動く。**行数は描画側が渡す**（画面の高さを知っているのはそちらだけ）|
|`Ctrl + Home` / `Ctrl + End`|文書の先頭・末尾へ。従来は行頭・行末のままだった|
|`Ctrl + ←` / `Ctrl + →`|語の単位で動く|
|`Shift + Delete` / `Ctrl + Insert` / `Shift + Insert`|切り取り・写し・貼り付け（Windows の別名）|
|**`Alt` / `Ctrl` 付きの文字が本文へ入りうる**|入れないようにした（下記）|
|**`Ctrl` / `Alt` 付きの `Enter` が改行になる**|改行にしない|

#### `Alt + F` で `f` が本文へ入る穴

割り当て文字（§7.2）とショートカットは**購読**で見ているが、購読は
出来事を捕まえられない（`listen_with` の制約）。一方、エディタは
「捕まっていない打鍵」を本文への入力として扱う。**どちらも捕まえないので、
両方が動く。**

メニューが開けば `accept_keys(false)` になるが、それは次の描画からで、
**同じ打鍵には間に合わない。**

エディタ側で `Ctrl` / `Alt` 付きを弾くようにした。本文へ入る文字に
修飾キーは要らないので、失うものは無い。

#### 残している（直していない）もの

|もの|理由|
|---|---|
|`Insert` 単独（上書きモード）|**機能そのものが無い。** TeraPad にはあるが、入れるなら状態表示と桁の扱いを含めて別に設計する|
|`Escape` で選択を解く|`Escape` は検索バーとメニューを閉じるのに使っている。選択の解除まで兼ねると、どれが閉じるのか分からなくなる|
|変換中の `Escape`|IME に渡したいが、購読が先に拾って検索バーを閉じる。IME の取り消しは変換窓側で行える|

### 10.48 正式版: キャレットが画面を縦に追わない（2026-10-02）

`PageUp` / `PageDown` / `Ctrl + Home` / `Ctrl + End` を押すと、
**ステータスバーの桁表示だけが動いて画面が止まって見えた**（利用者の指摘）。

原因は、縦の追従をアプリ側の**概算**（30 行と決め打ち）で行っていたこと。
画面の高さを知っているのは描画側だけなので、アプリは正しい行数を
持てない。1 行ずつの移動では概算でも見た目に出なかったが、
一度に大きく動く移動では外れる。

**横は最初から描画側がやっていた**（`Action::ScrollXTo`）。同じ形に
揃え、縦も描画側が `Action::ScrollTo` で知らせるようにした。

|どこ|役割|
|---|---|
|アプリ|**上へ外れた場合だけ**寄せる（行数が要らないので正確に決まる）|
|描画|下へ外れた場合を含め、**毎回の更新で**正しい先頭行を知らせる|

**値は絶対値で渡す。** 何度届いても同じ結果になり、取りこぼしても次の
フレームで直る。

### 10.49 正式版: 全角の上に空白の印が重なる（2026-10-02）

不可視文字の表示（§4.11）で、**全角括弧などの上に空白の印が見えた**
（利用者の指摘）。

印の行は本文と同じ幅で並べる必要があり、全角の位置には全角の空白
（U+3000）を置いていた。ところが**同梱フォントは U+3000 を見える枠として
描く**ため、空白のつもりが印になっていた。

半角の空白 2 つへ替えた。幅が合うのは、同梱フォントが半角と全角を
1 対 2 で作っているためである（技術選定書 §6.5）。

あわせて、**全角の空白そのものには印（`□`）を出す**ようにした。
半角と見分けがつかないまま保存されると、表の桁がずれるなどの形で
後から効いてくる。

### 10.50 正式版: 印に置ける字は半角に描かれるものだけ（2026-10-02）

全角スペースを並べると、**灰色の破線の四角と薄い実線の四角が、ずれて
二重に見えた**（利用者の指摘）。

原因は 2 つある。

|原因|中身|
|---|---|
|**二重**|同梱フォントは全角スペースを**破線の枠として自前で描く**。その上へ `□` を重ねていた|
|**ずれ**|`□`（U+25A1）は**曖昧幅**で、和文フォントでは全角に描かれる。1 桁ぶんのつもりが 2 桁を占め、置くたびに印が 1 桁ずつずれていった|

全角スペースには**印を置かない**ことにした。フォントが描くので本文を見れば
分かる。

**印に置ける字は、半角に描かれることが確かなものだけにする**（§4.11）。
曖昧幅の字（`□` `●` `■` など）は、使う環境のフォント次第で幅が変わり、
重ねた行がずれる。

> **ここで「`·` `→` `↵` `↓` は半角だと確かめてある」と書いたのは誤りで、
> 実際には測っていなかった。** その直後、タブの後ろの空白に印が付かない
> という指摘を受けた（§10.51）。**確かめていないことを確かめたと書かない。**

#### 試験で見ていること

「全角スペースを 3 つ並べたとき、印の桁数が 7（全角 3 × 2 + 半角 1）に
なる」ことを見る。**幅の合わない字を置くと 2 つ目から崩れる**ので、
1 つだけの試験では捕まえられない。

### 10.51 正式版: 印の幅を測る（2026-10-02）

タブの直後に半角スペースを並べると、**空白に印が付かないように見えた**
（利用者の指摘）。

原因は `→`（U+2192）の幅である。同梱フォントで**半角の 2 倍**に描かれる
ため、タブの印を 1 桁ぶんのつもりで置くと、その先の印がまるごと 1 桁
ずれていた。

#### 測った（`examples/check-marks.rs`）

同梱フォントの送り幅は半角 528・全角 1056（1em = 1000）。

|字|送り幅|半角比|使えるか|
|---|---|---|---|
|`·`|528|1.00|**使える**|
|`»`|528|1.00|**使える**|
|`↵`|528|1.00|**使える**|
|`>` `^`|528|1.00|使える|
|`→`|1056|2.00|**使えない**|
|`↓`|1056|2.00|行末のみ（下記）|
|`□` `¶`|1056|2.00|**使えない**|

タブの印を `→` から **`»`** へ替えた。

### 10.55 正式版: `$$` を数式として扱う（2026-10-05）

`$$ ... $$` がソースのまま出ていた（利用者の指摘）。GitHub や Qiita で
普通に使われる書き方で、既存の文書に含まれる。

#### 走査器では「囲みの一種」にする

```` ``` ```` や ```` ~~~ ```` と同じ仕組みに乗せ、**言語を `math` と
決め打つ**ことで既存の経路へ合流させる。判定を増やさない。

**1 行で閉じる書き方（`$$x$$`）は囲みにしない。** 開始と取ると、
**以降が全部数式になる**（試験で見ている）。

#### HTML だけは別の手当てが要った

画面と PDF は自前の走査器を通すが、**HTML 出力は comrak が解析する**。
comrak は `$$` を知らないので、そのままでは段落になる。

**走査器に聞いてから書き換える**ことにした（`parse::dollar`）。
ここで新しく「`$$` は数式か」を判定すると、画面と HTML で食い違う
余地ができる（§10.28 の形）。走査器の答えのとおりに
```` ```math ```` へ直すだけにする。

**置き換えるものが無ければ写さない**（10MB で複製しない）。

#### インラインの `$...$` は入れていない

`$100 と $200` のような文が数式になってしまう。囲みと違って**閉じ記号が
一意に決まらない**ため、別に設計が要る。

### 10.56 正式版: 図のデバウンス・キャッシュ上限・表示倍率（2026-10-05）

正式リリース前の積み残し（D-1 / D-2 / D-3）をまとめて片づけた。

#### デバウンスは「時間」ではなく「要るかどうか」で決まる（DD-OPEN-15）

最初は「依頼を 300ms 遅らせる」だけを考えたが、**それでは打鍵の途中の
図を遅れて描くだけ**で、何も減らない。

**要らなくなったものを捨てる**ところまで要る。そのために、依頼の渡し方を
1 件ずつ（`request`）から**まとめて**（`sync`）へ改めた。

|やり方|「もう要らない」が分かるか|
|---|---|
|1 件ずつ渡す|**分からない**。渡されなかったことと、呼ばれていないことが区別できない|
|**可視範囲を丸ごと渡す**|**分かる**。渡された集合に無いものが「要らないもの」|

打鍵のたびに `g` → `gr` → `gra` …と鍵が変わるが、**投げるのは止まった
あとの 1 件だけ**になる（試験で見ている）。

#### 待たせるのは編集中だけ

**開いた直後まで 300ms 待たせない。** 文書を開いただけで図が遅れて出ると、
遅いアプリに見える。編集の入口（`apply_edits`）から合図を送り、
**そこから 300ms の間だけ**溜める。

#### 追い出してよいものは限られる

|状態|追い出す|理由|
|---|---|---|
|届いている・画面に無い|**する**|これが本来の対象|
|**まだ届いていない**|しない|結果が戻ってきたときに持ち主がいない|
|**いま画面に出ている**|しない|次のフレームで描き直しになり、点滅する|

上限は基本設計書 §16.8 のとおり **200 件／合計 128MB**。
どちらか一方でも超えたら、古いものから捨てる。

> **順番を付けるのは「依頼したとき」である。** 状態を引く口
> （`EmbedLookup`）は不変参照で毎フレーム呼ばれるため、そこでは直せない。

#### 画像は更新時刻まで鍵に入れる（DD-OPEN-16）

パスと幅だけでは、**画像を差し替えても同じ鍵**になり、古いものが出続ける。
更新時刻（ミリ秒）を鍵に混ぜた。読めなければ混ぜない（無いファイルも、
更新時刻を持たないファイルシステムもある）。

**ファイル監視は入れていない。** 気づくのは、そのブロックを測り直した
ときである。差し替えてすぐ反映させたい場合は P4 の課題として残る。

#### 表示倍率は鍵にも入れる（§4.13）

設定ファイルに `zoom` はあったが、画面から変える手段が無かった。

|決めたこと|理由|
|---|---|
|**刻みで動かす**|1% ずつでは、押した回数と見た目が結びつかない|
|**エディタとプレビューの両方**|片方だけだと分割表示で食い違う|
|**レイアウトキャッシュの鍵に字の大きさを足す**|足さないと、倍率を変えても前の大きさで測った結果を引き続ける|
|**推定の寸法（`Metrics`）も掛ける**|掛けないと、まだ測っていないブロックの高さが前の倍率のままになる|
|**図の大きさは変えない**|表示幅に合わせて描いており、幅が変わらない以上そのままである|

> **`Ctrl + +` は JIS 配列では Shift が要る。** `;` と `=` でも通す。

#### `cargo fmt` が通っていなかった

この回の作業で気づいた。**組み立ての試験（CI）は `cargo fmt --all --check`
を見ており、45 か所で落ちる状態になっていた。** 設計の誤りではなく、
手で当てた修正を整形していなかったためである。

**ここまでの変更は Python で当ててきた**（§10.46 の経緯）。
整形器を通す手順が抜けていた。全体に `cargo fmt --all` を掛けた。

### 10.57 正式版後: スクロールバー・タッチパッド・自前のファイル選択（2026-10-06）

v2.0.0 を配ったあとの指摘 3 件。**どれも「配ってから分かった」もの**である。

#### 縦と横は選ぶものではない（タッチパッド）

「二本指で動かしてもスクロールしないことがある」という指摘。

ホイールの受け口が、**横の値が 0 でなければ横だけを送り、さもなくば縦**
という分岐になっていた。マウスのホイールは横がちょうど 0 になるので
この形で通っていたが、**タッチパッドの二本指はまっすぐ縦には動かない。**
縦へ送っても横に 0.2px といった値が一緒に届く。

結果、わずかな横揺れがあるだけで**縦が死んでいた**。

|直し方|理由|
|---|---|
|**両方出す**|横と縦は別の軸である。選ぶものではない|
|`Shift` のときだけ縦を捨てる|押している間は横送りの道具になる（DD-01 の代替手段）|

判断を `wheel_scroll` へ出し、窓なしで試験できるようにした。

#### スクロールバーは設計にあって実装が無かった

基本設計書 §16 と §3.7 は「`doc_y / height_index.total()` から描く」と
しているが、**実装が 1 行も無かった。** 利用者の指摘で気づいた。

|決めたこと|理由|
|---|---|
|幾何を `render::scrollbar` へ切り出す|窓を知らないので窓なしで試験できる|
|**単位を問わない**|エディタは行、プレビューは画素で巻き上げる。どちらも「全体・見えている量・いまの位置」で決まる|
|**つまみに下限を置く**（24px）|10MB・380,812 行では比率どおりだと 1px を割り、掴めない|
|**本文の幅を削らず重ねる**|削ると、押した場所から桁を求める計算とレイアウトキャッシュの鍵（幅）が巻き添えになる|
|溝を押すとつまみの中心がそこへ来る|掴んだときは差で動かす（掴んだ瞬間に飛ばない）|
|全部見えているなら出さない|動かせないものを出すと、動かせると誤解させる|

#### WSL でファイルが開けなかった

**Linux 版は WSL で使うことを主目的にしている**（利用者）。しかし
WSL の既定の環境では `Ctrl + O` が黙って何もしなかった。

`rfd` の Linux 側は xdg-desktop-portal（D-Bus）だけで組んであり、
WSL にはセッションバスも portal も無い。選択は `None` を返し、
アプリはそれを**「取り消した」と区別できない。**

|案|入るもの|代償|
|---|---|---|
|`.sublime-syntax` と同じく GTK を足す|本物のダイアログ|ビルドと配布物に依存が増え、**単一実行ファイル**の方針が崩れる|
|利用者に D-Bus と portal を入れてもらう|追加の実装が要らない|「入れればすぐ使える」という前提を壊す|
|**自前の選択を描く（採用）**|どこでも必ず動く|OS のダイアログの機能は持たない|

**呼ぶ側は区別しなくてよい形にした。** `ask` が OS のダイアログと
同じ形の仕事（`Task<Option<PathBuf>>`）を返すので、開く・保存・出力の
3 か所は 1 行も変えていない。中では一度きりの受け渡し口を使って、
選び終わったところで答えを流す。

> **必ず答えを返すこと。** 返さないと待っている仕事が終わらず、
> `picking` が立ったままになってファイル操作が押せなくなる。
> 試験で見ている（返さないよう壊すと 2 件落ちる）。

#### 画面写真で確かめようとして三度誤った

この回でいちばん費やしたのは、実は**確認の失敗**である。

|誤った判断|本当の原因|
|---|---|
|「プレビューにスクロールバーが出ていない」|捕捉した PowerShell が **DPI 非対応**で、窓の右 300px が落ちていた（表示倍率 125%）|
|「プレビューの表と図が右で切れている」|同上。描画は正しい|
|「ダイアログの窓は出るが中身が描かれない」|**窓が 2 つ起動**しており、古い方を測っていた。さらに全画面の取得で別のアプリを掴んでいた|

**画面を撮って判断するなら、何を撮ったのかを先に確かめる。**
いまは次のようにしている。

- 捕捉の側を DPI 対応にする（`SetProcessDpiAwarenessContext`）

- **撮らずに済むものは撮らない。** `update` は状態を変えるだけなので、
  窓なしの試験で確かめられる（`browser_wiring_tests`）

### 10.59 正式版後: 同期の取りこぼしと、画面の外の長い行（2026-10-06）

スクロールバーを入れたことで続けて露見した 2 件。

#### 先頭行を書く場所が散っていた

「矢印キーで戻るとき」と「スクロールバーを掴んだとき」に、
**プレビューが取り残されていた**（利用者の指摘）。

`editor.top_line` を書く場所が **8 か所**あり、同期を呼ぶかどうかが
その場ごとの判断になっていた。呼び忘れた 2 か所がそのまま不具合だった。

**入口を 1 つにした**（`set_top_line`）。書けば必ず同期される。

|経路|入口を通すか|
|---|---|
|ホイール・スクロールバー・キャレット追従|**通す**（同期の対象）|
|検索で飛ぶ・目次で飛ぶ|通さない。**設定によらず寄せる**のが決まり（明示の操作）|
|プレビュー → エディタの同期|通さない。**合わせ返して落ち着かなくなる**|
|計測用の送り|通さない。両側を明示に動かして測る|

> **ここでも試験を間違えた。** 矢印キーの経路を `Action::Move` で
> 書いたが、あちらは `follow_cursor` を通らない（画面の高さが要るため
> 描画層が `ScrollTo` で知らせる。§10.48）。落ちて気づいた。
> **打鍵の経路で書き直した。**

#### 横のバーは可視範囲しか見ていなかった

長い行から縦に離れると幅が 0 になり、**横のバーが消えて横へ動けなく
なっていた**（利用者の指摘）。普通のエディタは、長い行が画面の外に
在っても横へ動ける。

全行の幅を測るのは無理である。**整形が要るため、10MB では終わらない。**

|決めたこと|理由|
|---|---|
|文書が**いちばん長い行を 1 つ覚える**|描画層はそれを足して測るだけでよい。整形は 1 行ぶん|
|長さは**バイト数**で比べる|字の幅を測ると全行に整形が要る。多バイトの字は幅も広いので近い目安になる|
|可視範囲は**今までどおり正しく測る**|目安が外れても、見えているところは合う|
|編集では**触った行だけ**と比べる|打鍵ごとに全行を舐めない|

**いちばん長い行を消した場合、記録は長いまま残る。** 横のバーが必要より
少し長く動けるだけで、害は無い。読み込み直せば正しくなる。

### 10.60 v2.1.0: 機能追加の作り方（2026-10-08）

要件は [v2.1.0 要件定義書](../doc/v2.1.0の要件定義書.md)。ここには**作り方の判断**だけを残す。

#### 打鍵とメニューを 1 つの表から出す（R-10）

v2.0 までは、メニューに併記する `"Ctrl + S"` と、購読の `"s" =>` を
**別々に書いていた**。キー割り当てを変えられるようにすると、片方だけ
変わって食い違う。

**操作の一覧（`app::keymap::Command`）を 1 つ置き、** 既定の打鍵・
メニューの併記・押されたときのメッセージをすべてここから出す。
購読は「修飾キー付きの打鍵が来た」ことだけを知らせ（`Message::KeyChord`）、
判定はアプリ層で行う。

|決めたこと|理由|
|---|---|
|判定は**修飾キーを除いた文字**|JIS 配列で `Shift` が要る記号でも、キーの位置で押せる（§7.2）|
|記号は `Shift` を外しても引く|US の `+` は `Shift + =`、JIS の `+` は `Shift + ;` で届く。外さないと拡大が効かない|
|本文を書き換える操作は、入力欄に焦点があると止める|検索欄で `Ctrl + B` を押して本文が太字になってはいけない|
|設定ファイルには**既定から変えたものだけ**書く|既定を書くと、次の版で既定を変えたときに古い値が残り続ける|
|利用者の変更は 1 操作につき 1 打鍵|区切り文字を決めると、その文字（`,` など）を割り当てられなくなる|
|**メニューにある操作はすべて `Command` に置く**（既定の打鍵が無いものも）|最初は打鍵の併記がある項目だけを置いており、表示モード・目次・出力・変換・日付の挿入など 24 個が割り当てられなかった（GUI 試験の敵対的検証で見つけた）|
|変換と日付の挿入は**種類を持った 1 つの操作**（`Command::Transform(Transform)` / `Command::Insert(Stamp)`）|種類ごとに別の名前を並べると、変換を足したときに表を 3 か所直すことになる。設定ファイルの名前（`transform_upper` など）は種類から決める|
|対象外は字下げ（`Tab`）・終了（`Alt + F4`）・最近使ったファイルの各項目|`Tab` はエディタが直に扱う。`Alt + F4` は OS の打鍵。最近使ったファイルは中身が変わる|
|**割り当ての処理（`capture_key`）でも、`Ctrl`・`Alt`・F キーを含まない打鍵を断る**|画面の購読はそれを流さないが、流す道が増えたとき（試験の口など）に崩れないよう、判定を処理の側にも置く|

#### 折りたたみは「段と行の読み替え」で作る（R-20）

エディタは**行の高さが一定**であることを前提に、可視行を割り算で求めている
（DD-01）。畳んだ行を本文から抜くと、この前提も、ロープの行番号も壊れる。

**行番号は文書のまま使い、「画面の何段目か」との読み替えだけを足した**
（`app::fold::FoldMap`）。描画・クリック・スクロールバー・ホイール・
キャレット追従は、縦の位置を扱うところで必ずこの読み替えを通す。

- 畳んでいる見出しは**ブロックの番号**で覚える（§3.8）。位置がずれても変わらない
- 読み替えの手間は**畳んだ範囲の数に比例**する。10MB でも範囲が少なければ速い
- 畳んだ中へキャレットが入ったら開く。入口が多いので **`update` の出口 1 か所**で見る

#### ミニマップは帯の 1 画素に 1 行（R-01）

38 万行を縮図にすると、全行は描けない。**帯の 1 画素ごとに代表の 1 行を
選んで**、その長さと字下げだけを描く。描く本数は帯の高さ（数百）で決まり、
文書の大きさに依らない。

短い文書は 1 行 2px で上から描く（引き伸ばすと縮図に見えない）。
**つまみ（見えている範囲の枠）も同じ縮尺で決める。** 普通のスクロールバーの
縮尺で置くと、絵と枠がずれる。

10MB の計測（`--bench-scroll`）で **ミニマップあり 108.4fps・なし 108.3fps**。
v2.0.1 の 108fps から落ちていない。打鍵（`--bench-edit`）は中央値 10.51ms・
最悪 23.52ms（§20 の目標 150ms 以内）。

#### 別の窓は別のプロセス（R-09）

iced は 1 つのプロセスで複数の窓を持てるが、いまのアプリは「1 つの文書・
1 つの窓」を前提に状態を組んでいる。**自分の実行ファイルを引数つきで起こす**
ほうが、作りを変えずに済み、1 つの窓が落ちても他を巻き込まない。

代わりに、設定ファイルを複数の窓が書く。

#### 設定は「変えた項目だけ」を書く

窓ごとに設定を丸ごと書くと、**後から書いた窓が、他の窓の変更を古い値で
上書きする**（窓 A でテーマを変えても、窓 B を閉じると戻る）。利用者の指示で
「窓をまたいでも消えない・その場で効く」ようにした。

|決めたこと|理由|
|---|---|
|窓は**最後にディスクと揃えた設定**（`settings_baseline`）を覚える|これと比べて変わった項目が「この窓で変えたもの」|
|書くときは、ディスク上の設定に**変えた項目だけ**を重ねる（`Settings::merge_changes`）|他の窓の変更が残る|
|比べるのは **TOML の鍵**|項目を足しても、突き合わせを直さずに済む（直し忘れて消える事故を起こさない）|
|キー割り当て・最近使ったファイルは**まとまり**で扱う|1 件ずつ混ぜると、外した割り当てや消した履歴が戻る|
|設定ファイルの印を 0.5 秒ごとに見て、**他の窓が書いたら取り込む**。印は**中身の要約**（v2.3.0。以前は更新時刻と大きさ）|その場で効く。更新時刻と大きさでは、他の窓が同じ大きさの中身を同じ時刻の刻み（Windows は 15.6 ms ほど）のうちに書くと見分けられず、取り込みそこねた（公開側の CI の洗い出しで見つけた）。設定ファイルは数 KB なので、刻みごとに読んでも重くない|
|**読む → 重ねる → 書く → 印を取る**の間と、取り込むために読む間は、設定ファイルの隣の `settings.lock` を排他で掴む（`Settings::lock`。v2.3.0）。掴めなければ掴まずに進む|窓は別のプロセス。2 つの窓がほぼ同時に書くと、後の窓が先の窓の追加を知らずに上書きし、書きかけを読むと欠けた設定を取り込む（最近使ったファイルが 1 件消えた。公開側の CI の Windows で落ちた）。一時ファイルからの置き換えは、Windows で他のプロセス（ウイルス対策など）が開いている間に失敗することがあるので採らない|
|設定画面の変更は**デバウンスせずに書く**|他の窓へすぐに届ける。デバウンスは倍率や幅のように続けて変わるもののため|
|表示モード・目次・分割比・倍率・スクロール同期は**取り込まない**|窓ごとに違ってよい。他の窓で目次を広げたら、この窓まで動くのは困る|
|まとまりの判定は `key.` で始まる鍵と、`recent_` に**数字**が続く鍵だけ|`recent_` で始まるものをすべてまとまりにすると、件数の設定（`recent_limit`）まで最近使ったファイルの一覧と一緒に扱われ、他の窓が書くと消えた（GUI 試験で見つけた）|
|真偽値の項目に `true` / `false` 以外が書かれていたら、**その項目だけ既定のまま**|`maybe` を偽と読むと、既定が真の項目（ミニマップなど）が黙って消える（GUI 試験で見つけた）|

#### macOS の Finder から開く: 起動用アプリを挟む（R-08）

Finder はファイルを**起動引数ではなく Apple Event（odoc）で**渡す。iced（winit 0.30）は
これを受け取る口を持たない。v1（Tauri）は `RunEvent::Opened` で受けていた。

|案|採否|理由|
|---|---|---|
|**起動用アプリを挟む**|**採った**|winit の中身に依存しない。本体は「窓ごとに別のプロセス」（R-09）なので、引数で渡すだけで噛み合う|
|winit の delegate へ実行時に手を足す|採らない|winit の内部の作りに依存し、更新で黙って壊れうる|
|上流の対応を待つ|採らない|時期が読めない|

```
mdview.app/                               起動用（Swift。packaging/macos/launcher/main.swift）
  Contents/MacOS/mdview
  Contents/Helpers/mdview.app/            本体（Rust）
    Contents/MacOS/mdview
```

|決めたこと|理由|
|---|---|
|本体は**入れ子の .app**、**別のバンドル ID**（`io.github.mdview.editor`）|同じ ID だと、本体が起動している間に Finder で開いたとき、macOS が受け取れない本体へ送る|
|関連付け（`CFBundleDocumentTypes`）は**起動用だけ**が持つ|Finder から見えるのは起動用|
|起動用は `LSUIElement`（Dock に出さない）で、**渡し終えたら終わる**|窓は本体が出す。次に開くときは、また起動用が起こされる|
|ファイル付きで開かれなければ（アプリそのものを開いた）、0.3 秒待って空の窓|`open` は起動の完了より先に届く|
|**引数付きで起こされたら `execv` で本体に置き換わる**|端末からの使い方と CI の煙試験（`--version`）がそのまま通る|
|本体を起こせなければ**警告を出す**|黙って何も起きないのが一番困る|

**実機が無いので、動きは確かめていない。** Swift のコンパイルは CI の macOS ランナーで
型検査し、組み立てと煙試験も同じ CI（公開側の `ci.yml`）で行う（2026-10-13 から。それまでは `release.yml`）。

#### GUI 自動テストは試験用の操作口で行う（2026-10-08）

iced の UI は Windows UI Automation から**窓 1 つしか見えない**（子要素 0 件）。
AccessKit の後付け・座標とキーの黒箱試験・UI の作り直しと比べ、**アプリに試験用の
操作口を設ける**案を採った（利用者の判断）。決まりは [GUI 自動テストの方針](../doc/GUI自動テストの方針.md)。

|決めたこと|理由|
|---|---|
|**`--automation` のときだけ**標準入力を読む|普段の起動では口が無い|
|**標準入出力**で 1 行 1 件の JSON|ネットワークの口を開けない。起こした親だけが話せる|
|要素は **UIA と同じ考え方**（ID・役割・名前・有効／無効・値）|試験の書き方が UIA の道具と同じ形になる|
|要素の木は**画面の組み立てと同じ優先順**で作る|覆うものの下の要素を押せてしまうと、画面ではできない操作が試験だけ通る|
|押す・打つは**画面と同じメッセージ**を流す|試験のための別の道を作らない（作ると、試験が通っても画面で壊れる）|
|本文に焦点が無いときの `type` は断る|画面で打っても入らない場面で、試験だけ入るのを防ぐ|
|この方式では**自前のファイル選択**を出す|OS のダイアログは操作できない|
|標準入力が閉じたら確認なしで終わる|試験の道具が落ちたときに窓を残さない|
|**他のアプリを立ち上げない**（URL・その他のファイル・OS の設定画面は、開かずに `external_opens` へ覚える）|試験のたびにブラウザや設定アプリが立ち上がると、試験を回す端末が使えなくなる。開く先が正しいかは覚えた先で確かめる|
|起こした窓のプロセス番号を `spawned` で知らせる|OS の窓の一覧から探すと、試験の外で開いている mdview と取り違える|
|退避ファイルの置き場は `MDVIEW_DRAFT_DIR`、設定は `MDVIEW_CONFIG_DIR` で差し替える|利用者の設定と退避を汚さない・読み違えない|
|選べる値が決まっている要素は `options` を出す（配色など）|「何が選べるか」は画面の部品の中にあり、外から見えない|
|`drop` は `paths` で続けて流せる|まとめて落としたとき、1 つ目の読み込みが終わる前に 2 つ目が届く場面を作れる|
|座標から部品を当てる道（当たり判定）は通らない|iced は外から出来事を入れる口を持たない。ミニマップのつまみを掴む・溝を押す処理は、部品の `press_bar` / `drag_bar` を**単体試験で直に呼んで**確かめる（描く側は `()` の描画器で足りる）|

#### `<img>` タグを画像として描く（R-17）

GitHub は貼り付けた画像を `<img width height alt src>` で入れる。同じ形で入れる
ので、**`<img>` タグ 1 つだけの段落を画像として扱う**ようにした（解析層の
`img_tag`）。読む属性は `src`・`width`・`alt` だけで、HTML としては動かさない
（`onerror` などは捨てる。§19.3 の考えと同じ）。

> **安い判定を直し忘れて、「画像を描画中」のまま止まった。** 埋め込みかどうかは、
> レイアウトキャッシュを引く前の安い判定（`is_embed_block`。先頭が `![` か）と、
> comrak で確かめる本当の判定（`embed_source`）の 2 段になっている。
> 本当の判定だけ直したため、箱は置かれるのに描く依頼が出なかった。
> **両方を見る試験を足した。**

#### 外の変更は印だけを見る（R-21）

更新時刻と大きさを 2 秒ごとに見る。**中身は読まない**（10MB を 2 秒ごとに
読むことになる）。見るのは**別の糸**で行う（遅い共有フォルダで UI を止めない）。
自分で保存した直後は印を覚え直し、取り違えない。**覚え直す前に頼んだ確認の結果は捨てる**
（見張りの世代 `Watch::generation`。v2.3.0）。捨てないと、保存の前の古い印が保存の後に届き、
自分の保存を外の変更と取り違える。

#### プレビューのリンクは押した文字から拾い直す（R-19）

レイアウト結果はリンクの先を持たない（キャッシュに載る値を増やしたくない）。
**押した字の並び（`TextRun`）の文字を、ブロックの原文のリンクと突き合わせる。**
同じ文字のリンクが 1 つのブロックに 2 つあると先のほうを開くが、実際の
文書ではまず起きない。

#### 文字コードは OS のダイアログに足さない（R-04）

OS のダイアログへ選択欄を足せるのは Windows（`IFileDialogCustomize`）だけで、
Linux の portal ではほぼ足せない。**OS ごとに挙動が分かれる**のを避け、
自前のダイアログ（文字コード・改行コード）と、自前のファイル選択の欄に置いた。

#### 画像の貼り付けには `arboard` を足した（R-17）

iced のクリップボードは文字しか扱えない。**文字があれば画像は読まない**
（Excel や Word から写すと文字と画像の両方が載り、画像を貼ると写した文字が入らない）。
依存の記録は技術選定書 DEC-212。

#### GUI 試験で見つけて直したもの（2026-10-08）

要件の試験（`tools/automation/spec_test.py`）と、その網羅の敵対的検証の過程で見つけた。

|症状|原因|直し方|
|---|---|---|
|窓をまたぐと、最近使ったファイルの件数の設定が消える|まとまりの判定が `recent_` で始まる鍵をすべて含めていた|`recent_` に数字が続く鍵だけにした（単体試験 `the_recent_limit_survives_a_merge`）|
|「常に最前面」を ON で起動しても最前面にならない|窓を作る前に指定していた|窓ができてから指定する|
|`<img>` だけの段落が「画像を描画中」のまま|埋め込みのブロックの判定が `<img` を知らなかった|判定に足した|

|メニューにある操作の一部を割り当てられない|`Command` に打鍵の併記がある項目しか置いていなかった|メニューの操作をすべて置いた（R-10 の節）|

### 10.61 v2.2.0: 機能追加の作り方（2026-10-14）

#### 題名とステータスバーの書式（`app/template.rs`）

- **差し込み口を、その場の値で置き換える**だけの小さな展開器。知らない口は消さずに残す
  （書き損じが画面で分かる）。`{{` `}}` は波括弧そのもの
- **日付と時刻を分けた。** 1 つの書式で `mm` を月にも分にも使うと読み違えるので、`{date:…}` の中では月、
  `{time:…}` の中では分とした
- 文字コードの欄だけを押せるようにするため、書式を `{encoding}` の前・`{encoding}`・後ろの 3 つに
  分けて展開する。書式から外せば押す所も無い
- 時刻が進むのは、キャレットの点滅（500 ms）で描き直すたびに題名を組み直すため。別の刻みは足していない

#### 右端で折り返す（`render/wrap.rs`）

- **段の表（`Wrap`）をアプリが持つ**。行ごとの「最初の段」と「段の切れ目（表示の文字番号）」。
  畳んだ行は 0 段（R-20 と同じ考え方）。文書の版・行数・バイト数・桁・タブ幅・畳み込みを鍵に、
  `update` の出口で変わったときだけ作り直す
- **幅はエディタが測ってアプリへ知らせる**（`Action::WrapColumns`）。幅を知るのは描画層だけ
- **桁は等幅として数える**（半角 1・全角 2）。字形を測らないので速い。作り直しは文字列を作らずに数え、
  全角やタブでも確実に収まる短い行は数えない（512 KB で約 3 ms。`wrap_build_cost`）
- **先頭は「行と、その行の何段目か」で持つ**（`EditorState::top_segment`）。行も一緒に持つのは、
  `top_line` が何か所からも書き換わり、段だけ持つと別の行へ飛んだあとに古い段が残るため
- **描画は、行をまるごと描くのではなく段の文字だけを描き、段の範囲で切り抜く。** 段の左端の位置は
  前の段の幅に足していき、1 行ぶんを覚えて使い回す（段ごとに行頭から測ると、長い行で
  1 フレームに何十回も字形を組む）。選択・検索の強調・キャレットは、行の位置から段の左端を引いて置く
- **上下とページ送りはアプリで見た目の段に読み替える**（`Wrap::step`）。試験の口からの打鍵は
  ウィジェットを通らないため、ウィジェットで読み替えると経路で動きが変わる。横位置は段の左端からの
  桁で保つ（`goal_cells`）

#### Markdown 以外のファイル（`BlockKind::Plain`）

- **走査に「テキストとして読む」を足した**（`Document::plain_text`）。空行までを 1 つの塊にし、
  **空行も塊に入れる**（プレビューで空行を消さないため）。位置ではなく空行で区切るので、
  編集のあとの走査し直しは次の空行で再同期できる
- `Code` を流用しなかったのは、行頭が ``` の行を囲みと見なして消すため
- 読み方は**拡張子で決める**（無題は Markdown）。名前を付けて保存で拡張子が変われば読み直す
- HTML へ出力するときは、本文の中のどの ` の並びより長い囲みで包んで comrak へ渡す

#### プレビューで文字を選ぶ

- **選んだ範囲はウィジェットが持つ**（`(ブロック, 行, 行の中の文字番号)`）。文書の版が変われば捨てる
  （ブロックの番号がずれる）
- 選び終わったら選んだ文字をアプリへ知らせ（`PreviewAction::Selected`）、**写すのはアプリ**。
  最後に触ったのがエディタならエディタの選択を写す
- 行の間は、原文どおりに並ぶ行（コード・表・テキスト）なら改行、折り返した段落なら何も挟まない

#### プレビューのはみ出し・ミニマップの最下段

- プレビューは自分の領域で切り抜いていなかった（文字は窓全体で、四角形は切り抜き無し）。
  エディタと同じく `with_layer(領域)` の中で描く
- ミニマップは、帯の縮尺を「溝 − 枠」に合わせる。最後まで送ると先頭は最終行なので、枠は文書の外
  （帯の下）に来る。ミニマップのときは、横のバーのために下端を空けない

### 10.62 起動の短縮（2026-10-16）

基本設計書 §20.3 の実測で、**起動の大半は GPU の準備**だった（ダブルクリックから中身が描けるまで
1,632 ms のうち 1,000〜1,200 ms）。

#### 描画の下回りを 1 つに絞る（`main.rs` の `choose_graphics_backend`）

- iced（`iced_wgpu` 0.14）は、環境変数 `WGPU_BACKEND` が無ければ `wgpu::Backends::all()` で始める。
  Windows では DX12・Vulkan・OpenGL をすべて初期化し、高性能の GPU として Vulkan を選んでいた
- 環境変数で切り替えて測った（小さい文書）: 既定 1,594 ms・DX12 573 ms・Vulkan 975 ms・
  DX12 と Vulkan 1,006 ms・OpenGL 1,162 ms・ソフトウェア描画（tiny-skia）344 ms
- **`main()` の最初で `WGPU_BACKEND` を入れる**（ほかの糸を作る前。環境変数を書くため）。
  利用者が決めていれば触らない。Linux は `libvulkan.so.1` が置かれているときだけ Vulkan にする
  （無い環境で絞るとソフトウェア描画に落ちる）
- 選んだもので描けなければ、iced はソフトウェア描画に切り替わる。起動は速い（344 ms）が、
  10 MB のスクロールの滑らかさは測っていない

#### ファイルを並べて読む（`app/preload.rs`）

- iced は `App::new` を、窓を作って GPU の準備をするより**前に、同じ糸で**呼ぶ
  （`iced_winit` の `run`。`program::Instance::new` → 窓 → `Compositor::new`）。
  そこで読むと待ち時間に足される
- `main()` で起動引数の 1 つ目を別の糸で読み始め（`io::load` と `Document::plain_text`）、
  `App::new` は受け口だけ取って**待たない**。本文は空・題名はファイル名で窓を出し、
  `Message::Preloaded` で出来上がった文書を据え付ける（`install_document`。`replace_document` と同じ後始末）
- **差し替わるまで、本文の書き換え（`apply_edits`）と上書き保存（`save_now`）を断る。**
  空の本文で元のファイルを上書きしない。その間に別の文書を開いたら、届いたものは捨てる
- 試験の口の「話せる」と `-g` は、差し替えてから行う（試験が空の本文を見ない）

Dependabot の更新を取り込んだ。公開側でまだ v2.2.2 を出していなかったので、v2.2.2 に含めた（CHANGELOG の 2.2.2）。

#### merman 0.9 の背景

0.8 までは図の全面を白で塗っていた（§10.13 の「2 回目」の誤りはこれが前提）。0.9 から透明になり、
そのまま画素へ落とすと**暗い配色のプレビューで黒い線と文字が背景に溶ける**。CI の試験は通ってしまう
（図の形も文字の画素も変わらない）ので、**背景を見る試験 `the_background_is_white` を足した**。

- 四隅の**1 画素内側**を見る。図の寸法が整数でないと、最後の行と列は半分だけ塗られる
- 手当てを外すと (1, 1) が `[0, 0, 0, 0]` になって落ちることを確かめた
- 画面・PDF・HTML とも同じ SVG を使うので、3 つとも 0.8 までと同じ白い地になる

#### 確かめたこと

- 数式は、1.x と 2.1.1 の実行ファイルで同じ文書（分数・根号・総和・積分・行列・場合分け・揃えた複数行・括弧・書体・誤った式）を開いて見比べた
- 実行ファイルは、配る物（dist。本体の Release）で 63,740,928 → 63,913,984 バイト（+173 KB。v2.2.2a → v2.2.2b）。`release`（thin）では 63.7 MB → 65.2 MB（+1.5 MB）増えたが、fat LTO でほとんど消えた

#### 試験を流すときの注意

- **試験は debug で組む**（`cargo test --all`）。iced は試験で使う描画役 `()` を `debug_assertions` のときしか用意しないので、`--release` では組めない
- **利用者の設定が試験に入り込む。** `App::new()` は `%APPDATA%\mdview\settings.toml` を読む。試験は設定を既定へ戻すが、読んだときに決まった表示の切り替え（分割・プレビュー）は残る。手元の設定が `view_mode = "preview"` だと 3 件落ちる。`MDVIEW_CONFIG_DIR` を空のフォルダーへ向けて流す（CI は設定が無いので落ちない）

### 10.65 diff 表示とパッチ（v2.3.0 R-02〜R-04。2026-10-19）

要件は v2.3.0 の要件定義書 R-02〜R-04（決定 D-1〜D-9）。

|部品|置き場|中身|
|---|---|---|
|差分の計算|`src/diff/mod.rs`|行の対応（同じ・違うのかたまり）、空きの段、段と行の読み替え、1 列表示の並び、行の中の文字単位の違い。`similar` 3.2（Histogram。5 秒で打ち切り）。比べる前の正規化（空白・大文字小文字・改行コード）は行の「鍵」を作って済ませる|
|パッチ|`src/diff/patch.rs`|書き出し（unified は `similar`、context は自前）・読み込み（形式は中身から見分ける）・当てる処理（位置のずれは探す。前後の行は完全一致だけ = fuzz 0）|
|空きの段|`src/render/wrap.rs`（`Wrap::spacers`）|**折り返しの表に「行の前に文字の無い段」を持たせる。** 切れ目を 0 に置くと文字は最後の段に入る。段と行の読み替え・描画・クリック・ホイールは折り返しと同じ道を通り、`wraps()` が偽なので横には送れる。上下の移動は空きの段に止まらない|
|色|`src/render/editor.rs`（`DiffMarks`）|行ごとの地の色（違う・この面にだけある・もう片方にだけある）、行の中の違い、空きの段、選んでいる違いの枠|
|地図|`src/render/diffmap.rs`|左右の面の間の帯。左右に並べたときの段で印と見えている範囲を描き、押すとその段へ|
|画面|`src/app/diff.rs`|本文を覆う画面。開き方・面・比べ直し・保存・閉じる確認・移動・写す・入れ替え・1 列表示・パッチ|

#### 左右の面の編集（D-1）

打鍵の処理（`App::apply` と各操作）は本文（`App::document`）1 つを相手に作ってある。そこで**面を触るときだけ、
本文・キャレット・履歴・素性を面のものと入れ替えて同じ処理を通す**（`App::in_pane`）。空きの段の表は
折り返しの表（`App::wrap`）の場所へ入れ、畳み込みは外す。入れ替えている間は `diff_own` を立て、
`apply_edits` は**本文を書き換えて未保存の印を付けたところで戻る**（目次・畳み込み・退避・自動保存・図は
編集中の文書のもので、面の文書には関わらない）。

- 「保存してある元と比べる」の右の面は編集中の文書そのもの（D-9）。入れ替えずに直接書き換えるので、
  退避と自動保存はふだんどおり働く。表と畳み込みだけを入れ替え、書き換えたら畳み込みを作り直す
- diff の画面を出している間は `update` の入口で**メッセージを振り分ける**（`diff::route`）。編集の操作は
  打鍵を受けている面へ、上書き保存はその面の保存へ。編集中の文書を差し替える操作（新規・開く・最近の
  ファイル・ドロップ）と、検索・行へ移動・表示モードの切り替えは受け付けない
- 1 列表示の面は読むだけ（D-7）。同じ入れ替えで、`read_only` を立てて通す

#### 比べ直し

書き換えたら、左右の合計が 512 KB まではその場で、超えたら裏の糸で比べ直す。裏の糸の答えは頼んだ番号で
受け取り、古い答えは捨てる。比べている間にまた書き換えたら、答えを受け取ってからもう一度比べる。

**外から比べ方が変わったとき**（ほかの窓・試験の口。`adopt_settings`）も比べ直す。`adopt_settings` は
仕事を返せないので印（`diff_resync`）を立て、`update` の出口で比べ直す（裏の糸の仕事を取りこぼさない）。

#### パッチ

- 書き出しは左を元・右を新（D-4）。見出しは GNU diff と同じく、ファイル名・タブ・日時（保存したままなら
  ファイルの更新日時、直していれば今の日時）。改行コードは左の文書に合わせる
- 当てるときは**変わった範囲だけを 1 つの編集にする**（同じ頭と尻を除く）。元に戻すで 1 回で戻る
- **GNU diffutils 3.12 / patch 2.7.6 と突き合わせた。** GNU の出力（`src/diff/testdata/`）を読んで当てられ、
  こちらの context diff は日時の行を除いて GNU と同じ。こちらの出力は GNU patch で当たる（手で確かめた）

#### 見送ったこと

|もの|理由|
|---|---|
|diff の画面での検索|検索バーは編集中の文書を相手にしている。面ごとに持たせるのは後の版|
|写す・入れ替えの既定の打鍵|WinMerge の Alt+← / Alt+→ は、編集部品がキャレットの移動として先に受け取る。キー割り当てで付けられる|
|10 MB 同士の比較の性能|要件で目標に入れない（§0.2）。裏の糸で比べ、画面は止めない|
|3 つのファイルのマージ・フォルダーの比較・プレビューでの比較|要件定義書 §5.2（将来）|

- **日の出・日の入りの配色**は描くたびに今の時刻で選ぶ。起動中に時刻をまたげば、次に描いたときに変わる

#### 文書を書き換える操作は 1 つの編集にする

目次の作り直し・番号を振る・外す・検査の「直す」「まとめて直す」は、**変わった範囲だけを 1 つの編集にして
当てる**（同じ頭と尻を除く。§10.65 のパッチを当てる処理と同じ）。元に戻すで 1 回で戻る。番号を振った文書
（半分以上の見出しに番号がある文書）は、保存の前（`save_to`）にも振り直す。

#### 検査の重さ

書き換えるたびに `update` の出口で検査し直す。**512 KB を超える文書は、見えているあたりだけを検査する**
（右端での折り返しの上限と同じ）。そのときは、見出しの段（MD001）のように前後を見る規則も見えているあたりの
中だけで判断する。波線は空行の指摘（MD012）もあるので、空行でも引く。

#### 光と影（R-12）

- 面は角の丸み 8・細い縁・下へ落ちる柔らかい影（ずれ 8・ぼかし 24）。帯は影を浅く（ずれ 2・ぼかし 8）、
  メニューは本文の上に重ねるので中くらい
- 明るい配色か暗い配色かは地の色の輝度で決め、影と縁の濃さを変える（暗い配色は影を濃く、面を一段明るく）
- ボタンは休んでいるときだけ下へ 1px の影を付け、ホバーで明るく、押すと影が消えて沈んで見える。
  主な操作（保存・閉じる・出力・決定）は強調色
- 窓いっぱいの画面（設定画面・アプリ内のファイル選択）は周りを 12 空けた面（`sheet`）、本文の上の帯（検索・
  行へ移動・絞り込み）は一段浮かせた帯（`float`）に入れる

#### 集中モード（R-13）

- 入る・出るは `Message::ToggleFocusMode`（表示メニュー・F11）。全画面は `iced::window::set_mode` で、
  OS ごとの差は winit が吸う。**入る前に最大化していたかを聞いておく**（`FocusWasMaximized`）
- 集中モードの間は窓の大きさ・位置の知らせを覚えない（`window_width` だけは画面の組み立てに使う）。全画面のまま
  終わったときは、入る前の窓の様子を覚える（`ExitGeometry`）。次に開くと画面いっぱいの窓になるのを防ぐ
- **Esc は開いたものを先に閉じる。** 何も開いていないとき（`App::nothing_on_top`）だけ集中モードを出る。
  購読（`subscription`）の Esc の連鎖の最後と、試験の口の `escape_message` の最後に置く
- 外で書き換えられた知らせ・失敗の知らせ・検索バーは、集中モードでも出す（見落とすと困るもの・自分で開いたもの）
